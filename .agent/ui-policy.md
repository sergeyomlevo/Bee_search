# UI Policy — Bee Search

## Назначение и границы

Этот файл — постоянная редактируемая project-level policy для пользовательского
интерфейса Bee Search. Он применяется при создании, изменении, review и
verification пользовательских экранов, controls, текстов, layout, форм,
keyboard/IME, списков и повторяющихся workflows.

Это не skill для отдельной операции, не описание конкретного экрана и не новый
decision framework. Policy задаёт общие эргономические правила для UI, но не
переопределяет explicit current user instruction, ACCEPTED decisions, product
requirements, domain semantics или persistence rules. Конкретная domain
semantics остаётся в `docs/` и `docs/decisions.md`.

## 1. Полный и понятный пользовательский текст

Значимые пользовательские надписи должны отображаться целиком. Не допускаются
clipping, скрытые окончания, многоточие вместо значимой части текста,
неестественный перенос слов, перенос, который неоправданно увеличивает высоту
control, или сокращение, смысл которого нужно угадывать.

Если текст не помещается, искать решение в таком порядке:

1. сделать layout компактнее;
2. разумно уменьшить font size, сохранив читаемость;
3. сократить формулировку без потери смысла;
4. заменить длинное слово или выражение более коротким и понятным.

Короткая надпись предпочтительнее длинной, если обе одинаково передают смысл.
Например, `Обычная` заменяется на `Грудь`, когда фактический смысл — положение
метки на груди. `Завершить` может быть заменено на `Стоп`, если контекст делает
это однозначным и product semantics не меняется.

Подпись control должна называть пользовательский атрибут, а не внутреннюю
техническую классификацию. Выбирай точную короткую формулировку, например
`Цвет метки` или `Расположение метки`. Field label обычно имеет меньший
визуальный вес, чем действие или section title: он объясняет control, но не
должен конкурировать с текущей работой за площадь viewport.

## 2. Реальный мобильный экран и увеличенный font scale

UI проектируется для физического Android-смартфона, а не только для IDE preview
или screenshot стандартного размера. Учитываются portrait orientation, system
bars, ограниченная площадь экрана, увеличенный system font, software keyboard,
работа пальцем и outdoor use.

Интерфейс должен оставаться практически работоспособным при увеличенном system
font scale. Текст не должен перекрывать соседние controls, обрезаться,
создавать неестественные переносы, делать основной workflow неудобным или без
необходимости вытеснять основные actions. При конфликте между длинной
формулировкой и площадью экрана сначала искать более короткий понятный текст,
а не бесконтрольно увеличивать высоту элемента.

У пользователя Bee Search увеличенный font scale — реальный режим работы, а не
теоретический edge case. Physical-device verification при таком scale является
значимым evidence. Успешная Compose compilation сама по себе не доказывает
пригодность layout.

Проектировать по доступному окну приложения, а не по фиксированной модели
устройства или физической ориентации. При ограниченной ширине, увеличенном font
scale, split-screen или ином изменении окна допустима адаптивная перестройка
рядов и порядка второстепенных элементов, если сохраняются понятность workflow,
видимость meaningful content и доступность primary action. Не требовать любой
ценой исходную геометрию и не заставлять читать или вводить данные с
горизонтальной прокруткой.

## 3. Видимый viewport поддерживает текущее действие

Видимая часть экрана прежде всего поддерживает действие, которое пользователь
выполняет сейчас. Основные controls повторяющейся операции должны оставаться
доступны без постоянной ручной прокрутки. Рост результатов предыдущих действий
не должен после каждого шага вытеснять рабочие controls за пределы viewport.

Например, при последовательном добавлении Bee пользователь должен удобно
видеть выбор цвета, выбор положения метки, `Добавить` и результат только что
выполненного Add. Редкие действия могут находиться ниже и быть доступны после
scroll.

Повторяющееся действие не должно неожиданно перестраивать весь экран:

```text
action
→ появился новый большой status/result block
→ рабочие controls сдвинулись
→ пользователь вынужден снова искать следующий action
```

Основные controls такого workflow сохраняют максимально стабильное визуальное
положение. При необходимости viewport адаптируется вокруг рабочей области.

На каждом состоянии экрана должно быть понятно, какое действие является
primary сейчас. Secondary actions и справочная информация не должны иметь
равную с ним визуальную доминанту или мешать быстро продолжить основной
workflow.

## 4. Просмотр созданных данных и viewport после Add

Если пользователь создаёт, добавляет или записывает данные через UI, он должен
в любой момент удобно найти и полностью просмотреть созданное содержимое. Это
включает Bee, ObservationPoint, текстовые описания, фотографии, измерения,
результаты наблюдений, списки и другие пользовательские данные.

Недопустимо, чтобы успешно созданные данные были скрыты неудачным layout,
постоянно обрезаны, перекрывались, становились практически недоступны по мере
роста списка или были видимы только через неочевидное действие. UI не должен
уметь хорошо создавать данные, но плохо показывать результат.

Не решать эту проблему автоматически новыми buttons `Просмотреть`, `Открыть
список`, отдельными screens или дополнительными taps, если данные естественно
показываются в текущем workflow. Для последовательного создания предпочтителен
invariant:

```text
добавил элемент
→ новый элемент полностью виден
→ следующее действие сразу доступно
```

После успешного Add UI по возможности автоматически поддерживает удобное
положение viewport: новый элемент полностью виден, основные controls следующего
Add остаются видны, а рабочая область остаётся максимально стабильной. Ранее
созданные элементы могут естественно уходить вверх, но весь список остаётся
доступен обычной прокруткой. Пользователь не должен вручную восстанавливать
scroll position после каждого повторяющегося действия.

Допустимы LazyColumn/LazyListState, controlled scroll или другой естественный
механизм. Policy не предписывает технологию: важен наблюдаемый UX. Автоматическая
коррекция должна быть минимально необходимой и избегать раздражающих jumps.

### Повторяющийся editor и растущий список

Когда один экран сочетает повторяющийся editor и список только что созданных
элементов, защищать нужно обе области, а не только controls. Полный список —
первоклассная рабочая информация; отдельная карточка «последний добавленный» не
заменяет удобный просмотр списка, если остальным элементам остаётся лишь узкая
полоска viewport.

### Намерение действия и намерение просмотра

В workflow с повторяющимся editor и растущим списком различать два равноправных
намерения пользователя:

```text
успешный Add
→ editor остаётся в рабочем положении
→ новый результат виден рядом с ним
→ следующее действие сразу доступно

ручной scroll к списку
→ список получает максимум полезного viewport
→ editor естественно уходит за границу viewport
→ пользователь может просмотреть накопленные данные
```

Не стабилизировать editor ценой sticky container, который на target device и
font scale оставляет данным лишь символическую высоту. Если action и review
являются стадиями одного workflow, предпочитать один естественный scroll-контур
вместо отдельного экрана, режима или дополнительного control. Автоматически
возвращать рабочее положение допустимо после successful state-changing action
или явного выбора пользователя, но не во время deliberate manual scroll: UI не
должен бороться с намерением просмотреть созданные данные.

## 5. Следующее состояние готово к работе

После успешного повторяющегося действия UI автоматически подготавливает
следующее валидное состояние, если оно определяется однозначно. Не заставлять
пользователя повторять выбор, который система может безопасно сохранить или
вычислить. Автоматически предложенный выбор всегда можно изменить вручную.

Пример Bee preparation:

```text
Белая + Грудь
→ Add
→ Белая + КП
```

Если варианты текущего цвета исчерпаны, может быть выбрана первая доступная
комбинация следующего цвета в project/catalog order.

### Feedback, progress, unavailable и errors

После significant user action интерфейс должен ясно показать, что произошло,
какое состояние теперь актуально и что можно сделать дальше. Если изменившийся
контент или state сам даёт это понимание, не добавлять ради него snackbar,
modal или постоянный status banner.

Во время сохранения или другой значимой операции показывать пропорциональный
progress/availability state и не допускать неясного повторного запуска. Disabled
control должен выглядеть недоступным; если причина неочевидна, рядом должно
быть понятное условие доступности или следующий полезный шаг. Error описывает
произошедшее и способ продолжить или исправить ситуацию рядом с проблемой, без
developer terminology, кодов ошибок и обвиняющего тона.

### Review достижимых состояний и переходов

UI review и device verification охватывают не только основной статический
layout, но и все релевантные пользовательски достижимые состояния и переходы.
Перед завершением существенной UI-задачи составить небольшой state inventory
для затронутого workflow и проверить применимые варианты: исходный и
заполненный контент, success feedback, error, progress/disabled, confirmation
и cancel, undo/correction, empty/unavailable state, длинный список и
state-changing переходы. Проверять именно результат перехода, а не только
состояние до нажатия.

Один happy-path или screenshot статического layout не является достаточной UI
verification. Особенно проверить, что transient feedback отображается целиком,
не перекрывает текущий или следующий необходимый action и не становится
непригодным при увеличенном font scale. Не создавать искусственные состояния,
если они не достижимы в текущем workflow; в таком случае явно указать границу
проверки или `UNKNOWN`.

## 6. Text entry и keyboard/IME

При вводе текста, числа или иных данных активное поле и вводимый текст должны
оставаться видимыми. Relevant action по возможности остаётся доступным.
Software keyboard не должна скрывать текущую рабочую область или редактируемое
поле; при её появлении и исчезновении viewport корректируется при необходимости
appropriate IME, insets или scroll behavior.

То же относится к status/navigation bars, display cutouts и системным жестам:
meaningful content и interactive controls не должны оказываться под system UI.
Проверять реальное доступное окно и корректную реакцию на IME/insets, а не
только layout без keyboard.

## 7. Информационная плотность

Постоянно видимый текстовый элемент должен помогать понять текущее состояние,
выполнить действие, понять результат, выбрать следующий шаг или предотвратить
существенную ошибку. Не показывать текст только потому, что системе известна
эта информация.

Избегать очевидных и служебных сообщений, дублирования, developer/debug
terminology и status text без практической пользы. Если подготовленные Bee
непосредственно видны, строка наподобие `Готово к выпуску: 3` может быть
избыточна.

Если необходимая информационная запись занимает значительную часть рабочего
экрана, предусмотреть возможность её свернуть. В collapsed state остаётся
короткий понятный заголовок, например `ВАЖНО! Первый выпуск` с
expand/collapse. Не использовать modal dialog для обычной справочной
информации без необходимости. Короткая критически важная информация может
оставаться постоянно видимой, когда это действительно нужно.

Progressive disclosure скрывает secondary details, но не primary action и не
необходимый текущий context. Collapsed control должен понятно сообщать, что
доступна дополнительная информация или functionality; не превращать disclosure
в способ спрятать важный следующий шаг.

### Раскрытие справочной информации

Раскрытие справки — это намеренный переход от выполнения повторяющегося
действия к чтению. В этом состоянии полный текст не может оказаться под fixed
editor или другим закреплённым рабочим блоком. Либо экран становится единым
scroll-контуром, либо editor естественно прокручивается вместе с остальным
контентом; начало раскрытой справки должно быть показано без ручного поиска.

Обычное следующее действие может оставаться непосредственно перед collapsed
справкой: тогда пользователь, уже знакомый с инструкцией, не обязан раскрывать
её перед каждым повторением workflow. После раскрытия это действие может
естественно уйти выше viewport вместе с editor, если текущая задача пользователя
— чтение справки.

## 8. Размеры, цвет, контраст и semantics

UI должен быть одновременно читаемым, удобным для уверенного нажатия пальцем,
компактным и пригодным для быстрой полевой работы. Большой элемент не является
автоматически более удобным. Размер текста, buttons, icons, selectable controls
и spacing выбирается по частоте и значимости действия.

Каждый interactive touch target имеет минимум 48dp по ширине и высоте. Visible
icon или graphic может быть меньше, если его реальная touch area остаётся не
менее 48dp; соседние target areas не должны перекрываться или вызывать
неоднозначное нажатие. Повторяющиеся действия получают приоритет по площади
перед справочной информацией, редко используемыми actions и декором.

Если конкретный цвет не задан product/domain semantics, выбирать его прежде
всего по читаемости, контрасту, различимости, outdoor use и яркому освещению.
Не использовать низкоконтрастные декоративные сочетания только ради эстетики.
Цвет не должен быть единственным способом передачи существенного состояния,
если его разумно дополнить indicator, формой, текстом, icon или другим признаком.

Meaningful icon, image и custom interactive control должны предоставлять
понятные localized accessibility semantics: название/назначение, role, current
state и доступное действие, когда они применимы. Decorative graphic не должен
создавать лишний noise для accessibility services. Не полагаться только на
визуальный вид, цвет или gesture, если action/state можно разумно передать
semantics либо доступной альтернативой.

### Icon-only controls

Если действие можно быстро и однозначно распознать по крупному, понятному и
устойчивому в данном контексте symbol/icon, не дублировать его постоянно
видимой текстовой подписью без необходимости. Это особенно полезно в плотных
мобильных интерфейсах, повторяющихся карточках, полевой работе и при
увеличенном font scale, когда label заметно уменьшает полезный viewport.

Icon-only control допустим, только если icon однозначен в данном контексте,
визуально достаточно крупен, touch target соответствует policy, control явно
выглядит интерактивным и accessibility description полностью передаёт действие.
Удаление текста не должно создавать опасную неоднозначность. Это не правило
«icons всегда лучше текста»: для сложного, неоднозначного или рискованного
действия сохранять visible label либо сочетание icon + text.

### Пространственный баланс control groups

При размещении нескольких самостоятельных controls или indicators в одной
строке проверять не только физическое размещение, но и визуальное
распределение. Семантически отдельные actions не должны случайно сливаться в
одну визуальную группу, одновременно оставляя большую бессмысленную пустоту в
другой части строки.

Использовать доступную ширину для perceptually balanced distribution с
понятной grouping semantics, достаточным separation между самостоятельными
actions, сохранением touch targets, visual hierarchy и стабильности layout.
Не требовать механически равных расстояний: распределение должно следовать
смысловым группам и текущему действию пользователя.

Пространственный баланс не означает, что элементы должны каждый раз
растягиваться по всей доступной ширине. Для повторяющихся карточек и controls
приоритет имеет spatial stability: одно и то же действие по возможности
сохраняет одну и ту же позицию между состояниями.

Осмысленная пустая зона допустима, если она сохраняет стабильные семантические
slots и мышечную память пользователя. Исчезновение соседнего control не должно
без необходимости перемещать остальные controls. При конфликте stable action
position / muscle memory имеет приоритет над равномерным распределением
оставшихся controls.

## 9. Confirmation и field-first

Не добавлять confirmation dialog автоматически. Он оправдан прежде всего для
разрушительного или трудно обратимого действия, создания значимого research
result либо действия с существенными последствиями, которое легко вызвать
случайно.

Transient cancel обычно непосредственный:

```text
Отмена подготовки ObservationPoint
→ discard transient draft
→ main map
```

без дополнительного dialog. При этом `Пчёлы отсутствуют`, как значимый
отрицательный research result, может иметь отдельное confirmation.

Если reversible действие можно безопасно исправить после выполнения, простой
undo или понятная локальная correction может быть лучше interruptive
confirmation. Не имитировать undo и не ослаблять persistence/domain guarantees:
реальная обратимость определяется current user instruction, accepted decisions
и decision-policy.

Bee Search прежде всего полевой инструмент. При UI trade-off учитывать яркий
солнечный свет, работу одной рукой, спешку, отвлечение оператора, увеличенный
font scale, повторяющиеся быстрые действия и отсутствие сети. Минимизировать
лишние taps, scrolling, повторный выбор, дополнительную навигацию, чтение
служебного текста и необходимость помнить скрытое состояние UI. Если интерфейс
может автоматически и однозначно адаптироваться к следующему действию,
предпочитать это дополнительному ручному действию.

## 10. Граница UI policy

UI policy не переопределяет domain semantics, ACCEPTED decisions, persistence
boundary, research semantics или epistemic discipline. Она не создаёт новые
domain requirements и не заменяет decision log. Если эргономическое правило
конфликтует с accepted product/domain decision, агент сообщает о конфликте, а
не меняет semantics самостоятельно.

При конфликте применяется порядок: explicit current user instruction →
ACCEPTED product/domain decision → project UI policy → generic external
guidance. Apple HIG, Android Developers и Material guidance — baseline для
эргономики и accessibility, а не разрешение молча менять Bee Search semantics
или переносить iOS visual conventions в Android application.

## 11. External design baselines

Эта policy адаптирована с учётом официальных источников, а не заменяет их:

- Apple Human Interface Guidelines: design principles, accessibility, layout,
  writing, feedback и disclosure controls;
- Android Developers: Compose accessibility semantics/API defaults, adaptive
  layouts и window/IME insets;
- Material Design 3: accessible design, interaction states и typography.

При Android/Compose implementation constraints использовать актуальную
Android/Material guidance прежде platform-neutral формулировки этой policy.

Sources:

- https://developer.apple.com/design/human-interface-guidelines/
- https://developer.android.com/develop/ui/compose/accessibility/api-defaults
- https://developer.android.com/develop/ui/compose/accessibility/semantics
- https://developer.android.com/develop/ui/compose/system/insets-ui
- https://developer.android.com/develop/adaptive-apps/guides/support-different-display-sizes
- https://m3.material.io/foundations/accessible-design/overview

## 12. Operational verification checklist

Перед завершением существенной UI-задачи проверить применимые пункты:

- [ ] Значимые надписи отображаются полностью.
- [ ] Нет неестественных переносов слов.
- [ ] Нет clipping/overlap.
- [ ] Основное действие легко найти.
- [ ] Основные controls соответствуют текущему действию.
- [ ] Одно и то же действие сохраняет стабильную позицию между состояниями.
- [ ] Исчезновение соседнего control не заставляет остальные controls ненужно перемещаться.
- [ ] Оставшееся пустое пространство является осмысленным semantic slot, а не случайным layout gap.
- [ ] Повторяющиеся controls не вытесняются ростом контента.
- [ ] После повторяющегося действия UI сразу готов к следующему действию.
- [ ] Автоматическая viewport-коррекция не борется с deliberate manual scroll.
- [ ] Новый созданный элемент полностью виден после создания.
- [ ] Уже созданные элементы можно удобно найти и полностью просмотреть.
- [ ] Рост списка не делает предыдущие элементы практически недоступными.
- [ ] Если viewport можно адаптировать автоматически, для этого не введены лишние navigation actions.
- [ ] Пользователю не приходится вручную восстанавливать рабочую позицию scroll после каждого повторяющегося действия.
- [ ] Primary action различим и не конкурирует с secondary actions.
- [ ] Каждый interactive target не менее 48dp и не перекрывает соседний target.
- [ ] Meaningful icons и custom controls имеют применимые accessibility semantics.
- [ ] Нет redundant visible label у однозначного icon-only action.
- [ ] Visible label не удалён там, где icon недостаточно понятен.
- [ ] Icon-only control визуально отличается от своего background, а его форма и роль различимы.
- [ ] Самостоятельные controls в одной строке не слиплись в одной части при бессмысленной пустоте в другой.
- [ ] Доступная ширина используется композиционно и функционально разумно.
- [ ] Экран не перегружен нерелевантным текстом.
- [ ] Длинная справочная информация сворачивается, если это уместно.
- [ ] Значимое действие даёт пропорциональный feedback; disabled/error state понятен.
- [ ] Проверены релевантные достижимые состояния и переходы, а не только static happy path.
- [ ] Transient feedback, undo и persistent error отображаются полностью и не перекрывают текущий или следующий action.
- [ ] Keyboard, system bars и IME не закрывают активное поле, текущую рабочую область или action.
- [ ] Layout адаптирован к доступному окну, а не предполагает один размер устройства.
- [ ] Контраст пригоден для полевой работы.
- [ ] Нет лишних confirmation dialogs.
- [ ] Проверено поведение при увеличенном font scale.
- [ ] Если возможно, выполнена проверка на physical Samsung.

Checklist применяется только к relevant properties конкретной задачи. Не
объявлять свойство PASS только потому, что код выглядит правильным. Если
свойство фактически не проверено, применять `.agent/decision-policy.yaml`:
использовать existing epistemic discipline и при необходимости сообщать
`UNKNOWN`.

## 13. Living policy

`.agent/ui-policy.md` — living project policy. Когда реальная эксплуатация
выявляет повторяющуюся UI-проблему:

1. исправить конкретную проблему;
2. определить, является ли вывод общим;
3. если это общее правило — предложить дополнение к этой policy;
4. после принятия пользователем применять его в будущих UI-задачах.

Не превращать единичное решение конкретного экрана в глобальное правило без
достаточных оснований. Повторение одной и той же проблемы на разных UI-задачах
— сильное основание формализовать общее правило.

# Операция резервного копирования — design-only спецификация (single capture)

**Статус:** проектирование для следующего слайса (Backup UI + оркестрация). Реализация не начата.
Никакие принятые решения S6A/S6B здесь не пересматриваются: защита медиа, проверка требуемого набора,
профиль копии и поведение discovery остаются такими, какими они закрыты в S6A/S6B.

Связанный макет: `docs/ui/mockups/backup-v1.md` + `backup-v1.png` / `backup-v1-result.png`.

---

## 1. Зачем нужен отдельный компонент

Одна пользовательская кнопка `Создать резервную копию` внутри делает две вещи, которые сегодня
принадлежат разным механизмам:

```text
защита медиа        (S6A: MediaProtectionService.protect)
резервная копия     (S6B: RepositorySnapshotService.createFull)
```

Если собирать операцию «в лоб» из существующих публичных вызовов, получится:

```text
MediaProtectionService.protect(живое состояние)      ← первое чтение Room
        ↓
RepositorySnapshots.create()                          ← внутри ЕЩЁ одно чтение Room
```

Между двумя чтениями состояние может измениться (пользователь снял фото, добавил объект, поменял
настройки). Тогда:

- копия опишет состояние B, а медиа защищалось для состояния A;
- либо создание упадёт на блобе, которого не было в момент защиты, и пользователь увидит ошибку,
  которая не соответствует тому, что он сделал;
- при этом каждый шаг по отдельности «работает правильно».

Поэтому оркестрация — это не UI-логика, а отдельная application/domain-операция с одним неизменяемым
захватом.

## 2. Критический инвариант

```text
нажатие «Создать резервную копию»
        ↓
ОДИН неизменяемый захват Room + portable settings
        ↓
из ЭТОГО ЖЕ захвата:
    • снимок данных (то, что публикуется)
    • требуемый набор медиа
    • пути к приватным оригиналам медиа
        ↓
недостающие медиа принимаются в резервное хранилище (per-blob, S6A)
        ↓
все требуемые медиа ЭТОГО захвата проверяются в том же хранилище (S6B, read-only)
        ↓
копия публикуется ИЗ ТОГО ЖЕ захвата
        ↓
успех
```

После возврата захвата живые Room/DataStore больше не читаются. Всё добавленное после захвата
относится к следующей копии.

## 3. Где живёт компонент

- Пакет: `org.beesearch.app.data.backupoperation` (новый узкий пакет уровня application/domain, рядом
  с `data/backuprepository` и `data/backupsnapshot`; новый пакет оправдан устойчивой границей
  «одна операция резервного копирования»).
- Имя по конвенциям проекта (`BackupOperationCoordinator` уже занят координацией UI-состояния S2):
  предлагается **`CreateBackupOperation`** — одна операция, один неизменяемый захват.
- Компонент не зависит от Compose. ViewModel запускает операцию и отображает её состояние; семантика
  «что считается успехом» находится в компоненте, а не в экране.
- Компонент не заводит ни DataStore-ключей, ни таблиц, ни глобального индекса. Состояние операции
  живёт в памяти на время операции и её результата (как у S2), а постоянные факты по-прежнему читаются
  из содержимого резервного хранилища.

## 4. Какие существующие API используются

| Шаг | Существующий API | Что даёт |
|---|---|---|
| один захват | `database.withTransaction { database.backupDao().snapshot() }` | `Graph` — тот же вызов, которым сегодня пользуются `SnapshotCapture` и `MediaStateCapture` |
| настройки | `PortableSettingsStore.snapshot()` | `PortableSettingsSnapshot` (как в `SnapshotCapture`) |
| снимок данных | `SnapshotDomainCodec.encode(graph, settings)` | `SnapshotDomainEntries` — чистая функция, без I/O |
| требуемый набор | `RequiredMediaSet.resolve(...)` через `SnapshotDomainCodec.references` | единственное определение eligibility/dedup/расширения (S6A) |
| источники медиа | маппинг строк `graph.objectMedia` / `graph.attachments` в `CapturedMediaRow` | те же записи, что даёт `MediaStateCapture` |
| защита | `MediaProtectionPlanner.plan(captured)` + `MediaProtectionService.protect(captured, cancelled)` | per-blob результаты: `INGESTED` / `ALREADY_PRESENT` / ошибки |
| публикация | `RepositorySnapshotService.createFull()` → `BoundRepository.createFullSnapshot(...)` → `RepositorySnapshots.create(..., SnapshotEvidenceProfile.FULL_LOCAL_VERIFIED)` | проверка требуемого набора read-only и публикация снимка |

## 5. Минимальное изменение API

Сейчас захват находится **внутри** `RepositorySnapshots.create`, поэтому вызвать публикацию с уже
готовыми `SnapshotDomainEntries` нельзя. Минимальная правка — поднять захват на один уровень:

1. `RepositorySnapshots.create(capture: suspend () -> SnapshotDomainEntries, ...)` →
   `RepositorySnapshots.create(entries: SnapshotDomainEntries, ...)`.
   Внутри остаётся ровно то же: сборка архива, проверка медиа-доказательств, публикация, readback.
2. `RepositoryFoundation.createMetadataSnapshot(...)` сохраняет внешнюю сигнатуру (захват ровно один
   раз внутри этого вызова) и делегирует в новый вариант с готовыми `entries`.
3. Добавляется `RepositoryFoundation.createFullSnapshotFromCaptured(expectedRepositoryId, workspace,
   entries, cancelled)` и соответствующая обёртка в `BoundRepository` и `RepositorySnapshotService`
   (`createFullFromCaptured(entries)`).
4. `MediaStateCapture` и `SnapshotCapture` получают чистое «отображение из уже захваченного `Graph`»
   (`rowsOf(graph)` / `entriesOf(graph, settings)`), чтобы правило маппинга существовало один раз и им
   пользовались и старые одиночные вызовы, и новая операция.

Существующие одиночные API (`create()`, `createFull()`, `MediaProtectionService.protect(captured)`)
остаются рабочими и совместимыми: они просто вызывают те же шаги по отдельности. Никакого второго
протокола публикации и второго определения требуемого набора не появляется.

## 6. Как гарантируется ровно один захват

- Захват делает сама операция, один раз, и передаёт дальше **значения** (`Graph` → `SnapshotDomainEntries`
  и список строк медиа), а не лямбды, которые могли бы прочитать состояние повторно.
- Публикация принимает готовые `entries`; пути к источникам медиа выводятся из того же `Graph`.
- Пошаговое подтверждение:
  1. code review: в операции и в вызываемых ею компонентах нет второго обращения к `backupDao()`,
     `database.withTransaction`, Room-запросам и `PortableSettingsStore`;
  2. JVM-тест со счётчиком: фейковый источник графа считает чтения и asserts `reads == 1` для успешной
     операции, для операции с ошибкой медиа и для отмены;
  3. детерминированный тест границы захвата (тот же приём, что уже принят в S6B): после захвата
     добавить новое медиа и убедиться, что первая операция его не требует, а следующая — требует;
  4. device-тест: на реальном состоянии устройства результат операции ссылается ровно на тот набор
     медиа, который был защищён в этой же операции.

## 7. Порядок шагов и что считается успехом

1. Проверка предусловий: доступ к резервному хранилищу и его identity (существующие состояния S1).
2. Один захват (Room + portable settings).
3. Из захвата: `SnapshotDomainEntries`; требуемый набор; список приватных источников.
4. Планирование и защита недостающих блобов (per-blob; уже защищённые → `ALREADY_PRESENT`).
5. Если хотя бы один требуемый блоб не защищён → операция завершается ошибкой медиа:
   копия не публикуется; уже принятые блобы остаются и переиспользуются при повторе.
6. Публикация копии из того же захвата с профилем локального подтверждения: read-only проверка
   требуемого набора в том же хранилище непосредственно перед публикацией.
7. Успех только когда копия опубликована и все требуемые блобы этого захвата проверены.

Отдельного «успеха с оговоркой» нет: либо копия с проверенным медиа, либо нет копии.

Ошибки, которые UI обязан различать (тексты — в макете):

| Причина | Что показывать пользователю |
|---|---|
| не удалось сохранить часть фото/видео | `Резервная копия не создана` + количество несохранённых (ошибка медиа) |
| нет свободного места | сообщение о нехватке места |
| потерян доступ к папке (подтверждено свежей проверкой) | состояния доступа S1 + `Восстановить доступ` |
| логическая несогласованность данных | существующее сообщение о несогласованности |
| сбой контейнера копии | существующее сообщение о неудачной копии |
| отмена/прерывание | не показывается как успех; копия не создаётся |

## 8. Границы, которые нельзя переходить

- Оркестрация не живёт в Compose-экране и не собирается из UI-вызовов двух сервисов по очереди.
- Не создаётся долговечное состояние «последняя полная копия», «сколько медиа проверено» и подобное:
  постоянные факты читаются из содержимого хранилища.
- Не вводится новая архитектура отмены и кнопка `Отмена` (см. макет).
- Не меняются принятые лимиты медиа и правила S6A/S6B.

## 9. Ограничение для S5: стоимость проверки

Уже сегодня (S6B) обычное открытие экрана вызывает discovery, а discovery для копии с полным
подтверждением перечитывает и хеширует все требуемые блобы. На четырёх фотографиях это незаметно; на
20–50 ГБ это неприемлемо.

Поэтому для S5 фиксируется обязательное требование:

> Обычное открытие экрана резервного копирования и обычный discovery **не должны** требовать полного
> повторного чтения всех медиа-байтов.

Разделение, которое S5 должен окончательно определить:

| Слой | Что делает | Стоимость |
|---|---|---|
| сильная проверка при создании копии | фактический размер + SHA-256 каждого требуемого блоба (S6B, D101) | пропорциональна объёму медиа; выполняется в операции |
| дешёвое обычное состояние экрана | инвентарь: наличие канонических файлов и их размеры по листингу | один листинг каталога |
| политика проверки `вне операции` | presence+size / явная проверка по действию / ленивая проверка / фоновая проверка | предмет решения и измерений в S5 |

Решение между этими вариантами здесь **не принимается**. Отдельно отмечается, что выбранная политика
определяет и смысл любой медиа-строки в UI: сильное «проверено» относится только к результату
выполненной операции, а обычное состояние экрана не должно обещать проверку, которую оно не делало.

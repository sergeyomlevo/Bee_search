# Bee Search — Architecture & Product Decisions

## 1. Назначение документа

Этот документ фиксирует существенные продуктовые и архитектурные решения проекта **Bee Search**.

Его задача — не допустить повторного обсуждения уже принятых решений и случайного изменения базовых принципов проекта при дальнейшей разработке.

Документ дополняет:

- `product-requirements.md`;
- `user-workflows.md`;
- `domain-model.md`;
- `data-model.md`;
- `architecture.md`.

Если реализация требует изменить одно из зафиксированных здесь решений, изменение должно быть сначала осознанно обсуждено и отражено в документации.

---

# 2. Статусы решений

Используются следующие статусы:

- `ACCEPTED` — решение принято;
- `PROVISIONAL` — предварительное решение, которое требует проверки;
- `DEFERRED` — решение сознательно отложено;
- `SUPERSEDED` — решение заменено другим.

---

# D001 — Android как первая платформа

**Статус:** ACCEPTED

Первая версия Bee Search разрабатывается как нативное Android-приложение.

Основной язык:

`Kotlin`

UI:

`Jetpack Compose`

### Причина

Приложение предназначено прежде всего для полевой работы со смартфоном и требует прямого доступа к:

- GPS;
- датчикам ориентации;
- локальному хранилищу;
- офлайн-картам.

Разработка iOS-версии в MVP не планируется.

---

# D002 — Offline-first

**Статус:** ACCEPTED

Bee Search проектируется как offline-first приложение.

Все основные полевые функции должны работать без интернета:

- просмотр заранее подготовленной карты;
- создание точки;
- регистрация пчёл;
- регистрация вылетов;
- регистрация возвращений;
- регистрация азимута;
- завершение наблюдения;
- просмотр локальных результатов.

### Следствие

Сервер не должен участвовать в критическом пути регистрации полевого события.

Правильная последовательность:

`действие пользователя → локальное сохранение → продолжение работы → синхронизация позднее`

---

# D003 — Room / SQLite как локальное хранилище

**Статус:** ACCEPTED

Основные исследовательские данные хранятся локально с использованием:

`Room + SQLite`

### Причина

Необходимы:

- транзакции;
- связи;
- ограничения целостности;
- миграции;
- Flow;
- надёжное восстановление состояния после закрытия приложения.

DataStore используется только для небольших локальных настроек устройства.

---

# D004 — Текущая территория хранится в настройках устройства

**Статус:** ACCEPTED

Текущая территория не является свойством `Territory`.

Не используется:

`Territory.is_current`

Вместо этого в локальных настройках хранится:

`current_territory_id`

### Причина

«Текущая территория» — состояние конкретной установки приложения, а не свойство исследовательской территории.

После явного выбора территории она становится текущей и используется при следующих запусках приложения.

---

# D005 — Подготовка карты для офлайн является необязательной гарантией

**Статус:** ACCEPTED

Bee Search использует одну обычную карту. При наличии сети она может получать
картографические ресурсы online. Пользователь может выбрать один или несколько
прямоугольных фрагментов и выполнить действие `Подготовить для офлайн`; после
успешной подготовки их составное покрытие гарантированно доступно без сети.

Offline preparation не создаёт отдельный пользовательский режим карты и не
является обязательным условием создания, выбора или использования `Territory`.
Отсутствие подготовленного пакета не блокирует GPS, создание
`ObservationPoint` и другие исследовательские операции. Если сеть недоступна,
карта за пределами подготовленного покрытия может отображаться неполно, но
локальный research workflow остаётся доступен.

Следует различать:

```text
online availability
offline readiness
```

Видимая за счёт сети или ambient cache карта не доказывает offline readiness.

### История изменения

Первоначальная редакция D005 включала выбор области и загрузку карты в создание
Territory и требовала подготовить карту до обычной полевой работы. После
исследования MapLibre offline delivery эта обязательность отменена. Сохранён
номер D005, а текущее правило заменяет прежнюю редакцию.

### Следствие

Пользователь не должен начинать обычную полевую работу с постоянного повторного выбора территории.

---

# D006 — MapLibre как картографический движок

**Статус:** ACCEPTED

В качестве картографического движка используется:

`MapLibre Native for Android`

### Причины

- открытый исходный код;
- возможность встроить карту непосредственно в приложение;
- поддержка собственных источников;
- пригодность для offline-first архитектуры;
- отсутствие необходимости строить приложение поверх готового картографического пользовательского приложения.

### Важно

MapLibre является движком отображения карты.

Он не определяет автоматически:

- источник карт;
- формат офлайн-карт;
- стиль;
- механизм распространения картографических данных.

Эти решения принимаются отдельно.

---

# D007 — Первый offline milestone использует MapLibre OfflineRegion

**Статус:** SUPERSEDED BY D063

**Заменено решением:** D063

Первый production milestone офлайн-подготовки использует:

- `MapLibre Native Android OfflineRegion`;
- общую MapLibre resource database для online cache и offline regions;
- прямоугольные области, выбираемые пользователем;
- foreground-only download с progress, pause/resume и retry;
- те же canonical resource URLs, которые использует обычная online-карта.

Обычная карта и подготовленное покрытие являются одной картой: локально
сохранённые ресурсы используются там, где они существуют, а при доступной сети
отсутствующие ресурсы могут загружаться online. Отдельный переключатель
`online map / offline map` не создаётся.

Offline coverage задаётся составом одного или нескольких rectangle fragments.
Каждый фрагмент может первоначально формироваться из текущего viewport и
добавляться пользователем до начала download. Фрагменты могут иметь разный
охват и частично перекрываться; логическое покрытие является их объединением.
Автоматический fixed buffer и сведение состава к одному общему bounding
rectangle не используются. Bounds не являются данными `Territory` и не
сохраняются в Room research schema.

Region считается готовым только когда существует совместимый
`OfflineRegion`, его definition соответствует требуемым bounds и zoom, metadata
связывает его с нужными Territory/package/profile, а
`OfflineRegionStatus.isComplete == true`. Ambient cache и
`downloadState == inactive` сами по себе не означают Ready.

Bounds существующего `OfflineRegion` не меняются in place. Допускаются несколько
additive regions; при таком расширении существующее Ready coverage сохраняется.
При replacement старый region удаляется только после того, как новый подтверждён
как полностью Ready, совместим с нужным profile и покрывает необходимую старую
область.

Первый milestone не обещает продолжение загрузки после process death и не
требует background service. После restart приложение перечитывает status и
может продолжить incomplete region в foreground.

PMTiles и MBTiles не используются как формат первого milestone. PMTiles может
позднее рассматриваться для заранее подготовленных автономных packages, но не
является активной архитектурой текущего workflow.

# D008 — Bee Search использует собственный OSM-derived field source

**Статус:** ACCEPTED

Основной vector source строится по цепочке:

```text
Raw OSM
→ Planetiler / OpenMapTiles-compatible generation
→ минимальный Bee_search field profile
→ versioned MVT внутри PMTiles Map Package
→ acquisition-independent delivery
→ app-controlled local storage
→ MapLibre
```

Конкретный cloud/CDN vendor и способ получения package не фиксируются.
Stateful tile server не является обязательным архитектурным условием. Offline
delivery использует PMTiles Map Package по D063; manual import и future server
download должны приводить к одному совместимому локальному artifact. Online
delivery может использовать отдельный совместимый transport. Несовместимая
версия не должна молча переиспользовать identity или resources старого profile.

Стандартные OpenMapTiles-compatible layers переиспользуются для roads,
tracks/paths, waterways, landcover, buildings, settlements, railway и bridges.
Минимальное Bee_search extension сохраняет:

- `man_made=cutline`;
- `power=line` и `power=minor_line`;
- `tracktype`;
- field-relevant surface detail beyond generic paved/unpaved.

Окончательная нормализация surface categories остаётся задачей implementation
PoC; другие OSM tags не добавляются без подтверждённой полевой пользы.

Baseline zoom contract:

- vector source maxzoom — `15`;
- offline Map Package maxzoom — `15`;
- UI maxzoom — `20`;
- `z16–20` отображаются через vector overscaling.

Source z16 может быть принят позднее только после ограниченного Samsung A/B PoC,
если дополнительная полевая детализация оправдывает рост размера package и
времени его получения. Source z17–20 не входят в первый milestone.

Используется один versioned field `MapProfile`, описывающий совместимость
schema/profile, dataset snapshot, style/resources, zoom contract и attribution.
Provider catalog не создаётся. Старый активный Map Package должен оставаться
интерпретируемым после публикации новой версии profile.

Satellite не входит в обязательный vector offline milestone. При наличии
подходящих прав provider он может работать online независимо от vector
readiness, а позднее — иметь отдельный optional offline package с собственными
bounds, zoom, provider/profile и lifecycle. Конкретный satellite provider пока
не выбран. Contours, hillshade и DEM отложены.

Source data и delivery terms должны разрешать предусмотренную генерацию,
attribution и массовую подготовку выбранных областей для длительного локального
offline use.

# D009 — Минимальная предметная модель

**Статус:** ACCEPTED

Основная иерархия данных:

`Territory → ObservationPoint → Bee → FlightCycle`

Новые сущности не создаются без практической необходимости.

### В частности, пока отсутствуют отдельные сущности

- `ObservationSession`;
- `GroupRelease`;
- `PhysicalPlace`;
- `BeeState`;
- `AzimuthMeasurement`;
- `OfflineMap`.

# D010 — Отдельной сущности Observer в MVP нет

**Статус:** SUPERSEDED by D061

Это решение описывало раннюю code-only модель. Она заменена отдельной сущностью
Observer и UUID-связью ObservationPoint с Observer.id.

---

# D011 — Координаты принадлежат ObservationPoint

**Статус:** ACCEPTED

Координаты хранятся только у:

`ObservationPoint`

Отдельные координаты не хранятся у:

- `Bee`;
- `FlightCycle`.

### Причина

Все наблюдаемые на одной точке пчёлы используют одно физическое место.

Повторное получение GPS для каждой пчелы только создавало бы искусственный пространственный разброс.

---

# D012 — GPS можно корректировать вручную

**Статус:** ACCEPTED

При создании ObservationPoint GPS используется как исходное предложение положения.

Пользователь должен видеть точку на карте и иметь возможность скорректировать её вручную.

Сохраняются:

- итоговые координаты;
- при наличии — исходные GPS-координаты;
- при наличии — GPS accuracy.

### Причина

В полевых условиях GPS иногда показывает положение со значимой ошибкой, тогда как пользователь может определить своё фактическое положение по карте и окружающим объектам.

---

# D013 — Одинаковые координаты разных ObservationPoint допустимы

**Статус:** ACCEPTED

Координаты ObservationPoint не являются уникальными.

Две разные точки могут иметь совершенно одинаковые координаты.

### Пример

Наблюдение:

`26 августа → координаты X,Y`

Повторное наблюдение:

`29 августа → координаты X,Y`

Это две разные ObservationPoint.

---

# D014 — Новое наблюдение через несколько дней создаёт новую ObservationPoint

**Статус:** ACCEPTED

Если нормальное наблюдение не получилось и пользователь возвращается в то же место через несколько дней, создаётся новая ObservationPoint.

Старая точка не переоткрывается для нового полноценного наблюдения.

### Причина

Изменяются:

- дата;
- набор пчёл;
- условия наблюдения;
- результаты;
- потенциально другие внешние факторы.

Таким образом ObservationPoint означает не только географическое место, но и конкретное полевое наблюдение.

---

# D015 — PhysicalPlace пока не создаётся

**Статус:** ACCEPTED

Несмотря на возможность повторных наблюдений в одном месте, отдельная сущность `PhysicalPlace` пока не нужна.

Совпадение или близость координат позволяет позднее определить повторные наблюдения.

### Возможное будущее изменение

Если постоянные места наблюдений станут самостоятельным объектом исследования, модель можно расширить.

До появления такой необходимости сущность не вводится.

---

# D016 — Bee существует внутри ObservationPoint

**Статус:** ACCEPTED

`Bee` относится к одной конкретной ObservationPoint.

Пчела автоматически не переносится между точками.

Даже одинаковая визуальная метка в другой ObservationPoint означает другую запись Bee.

---

# D017 — Метка Bee состоит из цвета и положения

**Статус:** ACCEPTED

Метка определяется комбинацией:

`mark_color + mark_position`

Положение:

- `NONE`;
- `RIGHT_WING`;
- `LEFT_WING`.

Пользовательское представление:

- Белая;
- Белая КП;
- Белая КЛ.

### Ограничение

Одинаковая комбинация метки не может использоваться дважды внутри одной ObservationPoint.

---

# D018 — Набор цветов должен расширяться

**Статус:** ACCEPTED

Модель данных не должна жёстко ограничиваться первоначальными цветами:

- белый;
- синий;
- жёлтый.

Добавление нового цвета не должно требовать изменения структуры базы данных.

Конкретный механизм управления списком цветов определяется позднее.

---

# D019 — До 10 одновременно активных Bee является основным UX-сценарием

**Статус:** SUPERSEDED

Заменено решением D055.

Рабочий интерфейс проектируется прежде всего для наблюдения примерно за:

`до 10 Bee`

Это не обязательно жёсткое ограничение базы данных.

### Причина

Главная проблема интерфейса — возможность быстро зарегистрировать события у нескольких пчёл, находящихся в разных состояниях одновременно.

---

# D020 — Состояния Bee независимы

**Статус:** ACCEPTED

Каждая Bee имеет собственную историю FlightCycle.

Событие одной Bee не изменяет состояния других Bee.

### Пример

Если синяя вернулась раньше белой, пользователь сразу регистрирует возвращение синей независимо от порядка первоначального выпуска.

---

# D021 — Bee.status отдельно не хранится

**Статус:** ACCEPTED

Отдельное поле:

`Bee.status`

не используется.

Состояние вычисляется из FlightCycle и состояния ObservationPoint.

### Причина

Это предотвращает расхождение между сохранённым статусом и фактической историей событий.

---

# D022 — Первый выпуск является групповым

**Статус:** SUPERSEDED (D075)

**Примечание:** первый выпуск больше не является групповым. Каждый первый вылет
регистрируется индивидуально для конкретной Bee и получает её собственное время
вылета. Текст ниже сохранён как история.

Первый выпуск подготовленных пчёл происходит практически одновременно.

Пользователь выполняет одно действие:

`ВЫПУСТИТЬ ВСЕХ`

Для каждой подготовленной Bee создаётся первый FlightCycle с одним и тем же `departure_time`.

---

# D023 — GroupRelease как отдельная сущность не создаётся

**Статус:** ACCEPTED

Отдельной таблицы или сущности `GroupRelease` нет.

Первый цикл каждой Bee однозначно определяется:

`FlightCycle.sequence_number = 1`

### Следствие

Дополнительное поле:

`is_initial_group`

не требуется.

---

# D024 — Первый вылет сохраняется атомарно

**Статус:** ACCEPTED

**Уточнено:** D075. Атомарность относится к созданию конкретной Bee вместе с её
первым FlightCycle и установкой `BEES_FOUND`; группового старта больше нет.

Создание Bee и её первого FlightCycle выполняется одной транзакцией.

Недопустимо сохранение Bee без первого цикла или цикла без Bee.

Операция должна быть:

`либо полностью успешна → либо не сохранена`

---

# D025 — FlightCycle является основной единицей истории полётов

**Статус:** ACCEPTED

Каждый вылет Bee создаёт отдельный FlightCycle.

Цикл содержит:

- `sequence_number`;
- `departure_time`;
- `return_time?`;
- `azimuth_deg?`.

Количество циклов заранее не ограничивается.

---

# D026 — Одновременно может существовать только один открытый FlightCycle одной Bee

**Статус:** ACCEPTED

Новый FlightCycle нельзя создать, пока предыдущий не получил `return_time`.

Это является предметным инвариантом и должно проверяться не только UI.

---

# D027 — Продолжительность FlightCycle не хранится

**Статус:** ACCEPTED

Отдельное поле `duration` не используется.

Для завершённого цикла:

`duration = return_time - departure_time`

Для текущего:

`duration = current_time - departure_time`

### Причина

Продолжительность полностью выводится из исходных временных значений.

---

# D028 — Азимут относится к конкретному FlightCycle

**Статус:** ACCEPTED

Азимут хранится как:

`FlightCycle.azimuth_deg`

Он относится к конкретному вылету конкретной Bee.

---

# D029 — Азимут необязателен

**Статус:** ACCEPTED

`azimuth_deg = null`

является нормальным состоянием.

Регистрация азимута не должна блокировать регистрацию времени вылета.

### Причина

Надёжно определить направление удаётся не всегда.

Ошибочный азимут потенциально вреднее отсутствующего.

---

# D030 — Азимут можно удалить

**Статус:** ACCEPTED

Если пользователь считает измерение ненадёжным, азимут может быть удалён.

Результат:

`azimuth_deg = null`

FlightCycle при этом сохраняется.

---

# D031 — 0° является действительным азимутом

**Статус:** ACCEPTED

`0°` означает север.

Поэтому значение `0` нельзя использовать вместо отсутствующего значения.

Отсутствующий азимут представлен только `null`.

---

# D032 — Азимут не считается направлением на гнездо

**Статус:** ACCEPTED

Зарегистрированный азимут является направлением наблюдаемого ухода Bee.

# D054 — Ручная корректировка ObservationPoint использует фиксированный прицел

**Статус:** ACCEPTED

При создании ObservationPoint карта первоначально центрируется на исходном GPS fix. В геометрическом центре карты отображается неподвижный прицел, а пользователь перемещает и масштабирует карту под ним.

Координаты центра карты являются предлагаемыми итоговыми координатами ObservationPoint. Они не подменяют исходные GPS-координаты и не сохраняются до явного подтверждения пользователя.

До подтверждения доступно отдельное действие возврата карты и прицела к исходному GPS fix. Draggable marker в этом сценарии не используется.

### Причина

Фиксированный прицел сохраняет выбранную позицию визуально стабильной, делает ручную коррекцию понятной на сенсорном экране и явно отделяет исходное GPS-измерение от подтверждаемой пользователем позиции.

# D056 — ObservationPoint хранит год наблюдения и номер в годовой области

**Статус:** ACCEPTED

Каждая `ObservationPoint` хранит обязательные поля:

```text
observation_year
point_number
```

`observation_year` назначается при создании точки по локальному календарному году устройства. Это самостоятельный сохранённый атрибут наблюдения: позднее он не пересчитывается из `created_at`. Поле `created_at` продолжает хранить абсолютный `Instant` в Unix epoch milliseconds.

`point_number` — человекочитаемый последовательный номер. Нумерация начинается с 1 и ведётся отдельно для каждой комбинации:

```text
Territory + observation_year + observer_id
```

Например:

```text
KLZ / 2026 / observer-UUID-A / 1
KLZ / 2026 / observer-UUID-A / 2
KLZ / 2026 / observer-UUID-B / 1
KLZ / 2027 / observer-UUID-A / 1
```

Локальная Room-база обеспечивает уникальность `(territory_id, observation_year, observer_id, point_number)`, а следующий номер вычисляется и записывается внутри одной транзакции. `device_id` в область нумерации не входит. Отдельная сущность `ObservationSeason` не создаётся.

UUID остаётся истинной устойчивой идентичностью точки. `point_number` не является идентификатором и не заменяет UUID.

При будущей синхронизации два устройства одного наблюдателя могут временно создать совпадающие локальные номера. Это допустимый конфликт отображаемой нумерации. После объединения номера в одной области могут быть перенумерованы в единую хронологическую последовательность без изменения UUID и исследовательских данных. Распределённый глобальный генератор номеров сейчас не создаётся.

Формат полного отображаемого кода наподобие `KLZ-2026-GSE-007` этим решением не фиксируется; O005 остаётся открытым.

# D057 — Результат присутствия пчёл фиксируется явно

**Статус:** ACCEPTED

`ObservationPoint` хранит nullable-значение `bee_presence_result` со значениями:

```text
BEES_FOUND
NO_BEES_FOUND
```

Семантика:

- `null` — результат ещё не установлен явно; подготовка может быть не завершена;
- `BEES_FOUND` — на точке найдены пчёлы;
- `NO_BEES_FOUND` — наблюдатель явно подтвердил отсутствие пчёл.

Ноль записей `Bee` сам по себе никогда не означает `NO_BEES_FOUND`.

Создание первой `Bee` вместе с её первым FlightCycle и установка `BEES_FOUND` выполняются атомарно. Последующие Bee сохраняют `BEES_FOUND`. Если локальная отмена ошибочно зарегистрированного первого вылета удаляет последнюю Bee на точке, результат возвращается в `null`. При `NO_BEES_FOUND` создавать Bee нельзя.

Отдельная операция `Пчёлы отсутствуют` должна одной транзакцией установить `NO_BEES_FOUND` и завершить ObservationPoint. Обычное завершение точки запрещено, пока результат равен `null`.

Отдельная сущность результата и универсальное поле `ObservationPoint.status` для этого смысла не создаются.

При миграции существующие точки, содержащие хотя бы одну Bee, получают `BEES_FOUND`; точки без Bee получают `null`, но никогда не получают `NO_BEES_FOUND` автоматически.

# D058 — Короткий первый FlightCycle сохраняется, но исключается из анализа

**Статус:** SUPERSEDED (D075)

**Примечание:** решение отменено D075. Автоматическое исключение первого
FlightCycle по 60-секундной эвристике больше не применяется: индивидуальный
`departure_time` первого вылета реально фиксирует момент вылета конкретной Bee,
поэтому отдельная эвристика для «группового» цикла не требуется. Текст ниже
сохранён как история.

Первый групповой выпуск по-прежнему создаёт для всех подготовленных Bee их первые FlightCycle с одним общим `departure_time`. Если отдельная Bee фактически не улетела вместе с группой, наблюдатель регистрирует её возвращение обычным действием. Когда она позднее действительно улетает, обычная операция следующего вылета создаёт `FlightCycle 2` с её реальным индивидуальным временем вылета.

Первый FlightCycle сохраняется как корректное исходное полевое наблюдение, но исключается из всех расчётов, основанных на содержательной продолжительности полёта, если и только если одновременно выполнены условия:

```text
sequence_number = 1
return_time is not null
return_time - departure_time < 60 seconds
```

Такой цикл не участвует в оценке продолжительности полёта, расстояния до гнезда, средних значений и будущем анализе вероятного положения гнезда. Он не удаляется, его общий `departure_time` не переписывается, а поздний индивидуальный вылет не подменяет первый цикл.

Ровно 60 секунд этим правилом не исключаются. Правило не применяется автоматически к `FlightCycle 2` и последующим коротким циклам.

Пригодность для анализа вычисляется из `sequence_number`, `departure_time` и `return_time`; отдельный флаг наподобие `is_valid` не хранится. Исключение из анализа не означает недействительность исходных данных. Реализация самого анализа расстояния до гнезда этим решением не вводится.

# D059 — Азимут хранится относительно истинного севера

**Статус:** ACCEPTED

`FlightCycle.azimuth_deg` хранит направление относительно истинного / географического севера.
Значение `0°` из D031 означает именно истинный север, а не магнитный.

`HeadingProvider` получает магнитное направление верхней короткой стороны телефона через Android
Sensor APIs. Для каждого вычисления оно корректируется через Android `GeomagneticField` с
подтверждёнными координатами текущей ObservationPoint, системным timestamp момента вычисления и
высотой `0 м`, если отдельная высота недоступна. После добавления магнитного склонения результат
нормализуется в диапазон `[0, 360)` и только затем показывается пользователю и может быть явно
сохранён в `FlightCycle.azimuth_deg`.

Магнитное направление является transient sensor value и не сохраняется как исследовательское
значение. Расчёт склонения работает офлайн. Схема Room и тип `Double?` не изменяются.

# D060 — Полевая возможность фиксации азимута однократна для FlightCycle

**Статус:** ACCEPTED

Active observation workflow предоставляет одну возможность one-tap фиксации азимута для каждого
открытого FlightCycle. Факт использования этой возможности хранится отдельно в
`FlightCycle.azimuth_capture_consumed` и не выводится только из nullable `azimuth_deg`.

Новый FlightCycle получает `azimuth_deg = null` и `azimuth_capture_consumed = false`. Успешная
field-capture операция атомарно сохраняет скорректированный true/geographic azimuth и устанавливает
`azimuth_capture_consumed = true`. Техническая ошибка не должна изменять ни одно из этих значений.

После успешной фиксации control становится read-only. Действие `ОТМЕНИТЬ` удаляет только
`azimuth_deg`; consumed остаётся `true`, поэтому повторное измерение того же вылета через active
observation UI невозможно. Закрытый FlightCycle также не допускает field capture. Следующий вылет
создаёт новый FlightCycle с новой однократной возможностью.

Persisted consumed-state обязателен для корректного восстановления после process death/restart.
Обычная repository-возможность изменить или удалить азимут сохраняется отдельно для будущего
history/edit workflow и не меняет семантику однократной полевой фиксации.

Room schema v3 добавляет `azimuth_capture_consumed`. Migration 2 → 3 устанавливает `true` для старых
строк с `azimuth_deg != null` и `false` для строк с `azimuth_deg == null`. Ранее удалённую фиксацию
восстановить невозможно, поскольку до v3 этот факт не сохранялся.

# D061 — Territory и Observer являются отдельными сохранёнными сущностями

**Статус:** ACCEPTED

На одном устройстве может существовать несколько сохранённых Territory и
Observer. Territory имеет UUID, обязательные `code`, `name`, `region` и
`district`; Observer имеет UUID, обязательные `code`, `last_name` и
`first_name`, а также nullable `middle_name` и `contact`. Обязательные строки
trim-ятся и не могут быть пустыми. Оба code уникальны на устройстве, сохраняют
регистр и служат пользователю, но не являются technical identity или foreign
key.

`current_territory_id` и `current_observer_id` хранятся в DataStore как UUID
device-level selection. Новая запись может сразу становиться current. Invalid
saved ID не вызывает crash. При отсутствии active ObservationPoint карта всё
равно доступна; создание новой точки требует полного контекста согласно D062.
Active ObservationPoint всегда имеет приоритет recovery.

Новая ObservationPoint хранит обязательные `territory_id` и `observer_id`.
Переключение current selection не меняет уже созданные точки. ФИО, contact и
code Observer не snapshot-ятся в ObservationPoint без отдельной причины.

Будущее offline coverage принадлежит Territory через `Territory.id`; разные
Territory могут иметь разный device-local map context. Rectangle geometry,
tiles, package/download state и deduplication остаются map infrastructure, а
не Room research model. Эта связь не реализует persistence coverage и не
определяет download/storage алгоритм.

Migration 4 → 5 является единственным согласованным development-stage reset:
она очищает текущие test Territory/ObservationPoint/Bee/FlightCycle вместо
создания фиктивных ФИО, регионов или районов. Это не general destructive
migration policy: после этой точки будущие schema changes для реальных данных
должны быть non-destructive по умолчанию.

# D062 — Settings не блокирует карту при неполном контексте

**Статус:** ACCEPTED

Settings является обычным management screen, а не обязательным onboarding
барьером. При отсутствии current Observer или Territory приложение может
открыть карту, и пользователь может свободно войти в Settings, ознакомиться с

При неполном контексте операция не выполняется и показывает понятное сообщение

# D063 — PMTiles выбран форматом offline vector Map Package для Territory

**Статус:** ACCEPTED

**Заменяет:** D007

Основной offline vector Map Package Bee Search для Territory представляет собой
versioned PMTiles artifact, построенный из контролируемых OSM-derived данных
через Planetiler и совместимый Bee Search field profile. MapLibre Android читает
активированный package напрямую из app-controlled private storage; локальный
HTTP-сервер не является частью этой архитектуры.

Способ получения package не определяет его дальнейший lifecycle. Manual import,
future server download и другие разрешённые acquisition adapters должны
сходиться в одной последовательности:

```text
acquire
→ stage in app-controlled storage
→ validate compatibility and integrity
→ atomically activate
→ render through MapLibre
```

Отдельный copy step не является архитектурным инвариантом. Package считается
готовым для офлайн-работы только после полной проверки совместимости и
целостности и успешной атомарной активации. Внешний URI, cache hit, partially
staged artifact или сам факт начала acquisition не означают Offline Ready.

Каждый активированный Map Package должен иметь достаточно identity/version
metadata, чтобы Bee Search могла отличить установленный artifact от совместимой
замены. Конкретный manifest format этим решением не определяется.

Replacement выполняется безопасно: текущий активный package остаётся доступным,
пока новый artifact не прошёл validation и не был атомарно активирован. Ошибка
acquisition, staging или validation не удаляет и не повреждает рабочую карту.

Состояние установки, локальные пути и activation metadata являются
device-local map infrastructure и не хранятся в Room research schema.

Сохраняются следующие границы:

- base map не содержит редактируемые user/domain geodata;
- `Territory boundary` определяет рабочую область, а `map coverage` — один или
  несколько фрагментов желаемого или фактического offline coverage;
- map infrastructure не является `Territory`, `ObservationPoint`, `Bee` или
  `FlightCycle` и не входит в их Room-модель.

D063 заменяет OfflineRegion-specific механизм, readiness authority и delivery
assumptions D007, но сохраняет его общие требования explicit offline readiness,
device-local infrastructure и safe replacement.

Это решение не определяет конкретный server API, package manifest format,
downloader, update cadence или satellite imagery lifecycle.

# D064 — ObservationPoint появляется только с первым результатом наблюдения

**Статус:** ACCEPTED

**Supersedes:** только часть D035, относившуюся к сохранению точки при выборе
или подтверждении её координат.

Подтверждение координат на карте начинает transient-стадию «Подготовка точки».
Она хранит данные будущей `ObservationPoint`, включая current Territory,
current Observer, исходное GPS-измерение и подтверждённые координаты, но не
создаёт research record в Room.

До первого содержательного результата пользователь может явным действием
закрытия или Android system Back прекратить подготовку. Draft отбрасывается,
открывается карта текущей Territory, и в Room не создаются `ObservationPoint`,
`Bee` или `FlightCycle`. Для этого abort не показывается confirm dialog и не
создаётся отдельный persisted-статус.

Persistence boundary определяется первым содержательным результатом:

- первая добавленная Bee одной Room-транзакцией создаёт `ObservationPoint`,
  создаёт Bee и устанавливает `BEES_FOUND`;
- явное подтверждение «Пчёлы отсутствуют» одной Room-транзакцией создаёт
  `ObservationPoint`, устанавливает `NO_BEES_FOUND` и завершает точку.

Операция с первой Bee не может оставить сохранённую точку без этой Bee. После
успешной транзакции действует обычный persistent workflow; последующий выход
не удаляет фактические данные наблюдения.

`ABORTED PREPARATION` означает отсутствие начатого исследовательского
наблюдения и не является значением `bee_presence_result`. `NO_BEES_FOUND`
остаётся явным сохранённым отрицательным результатом проведённого наблюдения.

# D065 — Map Package contract v1 использует sidecar manifest

**Статус:** ACCEPTED

**Дополняет:** D063; формат map artifact остаётся PMTiles.

Каждый Map Package v1 состоит из immutable PMTiles artifact и отдельного
versioned JSON sidecar manifest, лежащего рядом с artifact при acquisition и
staging. Manifest называет archive только переносимым basename, а не
workstation path, external document URI или app-private installation path.
Так manual import и future server delivery используют один contract без
зависимости от PoC-specific paths.

Обязательные поля manifest v1:

- `schemaVersion` со значением `1`;
- стабильный versioned `packageId`;
- `territoryCompatibility` с policy `coverage_fragments_only`: package не
  содержит `Territory.id` и совместим с Territory через coverage, а не через
  identity;
- `datasetVersion`, `profileId`, `profileVersion` и `styleVersion`;
- непустой `coverageFragments` из отдельных geographic rectangles;
- целочисленные `minZoom` и `maxZoom`;
- basename `pmtilesFile`;
- положительный `pmtilesByteLength`;
- lower-case hexadecimal `pmtilesSha256` длиной 64 символа.

`coverageFragments` описывает фактическое заявленное coverage package и не
является `Territory boundary`, не заменяет desired coverage из DataStore и не
становится Room data. Один PMTiles header bbox недостаточен, чтобы описать
несколько fragments или доказать отсутствие пробелов между ними.

При staging приложение проверяет integrity: наличие названного artifact,
точный byte length, SHA-256 и читаемость поддерживаемого PMTiles header. Hash
обнаруживает повреждение относительно manifest, но сам по себе не доказывает
подлинность источника manifest; происхождение acquisition и возможная future
signature policy остаются отдельным решением.

Приложение проверяет compatibility: schema v1, допустимую пару
`profileId`/`profileVersion` и `styleVersion`, совпадение manifest zoom range с
PMTiles header, а также что header bbox включает каждый declared fragment.
Для v1 desired coverage считается покрытым только когда каждый его rectangle
целиком входит хотя бы в один `coverageFragments` package. Это намеренно
консервативнее вычисления объединения rectangles и не допускает назвать Ready
coverage с незакрытым промежутком.

Если desired coverage изменяется, приложение не меняет active package in place
и не удаляет его. Оно заново сравнивает desired fragments с manifest: package
остаётся Ready, только если все они покрыты; иначе старая карта остаётся
доступной для прежнего coverage, но новый desired coverage требует validated
replacement. `generatedAt`, source/licensing provenance, human description,
center, signature, server URL, download/retry state и quota не обязательны для
v1 и могут быть добавлены future schema version без изменения immutable
artifact.

# D066 — Локальная отмена последнего действия Bee в active observation

**Статус:** ACCEPTED

Для защиты от случайной регистрации полевого события active observation UI
показывает `↶ Отменить` только в карточке той Bee, чьё последнее обратимое
действие корректно определяется из её последнего `FlightCycle`. Это не global
undo, не unlimited history и не отдельная persisted undo-модель.

Последовательность обратимых действий выводится из current latest cycle:

- если текущий цикл закрыт, отменяется его последний `return_time`;
- если текущий открытый цикл содержит азимут, удаляется только `azimuth_deg`, а
  `azimuth_capture_consumed` остаётся `true`;
- если текущий открытый цикл имеет `sequence_number > 1` и азимута уже нет,
  удаляется только этот последний вновь созданный FlightCycle.

Поэтому `Улетела → Азимут → Undo → Undo` сначала удаляет азимут, а затем
удаляет созданный повторный цикл и возвращает Bee к предыдущему `return_time`.
Исходные timestamps не переписываются: после отмены `Прилетела` снова
используется исходный `departure_time`, после отмены `Улетела` — исходный
`return_time` предыдущего цикла. Специальное исключение для ошибочно
приписанного initial group launch определено последующим D067.

Каждая отмена выполняется одной Room-транзакцией и изменяет только данные
конкретной Bee. Если позднейшее действие уже делает correction неоднозначной,
local Undo не предлагается. После успешной correction UI перечитывает Room и
пересортировывает Bee по обычным derived данным.

# D067 — Correction ошибочно приписанного первого группового вылета

**Статус:** SUPERSEDED (D075)

**Примечание:** особый случай, который описывало это решение, больше не
существует: первый вылет каждой Bee регистрируется отдельно и уже имеет её
собственный `departure_time`, поэтому отдельная correction ошибочно
приписанного группового вылета не нужна. Общая возможность локальной отмены
первого вылета определена D066 и D075. Текст ниже сохранён как история.

Это решение supersedes только прежний безусловный запрет D066 на удаление
первого группового FlightCycle.

После атомарного `Выпустить всех` отдельная Bee может фактически не улететь.
Пока её автоматически созданный первый FlightCycle остаётся открытым, создан
именно групповой транзакцией и для него ещё ни разу не был записан `return_time`,
локальная `↶` этой Bee может удалить только этот цикл. Это одна Room transaction;
остальные Bee и их FlightCycle не меняются.

После correction Bee остаётся на точке без FlightCycle и без фиктивного
`return_time`. Когда она действительно улетает, `Улетела` создаёт новый
индивидуальный `FlightCycle sequence_number = 1` с фактическим временем.

Происхождение initial group launch и его ограниченная eligibility хранятся как
минимальная persisted provenance, а не как generic undo stack: групповой
timestamp принадлежит ObservationPoint, а цикл помечается как созданный
групповым выпуском. Запись `return_time` необратимо закрывает eligibility этой
особой correction; последующее обычное Undo прилёта не позволяет удалить
исторический первый цикл. Следующий цикл также исключает такое удаление.

# D068 — Signing rotation migration policy

**Статус:** ACCEPTED

Текущий stable signer — signer A: существующий debug key (`CN=Android Debug`,
RSA 2048). Будущая production-подпись использует отдельный signer B.

Разрешён прямой переход `v2-only A → v3 B` с SigningCertificateLineage `A → B`.
Криптографический transitional APK (промежуточный релиз, подписанный A по схеме
v3 с lineage) не требуется как обязательный этап.

Complete backup является обязательным operational safety gate перед реальной
ротацией: пока существуют уникальные полевые данные, ротация подписи не
выполняется без проверенного backup и проверенного restore path (D069–D071).

Перед реальной ротацией обязателен signing spike на реальном устройстве:
проверяются установка `v3 B` с lineage поверх установленного `v2-only A`,
сохранение данных приложения и поведение платформы на используемых API.

`rotation-min-sdk-version = 28` является текущей рекомендуемой стратегией.
Практическая совместимость этой стратегии должна быть подтверждена
device/API-проверкой до релиза 1.2.0; при неподтверждённой совместимости релиз
не выполняется.

Открытыми и не решёнными этим решением остаются: владение и хранение
production keystore, порядок вывода signer A из обращения, точная device/API
матрица проверки и необходимость v3.1-специфичных настроек.

# D069 — Logical backup archive

**Статус:** ACCEPTED

Канонический backup Bee Search — versioned logical archive. Архив формируется
приложением из логических данных и содержит собственные version/identity

Конкретный container format архива и его версионирование определяются при
реализации exporter/importer; этот выбор не изменяет statuses и ownership
данных.

# D070 — Safe restore boundary

**Статус:** ACCEPTED

Восстановление из backup выполняется по безопасной границе:

- полная validation архива до любой записи в research storage;
- сохранение UUID и FK-связей research graph, без переназначения identity;
- одна Room transaction для research graph;
- staging для файлов (attachments): файлы попадают в рабочее хранилище только
  после успешной проверки;
- первая версия importer работает только с пустой research DB;
- no silent overwrite/merge: при непустой research DB восстановление не
  выполняется молча и не смешивается с существующими данными.

Merge, частичный import и восстановление поверх непустой базы не входят в эту
границу и требуют отдельного решения.

# D071 — Backup data classification

**Статус:** ACCEPTED

Данные для backup разделяются по классам:

- уникальные research data обязательны в backup: Observer, Territory,
  ObservationPoint, Bee, FlightCycle и связанные research facts;
- settings отделены от research facts: device-local настройки не являются
  исследовательскими данными и не восстанавливаются как research graph;
- Complete backup включает уникальные attachments (например, изображения
  осмотров), если они существуют;
- повторно импортируемые map packages исключены из backup: offline PMTiles
  Map Packages являются device-local infrastructure по D063/D065 и
  восстанавливаются повторным импортом, а не из архива.

# D072 — Attachment storage boundary

**Статус:** ACCEPTED

Attachments (будущие изображения и подобные артефакты осмотров) разделяют
metadata и bytes:

- metadata хранится в Room (identity, owner-ссылка, имя, размер, SHA-256,
  timestamps);
- bytes хранятся в app-controlled file storage, а не в Room;
- integrity проверяется по size и SHA-256;
- удаление выполняется guarded: удаление записи и удаление bytes не создают
  молчаливых orphan-файлов, orphan cleanup является отдельной безопасной
  операцией.

Точная owner/link schema attachments (какая сущность является владельцем и как
выражается связь) пока **OPEN** и не фиксируется этим решением. Новые сущности
только ради будущих attachments не создаются.

# D073 — Durable object/history boundary

**Статус:** ACCEPTED

Разделяются уровни смысла:

- `ObservationPoint` остаётся событием наблюдения, а не долговечным объектом;
- будущий `FieldObject` является долговечным объектом (например, место,
  которое существует независимо от конкретного наблюдения);
- `Inspection` является отдельной историей осмотров такого объекта;
- current state не заменяет историю: актуальное состояние не отменяет и не
  переписывает предыдущие осмотры.

Конкретная Room schema для `FieldObject`, `Hollow`, `Trap` и их связей пока
**OPEN**. Сущности и поля не вводятся заранее, до появления реализуемого
сценария; этот документ фиксирует только границу смысла, а не схему.

# D074 — Research external technology before implementation

**Статус:** ACCEPTED

Перед проектированием или реализацией изменения, зависящего от внешней
технологии, framework, библиотеки, инструмента, платформы, API, plugin system или

2. официальный upstream repository и относящийся к делу исходный код;
3. release notes и документация той версии, которая фактически используется;
4. существующие официальные или устоявшиеся plugins, extensions, workflows и
   reference implementations.

Community-обсуждения и сторонние реализации используются как вторичное
свидетельство, когда первичных источников недостаточно.

Проект не создаёт собственный механизм только потому, что существующая
возможность не была известна в начале задачи.

Документированное поведение, поведение, выведенное из исходного кода,
наблюдаемое в runtime и предполагаемое, должны оставаться различимыми.

Для изменений, не зависящих от внешней технологии или экосистемы, этот
research gate может быть отмечен как `not applicable`.

Исполняемая часть правила зафиксирована в `AGENTS.md` и
`.agent/decision-policy.yaml` (`research_before_implementation`,

# D075 — Индивидуальный первый вылет вместо первого группового выпуска

**Статус:** ACCEPTED

**Supersedes:** D058 целиком; D067 целиком; часть D064 о persistence boundary
первого результата наблюдения и о невозможности сохранённой точки без Bee.

**Дополняет:** D016, D057 (лимит Bee на точке), D066 (локальная отмена).

## Открытие наблюдения

Подтверждение подготовленной точки действием `Добавить` одной Room-транзакцией
создаёт `ObservationPoint` с `bee_presence_result = null` и открывает рабочий
экран «Наблюдение». Реальные Bee при этом не создаются ни в Room, ни в UI:
заранее подготовленный список Bee больше не является частью workflow.

Отмена draft до `Добавить` по-прежнему отбрасывает только draft и не создаёт
`ObservationPoint`, `Bee` или `FlightCycle`.

Сохранённая точка может существовать без Bee и без `bee_presence_result`, пока
наблюдение не завершено явным результатом. Это осознанное изменение границы
D064: точка становится research record в момент подтверждения координат, а
не в момент первого вылета.

## Варианты метки

Экран наблюдения выводит доступные варианты метки как производное значение:
5 цветов × `NONE` / `RIGHT_WING` / `LEFT_WING`, то есть 15 вариантов, минус метки
уже существующих реальных Bee. Вариант не является Bee, не хранится отдельной
сущностью и не расходует лимит Bee.

`NONE` остаётся внутренним значением и показывается пользователю как `Грудь`.
Карточка варианта имеет серый фон, состояние `Выбор` и действие `УЛЕТЕЛА`.

## Первый вылет

`УЛЕТЕЛА` для выбранного варианта одной Room-транзакцией:

- создаёт реальную `Bee` с выбранной меткой;
- создаёт её `FlightCycle sequence_number = 1` с индивидуальным
  `departure_time` именно этой Bee;
- устанавливает `bee_presence_result = BEES_FOUND`, если он ещё не установлен.

Карточка реальной Bee сразу занимает место выше вариантов и показывается как
существующая Bee с обычным derived field state и таймером. Использованная метка
перестаёт предлагаться как вариант. Второй и последующие вылеты создаются
обычным действием следующего вылета, как и раньше.

Одна ObservationPoint содержит не более 10 реальных Bee. Достигнутый лимит
делает оставшиеся варианты недоступными, но не удаляет их; варианты лимит не
расходуют.

## Локальная отмена первого вылета

Если первый вылет был зарегистрирован ошибочно и для его цикла ещё ни разу не
записывался `return_time`, локальная `↶` этой Bee одной Room-транзакцией удаляет
и `FlightCycle 1`, и саму `Bee`; метка снова становится доступным вариантом,
а `bee_presence_result` возвращается к `null`, если на точке не осталось ни
одной Bee. Остальные Bee и их FlightCycle не меняются.

После подтверждённой регистрации прилёта удаление Bee через эту correction
невозможно; последующая отмена прилёта эту возможность не возобновляет.
Запрет выражен persisted eligibility текущего первого цикла, а не вычисляется из
одного `sequence_number`.

## Пригодность для анализа

`FlightCycle sequence_number = 1` не имеет автоматического исключения из
расчётов по продолжительности полёта: короткий первый цикл проходит тот же путь
пригодности, что и остальные. Отдельный persisted `is_valid` по-прежнему не
вводится.

## Отрицательный результат

`NO_BEES_FOUND` сохраняется как явный сохранённый отрицательный результат
проведённого наблюдения. Он может быть записан либо из draft до `Добавить`, либо
на открытом наблюдении, пока на точке нет ни одной Bee; запись результата
завершает точку.

## Persistence

Схема Room не изменяется. Столбец `initial_group_launch_correction_eligible`
сохраняет своё имя и тип, а его смысл сужается до «первый вылет этой Bee ещё
можно отменить»; `is_initial_group_launch` остаётся только как legacy
provenance восстановленных backup-записей. Backup contract и формат экспорта
также не изменяются.

# D077 — Карта разделяет создание записей и просмотр объектов

**Статус:** ACCEPTED

**Уточняет:** D054, D064, D075 и D076 только в части navigation/placement flow.

Геометрический центр основной карты с красным прицелом является координатой
будущей записи. Пользователь сначала получает GPS-позицию и при необходимости

# D079 — Редактор участка офлайн-карты сохраняет только по «Готово» и не теряет изменения молча

**Статус:** ACCEPTED

**Уточняет:** D063 и D065 только в части coverage-editing UX. Формат Map Package,
D065 manifest contract и PMTiles build pipeline не меняются.

Редактор участка офлайн-карты держит draft (working copy) отдельно от сохранённого
coverage. `Готово` — единственное явное завершение редактирования и означает
«сохранить выбранные участки и выйти из режима». Обычного действия `Выйти`, которое
отбрасывает несохранённые изменения, в редакторе нет: молчаливый выход с потерей
выбранного участка запрещён. Основание — полевой случай, когда созданный участок
был потерян обычным выходом из редактора, а воспроизвести ту же область вручную
оказалось трудно.

Открытие редактора не является изменением: draft инициализируется сохранённым
coverage, и dirty-state возникает только тогда, когда draft отличается от последнего
сохранённого набора (добавлен участок, отменён последний, очищен набор). После
успешного `Готово` dirty-state исчезает.

Системный `Back` при наличии несохранённых изменений требует явного решения
пользователя: `Сохранить`, `Выйти без сохранения` или `Остаться`. `Сохранить`
записывает draft и выходит, `Выйти без сохранения` восстанавливает сохранённый
coverage и выходит, `Остаться` продолжает редактирование с текущим draft.
Формулировки `Да`/`Нет` не используются. Без несохранённых изменений `Back` закрывает
редактор без диалога.

Действия редактора называются однозначно: `Отменить последний` убирает только
последний добавленный участок, `Очистить всё` очищает весь draft и требует
подтверждения. До `Готово` оба действия затрагивают только working copy, поэтому
`Выйти без сохранения` после очистки возвращает прежнее сохранённое состояние, а не
уничтожает его. Семантика undo не меняется.

Действие `Копировать bbox` доступно во всех сборках приложения, а не только в
отладочной: без него пользователь не может передать точные координаты выбранной
области для подготовки карты. Оно по-прежнему доступно только при ровно одном
добавленном участке.

Встроенная помощь содержит отдельные разделы `Создание участка офлайн-карты` и
`Загрузка офлайн-карты`, описывающие фактический интерфейс, включая `Готово`,
поведение `Back` и отказ импорта по неполному покрытию.

Room, ObservationPoint, Bee, backup, Map Package format, importer и MapLibre
rendering не меняются.

# D080 — Пользовательский обмен файлами идёт через один каталог обмена, разделённый по вариантам

**Статус:** ACCEPTED

Пользовательский обмен файлами имеет один короткий предсказуемый каталог:
`Download/BeeSearch/<вариант>/Exchange/` с подкаталогами `Areas`, `OfflineMaps` и
`Data`. `OfflineMaps` содержит пары офлайн-карт (`*.pmtiles` и
`*.pmtiles.manifest.json`), `Data` — экспортированные данные и файлы для
последующего импорта/восстановления, `Areas` зарезервирован под файлы участков,
формат которых определяется отдельной задачей. Отдельные `Import`/`Export` внутри
`Data` не вводятся: один и тот же файл может быть сначала экспортирован, а позже
импортирован обратно.

Вариант приложения определяется build configuration (`BuildConfig.EXCHANGE_VARIANT`),
а не разбором package name. Stable, Beta и Dev работают каждый только со своей
веткой каталога, поэтому сборки не смешивают файлы, и пользователь не выбирает
вариант вручную. Каталоги создаются идемпотентно при первом обращении: существующие
каталоги переиспользуются, ничего не удаляется, не переименовывается и не
дублируется.

**Каталог обмена — пользовательский контракт для переноса файлов, а не canonical
storage приложения.** Room DB, DataStore, кэш, установленная копия PMTiles и
map-package runtime state остаются в app-owned storage. Импорт по-прежнему копирует
пакет в app-owned storage, поэтому удаление пользователем файла из каталога обмена
не повреждает уже импортированную карту и не затрагивает данные наблюдений.

Scoped Storage не позволяет создать `BeeSearch` в корне общего хранилища. Широкие
разрешения на файловую систему, включая `MANAGE_EXTERNAL_STORAGE`, не запрашиваются;
выбран ближайший стандартный пользовательский путь `Download/BeeSearch/...`,
согласованный с существующей доставкой map package на устройство. Каталог обмена
передаётся системному picker как `DocumentsContract.EXTRA_INITIAL_URI`; выбор файла
и имени всегда подтверждает пользователь. Если система не открывает picker сразу в
каталоге обмена, приложение показывает точный путь текстом, а не расширяет
разрешения.

Формат backup-архива и его версия не меняются: новым каталогом меняется только
пользовательское место обмена. Map-package contract, D065 manifest, PMTiles build
pipeline, Room, ObservationPoint, Bee и MapLibre rendering не меняются.

# D081 — У Territory есть 0..1 именованный Ареал, хранимый device-local в versioned map-coverage записи

**Статус:** ACCEPTED

**Дополняет:** D063 и D065 в части device-local покрытия. Формат Map Package, D065
manifest, PMTiles build pipeline и Room не меняются.

У каждой Territory существует **не более одного** Ареала. Ареал — вся именованная
область территории, а «участок» — один прямоугольник внутри неё. В одной Territory не
бывает нескольких Ареалов, поэтому нет ни коллекции Ареалов, ни `currentAreaId`, ни
`selectedAreaId`: принадлежность задаётся ключом хранения по `Territory.id`, а текущая
Territory однозначно определяет текущий Ареал.

Ареал содержит стабильный `id` (UUID), изменяемое человекочитаемое `name` и **1..N
bounds** — участков. Имя не является техническим идентификатором: переименование не
меняет `id` и не создаёт новый Ареал. Ареал с нулём участков не существует.

Ареал хранится **device-local** в существующей записи `map_coverage_<territoryId>`
Preferences DataStore как versioned значение: `v1|…` — прежний безымянный набор
участков, `v2|{"areaId":…,"name":…,"bounds":[…]}` — Ареал. Отдельного canonical
хранилища не создаётся, Room для Ареала не используется. Принадлежность Ареала к
одной Territory выражается ключом, а не дублирующим полем.

Существующий непустой `v1` мигрирует в `v2` при первом чтении: одной транзакцией
DataStore, один раз, с новым устойчивым UUID и начальным именем, взятым из
человекочитаемого названия Territory, иначе — `Ареал`. Геометрия переносится без
изменений: координаты не округляются повторно, не нормализуются, не объединяются, не
сортируются и не теряют перекрытия. Пустой legacy-набор означает отсутствие Ареала, а
не Ареал без участков.

Чтение различает три состояния: Ареала нет, Ареал прочитан, сохранённое значение
повреждено. Повреждённое значение **не** считается отсутствием Ареала, **не**
заменяется пустым и **не** перезаписывается миграцией или сохранением: оно сообщается
явной ошибкой, а сохранение отклоняется.

Ареал входит в основной backup через существующую settings-секцию `map-coverage`: её
строки `{territoryId, encoded}` переносят значение `v2` без изменения
`backupFormatVersion`, `archiveSchemaVersion` и `roomSchemaVersion`. Валидатор
backup проверяет `v2` структурно, а не по префиксу, поэтому повреждённое значение
даёт явную контролируемую ошибку экспорта и не удаляется из DataStore. Корректный
`v1` остаётся принимаемым, поэтому старые архивы восстанавливаются и мигрируют при
первом чтении. Указатель активного Map Package по-прежнему в backup не входит.

Совместимость с Map Package остаётся **coverage-based**: `areaId` в manifest не
добавляется, жёсткой identity-связи Ареал↔package нет, а участки Ареала служат desired
coverage для существующего правила containment D065.

В это решение **не** входят и остаются отдельными задачами: диалог названия при первом
создании, пользовательский экран Ареала, JSON-обмен Ареала через Exchange, общая площадь
объединения участков, восстановление Ареала из manifest и multi-section генератор карт.

# Итог

На текущем этапе архитектурное ядро Bee Search выглядит следующим образом:

`Android + Kotlin + Compose`

`MapLibre + offline maps`

`GPS + ручная корректировка`

`Android sensors + необязательный азимут`

`Room / SQLite + offline-first`

`Territory → ObservationPoint → Bee → FlightCycle`

`DataStore → current_observer_id? + current_territory_id?`

`timestamps → Instant / Unix epoch milliseconds`

`MapLibre → online source or activated local PMTiles Map Package`

`field vector source → Bee_search OSM profile + versioned PMTiles/MVT`

`vector zoom → source/offline z15 + UI overscaling to z20`

`offline package metadata → device-local installation/activation metadata`

`локальное сохранение сейчас → серверная синхронизация позже`

Основной приоритет разработки:

> сначала создать надёжный и быстрый инструмент полевой регистрации, проверить его в реальной работе и только затем добавлять сервер, аналитику и дополнительные уровни сложности.

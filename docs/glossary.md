# Bee Search — Glossary

## 1. Назначение

Этот документ определяет основные термины проекта **Bee Search** и их однозначное значение.

Глоссарий используется:

- в проектной документации;
- при обсуждении требований;
- в исходном коде;
- при именовании сущностей, классов и полей;
- при работе Codex и других агентов с проектом.

Цель документа — не допускать появления нескольких названий для одного понятия и различного толкования одного термина.

Если термин имеет русское пользовательское название и английское техническое название, фиксируются оба.

---

# 2. Общие правила терминологии

## 2.1. Язык интерфейса и язык кода

Пользовательский интерфейс и рабочее обсуждение могут использовать русские термины.

В исходном коде используются английские технические названия.

Пример:

`Точка наблюдения → ObservationPoint`

Не следует создавать разные технические названия одного понятия без необходимости.

---

## 2.2. Предметные и технические термины

Следует различать:

**предметные понятия**

- территория;
- точка наблюдения;
- пчела;
- метка;
- вылет;
- возвращение;
- азимут;

и **технические понятия**

- Room;
- Repository;
- ViewModel;
- DataStore;
- MapLibre.

Технические термины не должны подменять предметные сущности.

---

# 3. Bee Search

**Русский:** Bee Search / приложение поиска пчёл  
**Техническое имя:** `Bee Search`

Мобильное приложение для регистрации полевых наблюдений за мечеными пчёлами.

Основная задача первой версии — надёжная регистрация исходных наблюдений, а не автоматическое определение местоположения гнезда.

---

# 4. Territory

**Русский:** территория  
**Техническое имя:** `Territory`

Долговременная область исследования, внутри которой проводятся наблюдения.

Territory объединяет множество ObservationPoint.

Пример:

`Клязьминская пойма`

Территория имеет собственные:

- `id`;
- `code`;
- `name`.

Территория не является отдельным полевым наблюдением.

---

# 5. Territory Code

**Русский:** код территории  
**Техническое имя:** `Territory.code`

Короткое устойчивое человекочитаемое обозначение территории.

Пример:

`KLYAZMA-01`

Не является первичным идентификатором базы данных.

---

# 6. Current Territory

**Русский:** текущая территория  
**Техническое имя:** `current_territory_id`

Territory, выбранная для текущей работы приложения.

После выбора территория используется по умолчанию при следующих запусках, пока пользователь явно не выберет другую.

Текущая территория является настройкой устройства, а не свойством самой Territory.

Не используется термин или поле:

`Territory.is_current`

---

# 7. Offline Map

**Русский:** офлайн-карта

Локально сохранённые картографические данные, позволяющие работать с картой Territory без подключения к интернету.

Offline Map является техническим ресурсом, а не самостоятельной предметной сущностью базы наблюдений.

Состояние загрузки и другие метаданные Offline Map локальны для конкретного устройства и не являются полями `Territory` в первой Room-схеме.

Конкретный формат офлайн-карт определяется отдельно.

---

# 8. Observation Point

**Русский:** точка наблюдения  
**Техническое имя:** `ObservationPoint`

Одно конкретное полевое наблюдение, выполняемое в определённом месте и в определённый период времени.

ObservationPoint содержит:

- координаты;
- код наблюдателя;
- время начала;
- время завершения;
- набор Bee;
- связанные с ними FlightCycle.

Важно:

`ObservationPoint` означает не просто географическое место.

Повторная работа через несколько дней в том же месте создаёт новую ObservationPoint.

---

# 9. Point

**Русский:** точка

Допустимое сокращение от `ObservationPoint` в пользовательском интерфейсе и разговорном обсуждении.

В технической документации и коде предпочтительно использовать полное название `ObservationPoint`, если сокращение может вызвать неоднозначность.

---

# 10. Coordinates

**Русский:** координаты

Подтверждённое географическое положение ObservationPoint.

Основные поля:

`latitude`

`longitude`

Координаты принадлежат ObservationPoint.

Bee и FlightCycle собственных координат не имеют.

---

# 11. GPS Position

**Русский:** GPS-позиция / исходная GPS-позиция

Положение, первоначально полученное от системы позиционирования телефона.

Может включать:

`gps_latitude`

`gps_longitude`

`gps_accuracy_m`

GPS Position не обязательно совпадает с итоговыми Coordinates ObservationPoint.

---

# 12. Manual Position Correction

**Русский:** ручная корректировка точки

Изменение пользователем предлагаемого GPS-положения непосредственно на карте перед подтверждением ObservationPoint.

После корректировки итоговые:

`latitude / longitude`

могут отличаться от:

`gps_latitude / gps_longitude`.

---

# 13. Observer Code

**Русский:** код наблюдателя  
**Техническое имя:** `observer_code`

Короткое обозначение человека, выполняющего наблюдение.

В MVP отдельная сущность `Observer` отсутствует.

Текущий `observer_code` хранится в настройках устройства.

На чистой установке он отсутствует и не заменяется фиктивным значением. Перед созданием первой ObservationPoint пользователь должен явно задать непустой код.

При создании ObservationPoint значение копируется в неё и становится частью исторических данных.

---

# 14. Bee

**Русский:** пчела  
**Техническое имя:** `Bee`

Конкретная меченая пчела, участвующая в одном ObservationPoint.

Bee идентифицируется внутри полевой работы прежде всего по своей метке.

Bee принадлежит ровно одной ObservationPoint.

---

# 15. Mark

**Русский:** метка

Визуальное обозначение, используемое для различения наблюдаемых Bee.

В текущей модели метка определяется сочетанием:

`mark_color + mark_position`

Например:

- Белая;
- Белая КП;
- Белая КЛ;
- Синяя;
- Синяя КП;
- Синяя КЛ.

---

# 16. Mark Color

**Русский:** цвет метки  
**Техническое имя:** `mark_color`

Цвет визуальной метки Bee.

Текущий каталог MVP:

`WHITE`

`YELLOW`

`BLUE`

`RED`

`GREEN`

Набор цветов должен иметь возможность расширяться.

---

# 17. Mark Position

**Русский:** положение метки  
**Техническое имя:** `mark_position`

Дополнительный признак расположения метки.

Значения:

`NONE`

`RIGHT_WING`

`LEFT_WING`

---

# 18. КП

**Русский:** КП  
**Техническое значение:** `RIGHT_WING`

Сокращение:

`крыло правое`

Пример:

`Белая КП`

означает белую метку с дополнительным обозначением на правом крыле.

---

# 19. КЛ

**Русский:** КЛ  
**Техническое значение:** `LEFT_WING`

Сокращение:

`крыло левое`

Пример:

`Белая КЛ`

означает белую метку с дополнительным обозначением на левом крыле.

---

# 20. Prepared Bee

**Русский:** подготовленная пчела

Bee, добавленная в текущую ObservationPoint, но ещё не имеющая FlightCycle.

То есть:

`FlightCycle count = 0`

Такая Bee ожидает первого группового выпуска.

Отдельное поле состояния для этого не хранится.

---

# 21. Flight Cycle

**Русский:** цикл полёта / цикл вылета  
**Техническое имя:** `FlightCycle`

Один цикл наблюдения конкретной Bee:

`вылет → возможное возвращение`

FlightCycle содержит:

- порядковый номер;
- время вылета;
- возможное время возвращения;
- возможный азимут.

Одна Bee может иметь несколько FlightCycle.

---

# 22. Sequence Number

**Русский:** номер цикла  
**Техническое имя:** `sequence_number`

Порядковый номер FlightCycle конкретной Bee.

Значения:

`1, 2, 3, ...`

Нумерация начинается с 1.

---

# 23. Initial Group Release

**Русский:** первый групповой выпуск / групповой старт

Одновременный первый выпуск всех подготовленных Bee.

В интерфейсе может соответствовать действию:

`ВЫПУСТИТЬ ВСЕХ`

Для всех участвующих Bee создаётся FlightCycle:

`sequence_number = 1`

с одинаковым `departure_time`.

Отдельная сущность `GroupRelease` не существует.

---

# 24. Departure

**Русский:** вылет / улетела  
**Техническое поле:** `departure_time`

Момент, когда Bee начала соответствующий FlightCycle.

Для первого цикла время определяется общим групповым стартом.

Для последующих циклов регистрируется индивидуально.

---

# 25. Departure Time

**Русский:** время вылета  
**Техническое имя:** `departure_time`

Timestamp начала FlightCycle.

Является обязательным.

---

# 26. Return

**Русский:** возвращение / вернулась

Наблюдаемое возвращение Bee после вылета.

Регистрация возвращения завершает текущий открытый FlightCycle.

---

# 27. Return Time

**Русский:** время возвращения  
**Техническое имя:** `return_time`

Timestamp зарегистрированного возвращения Bee.

Поле необязательно.

`return_time = null`

может означать:

- Bee ещё находится в полёте;
- Bee не вернулась до завершения ObservationPoint.

---

# 28. Open Flight Cycle

**Русский:** открытый цикл / пчела в полёте

FlightCycle, для которого:

`departure_time != null`

и:

`return_time = null`.

У одной Bee одновременно может существовать не более одного открытого FlightCycle.

---

# 29. Closed Flight Cycle

**Русский:** завершённый цикл

FlightCycle, имеющий:

`departure_time`

и:

`return_time`.

После завершения цикла Bee может быть зарегистрирована в новом FlightCycle.

---

# 30. Flight Duration

**Русский:** продолжительность полёта / время отсутствия

Вычисляемая продолжительность между вылетом и возвращением.

Для завершённого FlightCycle:

`return_time - departure_time`

Для открытого FlightCycle:

`current_time - departure_time`

Отдельно в базе не хранится.

---

# 31. Azimuth

**Русский:** азимут  
**Техническое имя:** `azimuth_deg`

Наблюдаемое направление ухода Bee при конкретном FlightCycle.

Измеряется в градусах:

`0 <= azimuth_deg < 360`

где:

`0° = север`

Азимут является необязательным.

---

# 32. Missing Azimuth

**Русский:** азимут не определён

Представляется:

`azimuth_deg = null`

Это нормальное состояние данных.

Если направление невозможно определить надёжно, его следует оставить отсутствующим.

---

# 33. Unreliable Azimuth

**Русский:** сомнительный / ненадёжный азимут

Азимут, которому наблюдатель не доверяет.

Такое значение допускается удалить:

`azimuth_deg → null`

Ненадёжное измерение не должно сохраняться только ради наличия данных.

---

# 34. Heading

**Русский:** направление телефона / показание компаса  
**Технический термин:** `Heading`

Текущее направление, полученное от датчиков телефона.

Heading является техническим измерением.

После действия пользователя его значение может быть сохранено как `FlightCycle.azimuth_deg`.

`Heading` и `Azimuth` поэтому не являются полностью взаимозаменяемыми понятиями.

---

# 35. Heading Provider

**Техническое имя:** `HeadingProvider`

Компонент приложения, получающий данные ориентации телефона через Android Sensor APIs.

Не является предметной сущностью.

---

# 36. Location Provider

**Техническое имя:** `LocationProvider`

Компонент приложения, отвечающий за получение текущего положения устройства.

Может предоставлять:

- latitude;
- longitude;
- accuracy;
- timestamp.

Не является предметной сущностью.

---

# 37. Active Observation Point

**Русский:** активная точка / текущее наблюдение

ObservationPoint, для которой:

`completed_at = null`

В MVP на одном устройстве предполагается не более одной активной ObservationPoint.

---

# 38. Completed Observation Point

**Русский:** завершённая точка / завершённое наблюдение

ObservationPoint, имеющая:

`completed_at != null`

Новая полноценная работа в том же месте через несколько дней создаёт новую ObservationPoint.

---

# 39. Repeated Observation

**Русский:** повторное наблюдение

Новое ObservationPoint, созданное в месте, где наблюдение уже проводилось ранее.

Координаты нового и старого ObservationPoint могут совпадать.

Повторное наблюдение не является продолжением старой ObservationPoint.

---

# 40. Physical Place

**Русский:** физическое место

Концептуальное географическое место, в котором потенциально могут проводиться повторные ObservationPoint.

В текущей модели отдельной сущности `PhysicalPlace` нет.

Термин может использоваться при обсуждении, но не должен автоматически превращаться в новую таблицу или класс предметной модели.

---

# 41. Observation Session

**Русский:** сессия наблюдения

Термин, который не используется как самостоятельная сущность текущей модели.

Функцию предполагаемой сессии выполняет сама активная `ObservationPoint`.

Не следует создавать `ObservationSession` без изменения требований.

---

# 42. Group Release

**Русский:** групповой выпуск

Понятие пользовательского процесса первого выпуска Bee.

Отдельной сущности `GroupRelease` в модели нет.

Представляется набором первых FlightCycle с:

`sequence_number = 1`

и общим `departure_time`.

---

# 43. Bee State

**Русский:** состояние пчелы

Вычисляемое состояние Bee.

Примеры пользовательских состояний:

- подготовлена;
- в полёте;
- вернулась;
- не вернулась к завершению наблюдения.

Отдельное поле `Bee.status` не хранится.

---

# 44. Offline-first

Архитектурный принцип, согласно которому основные функции Bee Search работают без соединения с сервером.

Сначала данные записываются локально.

Сеть и будущая синхронизация не участвуют в критическом процессе регистрации полевого события.

---

# 45. Local Database

**Русский:** локальная база

Основное постоянное хранилище исследовательских данных на Android-устройстве.

Технология:

`Room / SQLite`

Содержит:

`Territory → ObservationPoint → Bee → FlightCycle`

---

# 46. Room

Android-библиотека доступа к SQLite, используемая для локального хранения структурированных исследовательских данных.

Room является техническим компонентом и не относится к предметной модели.

---

# 47. DataStore

Android-механизм хранения небольших локальных настроек.

В частности:

`current_territory_id`

`observer_code`

DataStore не используется вместо Room для истории наблюдений.

Оба ключа могут отсутствовать на чистой установке.

---

# 48. MapLibre

**Техническое имя:** `MapLibre Native for Android`

Открытый картографический движок, используемый Bee Search для отображения карты.

MapLibre не следует путать с источником картографических данных.

---

# 49. Map Source

**Русский:** источник карты

Источник географических данных, которые отображает MapLibre.

Картографический движок и Map Source являются разными компонентами.

Конкретный источник для Bee Search пока не зафиксирован.

---

# 50. Map Style

**Русский:** стиль карты

Описание визуального представления картографических данных:

- дороги;
- леса;
- водоёмы;
- подписи;
- другие слои.

Стиль не является исследовательскими данными Bee Search.

---

# 51. Map Region

**Русский:** область карты / область офлайн-карты

Географическая область, для которой подготавливаются офлайн-картографические данные Territory.

Это локальная техническая информация устройства. В первой Room-схеме она не моделируется; точный способ представления будет определён вместе с механизмом офлайн-карт.

---

# 52. Repository

Технический слой приложения, предоставляющий предметным операциям доступ к данным и скрывающий детали конкретного хранилища.

Repository не является предметной сущностью.

---

# 53. DAO

**Data Access Object**

Технический компонент Room для выполнения операций с SQLite.

DAO не должен содержать пользовательские сценарии или UI-логику.

---

# 54. ViewModel

Android-компонент Presentation layer.

Отвечает за:

- состояние UI;
- обработку UI events;
- вызов предметных операций;
- получение данных.

ViewModel не является местом постоянного хранения исследовательских данных.

---

# 55. UI State

Текущее представление данных, необходимое конкретному экрану.

UI State может содержать вычисляемые значения, например:

`Bee находится в полёте`

или:

`продолжительность 06:42`.

UI State не является самостоятельной записью исследовательской базы.

---

# 56. UUID

Устойчивый уникальный идентификатор записи.

Используется для:

- Territory;
- ObservationPoint;
- Bee;
- FlightCycle.

UUID создаётся непосредственно на устройстве.

Человек обычно не должен видеть UUID в рабочем интерфейсе.

---

# 57. Timestamp

Однозначное машинное представление абсолютного момента времени.

В Kotlin используется `Instant`, в SQLite — Unix epoch milliseconds.

Используется для регистрации:

- создания данных;
- вылета;
- возвращения;
- завершения наблюдения.

Пользовательское отображение времени может отличаться от внутреннего формата хранения.

Часовой пояс отдельно не сохраняется; для отображения используется текущий часовой пояс устройства.

---

# 58. MVP

**Minimum Viable Product**

Первая практически пригодная версия Bee Search.

Для этого проекта MVP означает прежде всего возможность провести реальное полевое наблюдение:

`выбрать Territory`

→ `работать с офлайн-картой`

→ `создать ObservationPoint`

→ `подготовить Bee`

→ `выпустить их`

→ `независимо регистрировать возвращения`

→ `регистрировать следующие циклы`

→ `при возможности фиксировать азимут`

→ `завершить ObservationPoint`

→ `не потерять данные`.

MVP не требует наличия сервера, web-интерфейса или автоматического определения гнезда.

---

# 59. Sync

**Русский:** синхронизация

Будущий механизм обмена данными между мобильным устройством и сервером.

Синхронизация не входит в первый MVP.

Даже после её появления Bee Search должен сохранять offline-first поведение.

---

# 60. Sync Engine

**Техническое имя:** `SyncEngine`

Будущий технический компонент, отвечающий за обмен локальными и серверными данными.

В текущей версии не реализуется.

---

# 61. Server

**Русский:** сервер

Будущая инфраструктура для:

- объединения данных разных устройств;
- синхронизации;
- долговременного хранения;
- доступа с ПК;
- последующей аналитики.

Сервер не входит в критический путь полевой регистрации.

---

# 62. Nest

**Русский:** гнездо

Предполагаемое естественное место проживания исследуемых пчёл.

Координаты гнезда не являются непосредственно наблюдаемыми данными текущего MVP.

В дальнейшем положение гнезда может оцениваться аналитическими методами на основании совокупности наблюдений.

---

# 63. Nest Estimation

**Русский:** определение / оценка положения гнезда

Будущая аналитическая задача Bee Search.

Может использовать:

- ObservationPoint;
- FlightCycle;
- продолжительность отсутствия Bee;
- азимуты;
- данные нескольких точек;
- дополнительные исследовательские правила.

Не входит в текущую модель регистрации полевых событий.

---

# 64. Термины, которых следует избегать без уточнения

## Session

Не использовать как синоним ObservationPoint в техническом коде.

Отдельной `ObservationSession` нет.

## Location

Может означать как GPS reading, так и физическое место.

В коде следует использовать более точные названия:

`ObservationPoint`

`LocationReading`

`coordinates`

## Point

Допустимо в UI, но в технической модели предпочтительно `ObservationPoint`.

## Status

Не следует создавать обобщённое поле `status`, если состояние может быть вычислено из существующих данных.

## GroupRelease

Допустимо как название пользовательского действия, но не как существующая предметная сущность.

## Observer

Допустимо как понятие человека-наблюдателя, но в MVP сущности `Observer` в базе нет.

# 66. Правило расширения глоссария

Новый термин следует добавлять в этот документ, если:

1. он становится частью предметной модели;
2. для одного понятия начинают использоваться разные названия;
3. термин может быть неоднозначно понят Codex или разработчиком;
4. появляется новое устойчивое техническое понятие проекта;
5. термин используется в нескольких проектных документах.

Глоссарий не должен превращаться в описание реализации.

Для подробных правил используются соответствующие документы:

- требования → `product-requirements.md`;
- сценарии → `user-workflows.md`;
- предметные правила → `domain-model.md`;
- структура данных → `data-model.md`;
- техническая архитектура → `architecture.md`;
- принятые решения → `decisions.md`.

# 67. Главная терминологическая цепочка проекта

Основная структура предметной области:

`Territory → ObservationPoint → Bee → FlightCycle`

Основная структура одного FlightCycle:

`departure_time → return_time? + azimuth_deg?`

Основная идентификация Bee:

`mark_color + mark_position`

Основной географический принцип:

`coordinates belong to ObservationPoint`

Основной принцип повторных наблюдений:

`новое наблюдение в том же месте → новая ObservationPoint`

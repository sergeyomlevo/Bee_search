# Bee Search — User Workflows

## 1. Назначение документа

Этот документ описывает основные пользовательские сценарии мобильного приложения **Bee Search**.

Главная задача документа — зафиксировать последовательность действий наблюдателя в реальной полевой работе.

Документ отвечает прежде всего на вопрос:

> Что делает пользователь и как приложение должно реагировать на его действия?

Функциональные требования продукта определены в `product-requirements.md`.

Модель предметной области определяется отдельно в `domain-model.md`.

---

# 2. Общая схема работы приложения

Работу с приложением следует разделять на два разных процесса:

1. **настройка территории** — выполняется редко;
2. **обычная полевая работа** — выполняется при каждом наблюдении.

Создание или выбор территории не должно быть обязательным шагом при каждом запуске приложения.

## 2.1. Первичная настройка территории и необязательная подготовка карты

```text
Создание территории
        ↓
Задание кода и названия
        ↓
Территория становится текущей
        ↓
Обычная карта работает online при наличии сети
        ↓ при необходимости
Подготовить прямоугольную область для офлайн
```

Offline preparation является дополнительной гарантией доступности карты, а не
частью существования Territory и не отдельным режимом карты.

## 2.2. Обычная полевая работа

```text
Запуск приложения
        ↓
Автоматически используется текущая территория
        ↓
Карта территории
        ↓
Создание точки наблюдения
        ↓
Подготовка пчёл
        ↓
Групповой первый выпуск
        ↓
Независимое наблюдение
        ↓
Возвращения
        ↓
Повторные индивидуальные вылеты
        ↓
Возвращения
        ↓
...
        ↓
Завершение наблюдения
        ↓
Просмотр сохранённых результатов
```

Количество повторных циклов заранее не задаётся.

---

# 3. Первый запуск приложения

Если приложение запускается впервые и ни одна территория ещё не создана или не выбрана, пользователь должен перейти к настройке территории.

Код наблюдателя не требуется для создания Territory и не должен заполняться автоматически на чистой установке.

Для обычной полевой работы должна быть определена хотя бы одна текущая
Territory. Offline package не обязателен: при наличии сети карта работает
online, а GPS, ObservationPoint и исследовательские операции не блокируются
его отсутствием.

Минимальный сценарий первого запуска:

```text
Запуск Bee Search
        ↓
Территорий нет
        ↓
Создать территорию
        ↓
Задать код и название
        ↓
Сделать территорию текущей
        ↓
Перейти к рабочей карте
        ↓ при необходимости
Выбрать область → Подготовить для офлайн
```

---

# 4. Обычный запуск приложения

Если пользователь ранее уже работал с приложением и текущая территория определена, приложение должно запомнить её между сессиями.

При следующем запуске приложение не должно снова требовать выбора территории.

Пользователь должен максимально быстро попадать в рабочую часть приложения.

Пример:

```text
Запуск Bee Search
        ↓
Текущая территория:
KLYAZMA-01
        ↓
Открывается карта этой территории
```

На рабочем экране должно быть понятно, какая территория сейчас активна.

Пользователь должен иметь возможность явно перейти к управлению территориями и выбрать другую.

---

# 5. Текущая территория

Приложение должно хранить понятие **текущей территории**.

После создания новой территории или явного выбора существующей она становится текущей.

Текущая территория сохраняется между запусками приложения.

Все новые точки наблюдения по умолчанию создаются внутри текущей территории.

Пример:

```text
Текущая территория

KLYAZMA-01
Клязьминская пойма
```

Пользователь не должен подтверждать этот выбор при каждом запуске.

Для смены территории используется отдельное действие:

```text
Территория → Сменить
```

После выбора другой территории она становится новой текущей территорией и используется также при последующих запусках.

---

# 6. Управление территориями

Управление территориями является отдельным режимом приложения и не должно мешать быстрому запуску полевой работы.

В нём пользователь может:

* увидеть список доступных территорий;
* увидеть текущую территорию;
* создать новую территорию;
* выбрать другую существующую территорию;
* проверить гарантированное offline coverage;
* при необходимости подготовить новую область;
* продолжить или повторить incomplete download;
* безопасно расширить подготовленное покрытие.

Пример:

```text
Территории

● KLYAZMA-01
  Клязьминская пойма
  Offline: готово
  Текущая

○ MESCHERA-01
  Мещёра
  Offline: готово

○ VLAD-02
  Владимирский участок
  Offline: загружено не полностью

[ + НОВАЯ ТЕРРИТОРИЯ ]
```

---

# 7. Создание новой территории

Создание Territory и подготовка offline coverage являются разными действиями.
После сохранения идентификационных данных Territory может стать текущей и
использоваться с обычной online-картой. Подготовку нужной области пользователь
может выполнить сразу или позднее.

## 7.1. Данные территории

Пользователь задаёт как минимум:

```text
Код территории
Название территории
```

Пример:

```text
Код: KLYAZMA-01
Название: Клязьминская пойма
```

Код должен быть удобен для дальнейшего объединения данных.

Название предназначено для человека и может быть более описательным.

---

## 7.2. Выбор области для offline preparation

На обычной карте пользователь находит область, которую требуется гарантированно
сохранить на устройстве.

Предполагаемый сценарий:

1. приложение открывает карту;
2. пользователь находит район исследований;
3. выбирает действие `Подготовить для офлайн`;
4. получает rectangle, первоначально основанный на текущем viewport;
5. корректирует rectangle;
6. видит используемый в первом milestone единый field vector profile и zoom;
7. приложение показывает площадь, zoom range, доступное место и приблизительный
   объём загрузки, если его можно оценить без ложной точности;
8. пользователь подтверждает загрузку.

Offline rectangle не обязан совпадать с Territory boundary, ObservationPoint
или текущим viewport. Он является device-local infrastructure, а не данными
Territory.

---

## 7.3. Загрузка офлайн-карты

После выбора области приложение должно загрузить необходимые картографические данные на устройство.

Пользователь должен видеть состояние процесса:

```text
Подготовка территории KLYAZMA-01

Загрузка офлайн-карты
██████████████░░░░ 76 %
```

В первый milestone download выполняется только в foreground. Пользователь может
приостановить, продолжить или повторить incomplete download. После restart
приложение перечитывает сохранённый MapLibre OfflineRegion status и предлагает
продолжение в foreground; продолжение после process death в фоне не обещается.

После успешной загрузки приложение на данном устройстве показывает для области
состояние:

```text
Готово офлайн
```

Это состояние относится к локальной установке приложения на данном устройстве, а не к синхронизируемым исследовательским данным Territory.

Ready показывается только для совместимого `OfflineRegion`, definition которого
соответствует bounds/zoom, metadata связывает его с нужными
Territory/package/profile, а `OfflineRegionStatus.isComplete == true`.
`downloadState == inactive`, ambient cache и тот факт, что карта сейчас видна
online, этого не доказывают.

Границы Ready, downloading/incomplete, failed и выбранной областей должны быть
доступны прямо на обычной карте. Для первого milestone достаточно простого
app-generated GeoJSON outline без сложного объединения полигонов.

---

## 7.4. Переход к рабочей карте

После успешного создания Territory она может автоматически стать текущей и
открыть рабочую карту независимо от наличия offline package.

Сценарий:

```text
Создать территорию
        ↓
Задать код и название
        ↓
Сделать территорию текущей
        ↓
Перейти к рабочей карте
        ↓ optional
Подготовить область для офлайн
```

Последующие запуски приложения используют эту территорию без повторного запроса.

---

## 7.5. Прерывание или ошибка загрузки

Если загрузка карты была прервана, территория не должна теряться.

Приложение должно сохранить её данные и позволить продолжить загрузку позднее.

Состояние OfflineRegion является локальным для данного устройства. Неуспешная
загрузка не изменяет Territory и исследовательские данные.

Состояние может отображаться, например, так:

```text
KLYAZMA-01
Offline coverage загружено не полностью

[ Продолжить загрузку ]
```

Приложение не должно ошибочно показывать такую территорию как полностью подготовленную для офлайн-работы.

Если пользователь добавляет соседнюю область или создаёт replacement, уже
Ready coverage сохраняется. Bounds существующего OfflineRegion не изменяются
in place. Для первого milestone допустимы несколько additive regions. Старый
region можно удалить только после того, как replacement полностью Ready,
использует совместимый profile и действительно покрывает требуемую старую
область.

---

# 8. Выбор другой территории

Смена территории является явным действием пользователя.

Она не должна происходить автоматически при обычном запуске приложения.

Пользователь открывает список территорий и выбирает другую:

```text
KLYAZMA-01   ← текущая
MESCHERA-01
VLAD-02
```

После выбора, например, `MESCHERA-01`:

* она становится текущей;
* открывается её карта;
* новые точки создаются внутри неё;
* при следующем запуске приложения по умолчанию используется `MESCHERA-01`.

Если offline coverage выбранной территории отсутствует или загружено не
полностью, приложение должно ясно показать отсутствие гарантированной карты,
но не блокировать рабочую карту, GPS, создание ObservationPoint или локальные
исследовательские операции.

---

# 9. Незавершённое наблюдение при запуске

Если при предыдущем закрытии приложения существовало незавершённое наблюдение, приложение должно предложить продолжить его.

Территория при этом определяется самим незавершённым наблюдением.

Она не должна автоматически заменяться другой текущей территорией.

Возможный сценарий:

```text
Найдено незавершённое наблюдение

Территория: KLYAZMA-01
Точка: P-017

[ ПРОДОЛЖИТЬ ]
[ ПЕРЕЙТИ К КАРТЕ ]
```

Конкретная форма интерфейса определяется позднее.

---

# 10. Переход к рабочей карте

При обычном запуске после определения текущей территории приложение должно максимально быстро предоставить пользователю рабочую карту.

На ней отображаются:

* одна карта текущей территории, использующая online и подготовленные offline
  ресурсы;
* текущее GPS-положение;
* ранее созданные точки этой территории;
* код или название текущей территории.

Пример:

```text
KLYAZMA-01                         ⋮

             КАРТА

                  ● P-012

        ◎ текущее положение


[ + НОВАЯ ТОЧКА ]
```

Этот экран следует считать основным стартовым экраном обычной полевой работы.

---

# 11. Создание новой точки наблюдения

Пользователь выбирает действие:

**Новая точка**

Перед началом создания приложение проверяет `observer_code`.

Если код отсутствует:

```text
Новая точка
        ↓
observer_code отсутствует
        ↓
предложить ввести непустой код
        ↓
сохранить код в DataStore
        ↓
продолжить создание ObservationPoint
```

Фиктивный код не подставляется. Если сохранить введённый код не удалось, ObservationPoint не создаётся.

Приложение получает текущую GPS-позицию и создаёт предварительное положение новой точки.

При начале создания карта центрируется на этой GPS-позиции. Исходный GPS fix, включая доступную accuracy, фиксируется как исходное измерение для создаваемой точки и не заменяется последующими координатами центра карты.

На карте одновременно должны быть различимы:

* текущее GPS-положение;
* предполагаемое положение создаваемой точки.

Если доступна оценка точности GPS, она показывается пользователю.

---

# 12. Корректировка GPS-положения

Пользователь визуально сравнивает показанное положение с окружающей местностью и картой.

Если GPS определил положение достаточно точно, пользователь подтверждает точку без изменения.

Если положение ошибочно, пользователь перемещает и масштабирует карту под неподвижным прицелом, расположенным в геометрическом центре карты. Отдельный маркер не перетаскивается. Координаты под прицелом всегда соответствуют текущему центру карты и являются предлагаемым итоговым положением ObservationPoint.

Например, пользователь знает, что находится:

* на конкретной лесной дороге;
* возле пересечения просек;
* на берегу;
* рядом с хорошо различимым объектом,

а GPS показывает положение в стороне.

До подтверждения пользователь может отдельным действием вернуть карту и прицел к исходной GPS-позиции.

После корректировки пользователь явно подтверждает точку. Перемещение карты само по себе не создаёт и не сохраняет ObservationPoint.

Приложение сохраняет итоговое положение точки, локальный календарный `observation_year` и следующий `point_number` в области `Territory + observation_year + observer_code`. Определение номера и запись точки выполняются одной транзакцией. UUID остаётся идентичностью записи.

При наличии соответствующих данных желательно также сохранить:

* первоначальную GPS-позицию;
* заявленную точность GPS;
* подтверждённые пользователем координаты точки.

---

# 13. Координаты точки и пчёл

Координаты принадлежат точке наблюдения.

Отдельным пчёлам координаты не присваиваются.

Все наблюдения за пчёлами внутри одной точки используют координаты этой точки.

Это позволяет избежать искусственного пространственного разброса из-за повторных GPS-измерений.

---

# 14. Подготовка наблюдения

После создания точки пользователь переходит к подготовке списка пчёл.

К этому моменту пчёлы уже могут быть:

* пойманы;
* индивидуально помечены;
* помещены в контейнер;
* накормлены сиропом.

Количество пчёл определяется фактическим результатом отлова.

Пользователь не обязан заполнять заранее заданное количество позиций.

Отдельного числового лимита Bee нет. Добавлять можно любую ещё не использованную комбинацию `mark_color + mark_position` из текущего каталога; когда свободных комбинаций нет, добавление становится недоступно.

---

# 15. Добавление пчёл

Пользователь выбирает метки тех пчёл, которые реально подготовлены к выпуску.

Например:

```text
☑ Белая
☑ Белая КП
☑ Белая КЛ

☑ Синяя
☑ Синяя КП
☑ Синяя КЛ

☑ Жёлтая
☑ Жёлтая КП
☐ Жёлтая КЛ
```

В этом примере активными становятся восемь пчёл.

`Жёлтая КЛ` не создаётся как наблюдаемая пчела.

Пользователь должен иметь возможность исправить набор до начала первого выпуска.

Для быстрого последовательного ввода после ручного выбора цвета интерфейс автоматически выбирает первую свободную позицию в порядке `Обычная → КП → КЛ`. После успешного сохранения Bee цвет остаётся выбранным, а выбор переходит к следующей свободной позиции этого цвета. Когда позиции цвета исчерпаны, выбирается первая свободная комбинация следующего цвета в порядке каталога.

Ручной выбор цвета или позиции всегда имеет приоритет. Занятые комбинации недоступны, а нажатие `Добавить` сохраняет только явно показанную выбранную комбинацию; изменение доступности не должно молча создать другую Bee.

Создание первой Bee одной транзакцией устанавливает для ObservationPoint результат `BEES_FOUND`. Добавление следующих Bee этот результат не меняет. Если до первого выпуска пользователь удаляет последнюю подготовленную Bee, результат возвращается в неустановленное состояние.

Пустой список Bee не означает, что пчёлы отсутствуют: он также может означать незавершённую подготовку.

Если после проверки точки пчёлы не найдены, на экране подготовки доступен явный сценарий:

```text
Пчёлы отсутствуют
        ↓
явное подтверждение пользователя
        ↓
NO_BEES_FOUND + completed_at сохраняются одной транзакцией
        ↓
возврат к карте текущей Territory
```

Перед сохранением приложение объясняет, что точка останется историческим наблюдением и будет завершена. Отмена подтверждения ничего не изменяет. Действие доступно только пока результат присутствия не установлен и Bee ещё не добавлены.

После успешного сохранения активной ObservationPoint больше нет: перезапуск не возвращает пользователя к ней, и можно создать следующую точку. После `NO_BEES_FOUND` Bee в завершённую ObservationPoint не добавляются.

---

# 16. Проверка перед первым выпуском

Перед выпуском приложение показывает подготовленный список.

Пользователь визуально проверяет, что набор соответствует фактически находящимся в контейнере пчёлам.

На этом этапе должна существовать возможность:

* добавить пропущенную пчелу;
* удалить ошибочно выбранную;
* изменить ошибочно указанную метку.

После начала наблюдения изменение идентичности уже участвующей пчелы должно выполняться осторожно, чтобы не повредить историю данных.

---

# 17. Первый групповой выпуск

Когда пользователь открывает контейнер, подготовленные пчёлы могут вылететь практически одновременно.

Поэтому пользователь выполняет одно действие:

**Выпустить всех**

Приложение:

1. фиксирует текущее время;
2. создаёт первый цикл для каждой подготовленной пчелы;
3. присваивает всем этим циклам одинаковое время вылета;
4. переводит всех участвующих пчёл в состояние `в полёте`.

Индивидуальная последовательная регистрация первого вылета не требуется.

---

## 17.1. Bee не улетела вместе с группой

Если после группового выпуска отдельная Bee осталась у точки, пользователь регистрирует её как вернувшуюся. Это закрывает её первый FlightCycle, но не меняет общее время группового выпуска.

Когда эта Bee позднее действительно улетает, пользователь запускает обычный следующий вылет. Создаётся `FlightCycle 2` с фактическим индивидуальным временем вылета.

Если первый цикл завершился менее чем через 60 секунд, он остаётся в истории как исходное наблюдение, но позднее не используется как содержательное измерение продолжительности полёта. Ровно 60 секунд и короткие последующие циклы автоматически не исключаются.

---

# 18. Азимут первого выпуска

Во время первого выпуска пчёлы обычно выполняют ориентировочный облёт.

Надёжно определить направление их дальнейшего движения часто невозможно.

Поэтому азимут первого группового выпуска:

* не является обязательным;
* не должен автоматически назначаться;
* его отсутствие является нормальным состоянием данных.

---

# 19. Состояние сразу после первого выпуска

После группового выпуска приложение автоматически переходит на рабочий экран наблюдения.

Например:

```text
БЕЛАЯ
В полёте
00:00
[ ПРИЛЕТЕЛА ]

БЕЛАЯ КП
В полёте
00:00
[ ПРИЛЕТЕЛА ]

СИНЯЯ
В полёте
00:00
[ ПРИЛЕТЕЛА ]
```

Для каждой пчелы может отображаться увеличивающаяся продолжительность текущего отсутствия.

---

# 20. Основной рабочий экран

Это наиболее важный экран приложения во время наблюдения.

Пользователь большую часть времени должен иметь возможность оставаться на нём.

На экране одновременно представлены все активные пчёлы.

Для каждой пчелы показываются как минимум:

* метка;
* текущее состояние;
* живой таймер текущего состояния: от вылета для Bee в полёте либо от возвращения для Bee на точке;
* следующее допустимое действие.

Интерфейс должен позволять быстро найти нужную пчелу по визуальной метке.

Большая часть списка активных пчёл должна быть доступна без сложной навигации. Интерфейс не должен вводить отдельный числовой предел помимо доступных уникальных сочетаний меток.

---

# 21. Возвращение пчелы

Допустим, одновременно находятся в полёте:

```text
Белая
Синяя
Жёлтая КП
```

Хотя белая была первой в списке, раньше возвращается синяя.

Пользователь не должен завершать наблюдение белой или переключать приложение в строгой последовательности.

Он сразу нажимает:

```text
Синяя → ПРИЛЕТЕЛА
```

Приложение:

1. фиксирует текущее время;
2. записывает его как время возвращения синей пчелы;
3. вычисляет продолжительность её цикла;
4. переводит синюю пчелу в состояние `вернулась`;
5. оставляет остальные пчёлы без изменений.

---

# 22. Независимость состояний пчёл

Каждая пчела имеет собственное состояние.

Например:

```text
Белая       В ПОЛЁТЕ       08:41
Белая КП    НА ТОЧКЕ       06:13
Белая КЛ    В ПОЛЁТЕ       07:58
Синяя       НА ТОЧКЕ       05:22
Синяя КП    В ПОЛЁТЕ       08:02
```

Действие с одной пчелой не должно изменять состояние других.

Это является фундаментальным требованием рабочего процесса.

---

# 23. Повторный выпуск

После возвращения пчела может снова получить сироп и быть выпущена.

Пользователь выбирает соответствующую пчелу и выполняет действие:

**Улетела**

Приложение:

1. создаёт новый цикл;
2. фиксирует текущее время вылета;
3. переводит пчелу в состояние `в полёте`;
4. сохраняет предыдущий цикл без изменений.

Например:

```text
Синяя

Цикл 1
09:34:12 → 09:39:27
5:15

Цикл 2
09:41:08 → ...
```

---

# 24. Регистрация азимута

Во время активного наблюдения карточка Bee показывает live-направление верхней короткой стороны
телефона только для текущего открытого FlightCycle, если его `azimuth_deg` ещё отсутствует.
Дополнительно persisted `azimuth_capture_consumed` этого цикла должен быть `false`.

В таком случае он:

1. направляет верх телефона в наблюдаемую сторону ухода Bee;
2. видит текущее true/geographic heading, например `247°`;
3. один раз нажимает на значение;
4. приложение сохраняет его в явный последний FlightCycle этой Bee;
5. атомарно помечает полевую возможность этого FlightCycle использованной;
6. сохранённое число перестаёт изменяться вслед за поворотом телефона, а control становится
   read-only.

После `Прилетела` FlightCycle закрыт, поэтому azimuth control остаётся на месте, но становится
read-only: он показывает сохранённый азимут закрытого цикла либо `—°`. После `Улетела` persisted
состояние содержит новый открытый FlightCycle, и control снова показывает live heading и принимает
one-tap фиксацию.

Например:

```text
247°
```

Sensor heading сначала является магнитным. `HeadingProvider` корректирует его через
`GeomagneticField`, используя подтверждённые координаты ObservationPoint, системное время каждого
вычисления и высоту `0 м`, поскольку отдельная высота в текущей модели отсутствует. В Room попадает
только скорректированный истинный / географический азимут.

После успешной фиксации вверху экрана примерно на три секунды появляется `ОТМЕНИТЬ`. Оно очищает
азимут только этого FlightCycle, но не возвращает возможность повторной фиксации: control показывает
`—°` и остаётся disabled даже после restart. Более новая фиксация другого FlightCycle заменяет
предыдущий Undo-контекст. Постоянное редактирование и ручной числовой ввод на активном полевом экране
отсутствуют; repository-возможность изменить или удалить ненадёжное значение сохраняется для
будущего history/edit workflow.

---

# 25. Вылет без азимута

Пользователь может не успеть определить направление.

В таком случае он просто регистрирует:

**Улетела**

без азимута.

Цикл остаётся полностью допустимым.

Приложение не должно:

* требовать измерить направление;
* задерживать регистрацию времени;
* автоматически подставлять предыдущее значение;
* использовать `0°` вместо отсутствующего значения.

---

# 26. Ошибочный азимут

После фиксации пользователь может решить, что измерение было ненадёжным.

Например:

* пчела изменила направление;
* пользователь неправильно направил телефон;
* компас был нестабилен;
* рядом находился источник магнитных помех.

На active observation screen сразу после фиксации доступно только короткое действие `ОТМЕНИТЬ`.
Оно удаляет азимут, но сохраняет использованной однократную возможность этого FlightCycle.

Постоянное удаление позднее может быть доступно через отдельный history/edit workflow, где
пользователь открывает соответствующий цикл и выбирает:

**Удалить азимут**

После этого значение отсутствует.

Время вылета и остальные данные цикла сохраняются.

Такой history/edit UI в текущий active observation milestone не входит.

---

# 27. Окно полевой фиксации азимута

Регистрация времени вылета имеет более высокий приоритет, чем работа с компасом.

Поэтому интерфейс не должен заставлять пользователя задерживать регистрацию события ради азимута.

На рабочем экране азимут можно добавить одним быстрым нажатием только к текущему открытому
FlightCycle Bee в состоянии `В полёте`. Возможность однократна для конкретного вылета. После
успешной фиксации повторный capture запрещён; Undo удаляет ошибочное значение, но не даёт второй
попытки. После `Прилетела` закрытый FlightCycle через active observation UI не редактируется.

Следующее `Улетела` создаёт новый FlightCycle и новую однократную возможность. Действия `Прилетела`
и `Улетела` не создают и не требуют азимут автоматически.

---

# 28. Несколько событий подряд

Интерфейс должен учитывать ситуацию, когда события происходят почти одновременно.

Например:

```text
09:41:10 — вернулась Белая
09:41:14 — вернулась Синяя КП
09:41:20 — улетела повторно Белая
09:41:27 — вернулась Жёлтая
```

Каждое действие должно выполняться независимо и требовать минимального количества операций.

После регистрации события приложение должно возвращать пользователя к общему рабочему экрану, а не оставлять его глубоко внутри карточки одной пчелы.

---

# 29. Ошибочное нажатие

Полевой интерфейс должен учитывать случайные нажатия.

Пользователь должен иметь возможность исправить ошибочно зарегистрированное событие.

При этом исправление не должно быть настолько лёгким, чтобы событие можно было случайно удалить одним касанием.

Предпочтительная схема:

```text
обычное нажатие → регистрация события
дополнительное действие → редактирование / отмена
```

Конкретная UX-модель определяется после прототипирования.

---

# 30. Пчела не вернулась

Если пчела не возвращается, пользователь продолжает работать с остальными пчёлами.

Такая пчела остаётся в состоянии `в полёте`.

Она не должна блокировать:

* регистрацию других возвращений;
* повторные выпуски;
* завершение работы на точке.

При завершении наблюдения приложение должно позволить оставить её цикл без времени возвращения.

---

# 31. Завершение наблюдения

Когда пользователь решает закончить работу на данной точке, он выбирает:

**Завершить наблюдение**

Обычное завершение доступно только после явного установления результата присутствия пчёл. Оно не должно молча завершать точку, если результат ещё не установлен. Отдельный сценарий `Пчёлы отсутствуют` одновременно сохраняет `NO_BEES_FOUND` и завершает точку.

Если существуют пчёлы, которые всё ещё числятся в полёте, приложение предупреждает об этом.

Например:

```text
Наблюдение ещё не завершено для:

Белая КЛ
Синяя

Завершить наблюдение всё равно?
```

Пользователь может:

* вернуться к наблюдению;
* подтвердить завершение.

Подтверждение не создаёт фиктивного времени возвращения.

---

# 32. Автоматическое сохранение

Все значимые действия должны сохраняться сразу после выполнения.

Например, после нажатия `Прилетела` запись должна быть сохранена до выполнения следующего пользовательского действия.

Не следует рассчитывать только на общую кнопку сохранения в конце наблюдения.

Это снижает риск потери данных при:

* случайном закрытии приложения;
* разрядке телефона;
* сбое приложения;
* перезагрузке устройства.

---

# 33. Восстановление после закрытия приложения

Если приложение было закрыто во время активного наблюдения, при следующем запуске пользователь должен иметь возможность продолжить работу.

Должны быть восстановлены:

* территория;
* точка;
* набор активных пчёл;
* состояния пчёл;
* времена текущих вылетов;
* предыдущие циклы;
* зарегистрированные азимуты.

Продолжительность текущего полёта вычисляется из сохранённого времени вылета и текущего времени, а не зависит от непрерывно работающего таймера.

---

# 34. Просмотр завершённой точки

Пользователь выбирает ранее созданную точку на карте.

Приложение показывает сводку наблюдения.

Например:

```text
Точка 12
26.08.2026

Белая
  цикл 1   05:15
  цикл 2   04:48   127°
  цикл 3   05:02   132°

Белая КП
  цикл 1   06:41
  цикл 2   не вернулась

Синяя
  цикл 1   04:57
```

Точный внешний вид определяется позднее.

Сохранённые абсолютные моменты событий отображаются в текущем часовом поясе устройства. Отдельный часовой пояс ObservationPoint в MVP не хранится.

История должна позволять отделять точки по сохранённому `observation_year` и различать `BEES_FOUND` и явно подтверждённый `NO_BEES_FOUND`. Конкретный экран Points и визуальное оформление карты определяются отдельным UI milestone.

Пользователю не требуется читать JSON или содержимое внутренней базы данных.

---

# 35. Работа с несколькими точками

После завершения наблюдения пользователь возвращается к карте текущей территории.

Он может:

* просмотреть существующую точку;
* перейти в другое место;
* создать новую точку;
* начать новое наблюдение.

Новая точка получает собственные координаты и собственный набор наблюдений.

Пчёлы одной точки не должны автоматически переноситься в другую точку.

---

# 36. Работа без интернета

Offline readiness означает, что выбранная область была явно подготовлена и
полностью сохранена на устройстве. Это не отдельный режим карты.

Типичный сценарий:

```text
Дома / при наличии интернета

Открыть обычную карту Territory
→ выбрать прямоугольную область
→ Подготовить для офлайн
→ дождаться Ready

              ↓

В поле / связи нет

Запустить приложение
→ автоматически открыть текущую территорию
→ использовать ранее загруженную карту
→ создать точку
→ подготовить пчёл
→ провести наблюдение
→ сохранить результаты
```

Недоступность сервера или мобильной сети не должна прерывать этот процесс.

Если необходимые картографические данные не были подготовлены, приложение
должно явно предупредить, что гарантированной карты нет. Исследовательский
workflow остаётся доступен; за пределами Ready coverage карта без сети может
быть неполной.

---

# 37. Будущая синхронизация

Когда соединение доступно, приложение в дальнейшем должно иметь возможность синхронизировать локальные данные с сервером.

С точки зрения пользователя предполагаемый сценарий:

```text
Полевое наблюдение
        ↓
Локальное сохранение
        ↓
Появление сети
        ↓
Синхронизация
        ↓
Данные доступны на ПК
```

Пользователь не должен вручную экспортировать JSON для обычной синхронизации.

Точная модель синхронизации определяется отдельно.

---

# 38. Приоритет действий в полевом интерфейсе

При проектировании интерфейса следует исходить из следующего порядка важности:

1. не пропустить событие;
2. правильно определить пчелу;
3. точно зафиксировать время;
4. при возможности определить азимут;
5. показать дополнительную информацию;
6. выполнить административные действия.

Если дополнительная функция мешает быстро зарегистрировать возвращение или вылет, она должна быть вынесена из основного пути.

---

# 39. Основной UX-принцип

Во время активного наблюдения пользователь должен работать преимущественно с **одним общим экраном**, а не постоянно открывать и закрывать карточки отдельных пчёл.

Основная единица взаимодействия — компактная строка или карточка активной пчелы.

Она должна позволять быстро ответить на три вопроса:

```text
Кто это?
Что с ней сейчас?
Что я могу нажать?
```

---

# 40. Что требует полевого прототипирования

Следующие решения нельзя считать окончательными без испытания интерфейса в реальной работе:

* размер карточки пчелы;
* расположение кнопок `Улетела` и `Прилетела`;
* способ визуального отображения цвета метки;
* способ обозначения `КП` и `КЛ`;
* необходимость постоянного отображения секундомера;
* звуковая или вибрационная обратная связь после фиксации события;
* необходимость подтверждения обычных событий;
* способ отмены ошибочного события;
* порядок регистрации азимута;
* возможность работы одной рукой;
* удобство интерфейса при ярком солнечном освещении;
* максимально удобное количество одновременно видимых пчёл;
* допустимый объём офлайн-карты одной территории;
* поведение при неполной загрузке карты;
* практическая разница source z15 и z16 на целевом Samsung.

Эти вопросы должны решаться не только теоретически, но и посредством раннего рабочего прототипа на реальном телефоне.

# 41. Первый прототип пользовательского потока

Первая версия интерфейса должна позволить проверить следующий минимальный сценарий:

```text
Если территория ещё не создана:
создать территорию
        ↓
Открыть текущую территорию
        ↓ optional до поля
выбрать rectangle и подготовить его для офлайн
        ↓
Перед первой точкой при необходимости ввести observer_code
        ↓
Создать точку на карте
        ↓
При необходимости скорректировать GPS
        ↓
Выбрать 5–10 меток
        ↓
Выпустить всех
        ↓
Увидеть всех пчёл в состоянии «В полёте»
        ↓
Нажать «Прилетела» у произвольной пчелы
        ↓
Повторно нажать «Улетела»
        ↓
При желании сохранить азимут
        ↓
Продолжать работу с остальными пчёлами
        ↓
Завершить наблюдение
        ↓
Открыть сохранённый результат
```

До реализации сложной аналитики, серверной синхронизации и дополнительных функций этот поток должен быть проверен в реальной полевой работе.

# Bee Search — User Workflows

## 1. Назначение документа

Этот документ описывает основные пользовательские сценарии мобильного приложения **Bee Search**.

Главная задача документа — зафиксировать последовательность действий наблюдателя в реальной полевой работе.

Документ отвечает прежде всего на вопрос:

> Что делает пользователь и как приложение должно реагировать на его действия?

Функциональные требования продукта определены в `product-requirements.md`.

Модель предметной области определяется отдельно в `domain-model.md`.

---

# 2. Общая схема работы приложения

Работу с приложением следует разделять на два разных процесса:

1. **настройка наблюдателей и территорий** — выполняется редко;
2. **обычная полевая работа** — выполняется при каждом наблюдении.

Создание или выбор территории не должно быть обязательным шагом при каждом запуске приложения.

## 2.1. Первичная настройка и необязательная подготовка карты

```text
Создание Observer
        ↓
Задание кода и ФИО
        ↓
Observer становится current
        ↓
Создание Territory
        ↓
Задание кода, названия, региона и района
        ↓
Территория становится текущей
        ↓
Обычная карта работает online при наличии сети
        ↓ при необходимости
Подготовить прямоугольную область для офлайн
```

Offline preparation является дополнительной гарантией доступности карты, а не
частью существования Territory и не отдельным режимом карты.

## 2.2. Обычная полевая работа

```text
Запуск приложения
        ↓
Автоматически используются current Observer и current Territory
        ↓
Карта территории
        ↓
Создание точки наблюдения
        ↓
Открытие наблюдения
        ↓
Первый вылет конкретной Bee
        ↓
Независимое наблюдение
        ↓
Возвращения
        ↓
Повторные индивидуальные вылеты
        ↓
Возвращения
        ↓
...
        ↓
Завершение наблюдения
        ↓
Просмотр сохранённых результатов
```

Количество повторных циклов заранее не задаётся.

# 3. Первый запуск приложения

Если приложение запускается впервые, карта всё равно доступна даже без current
Observer или current Territory, чтобы пользователь мог ознакомиться с
интерфейсом. Settings можно открыть и покинуть в любой момент. Фиктивные
записи не создаются автоматически.

Если существует активная незавершённая ObservationPoint, её recovery имеет
приоритет над проверкой current selection: приложение открывает эту работу,
чтобы не скрыть уже начатое полевое наблюдение.

Для создания новой ObservationPoint и других действий, требующих контекста,
должны быть определены оба current selection. При неполном контексте запись не
выполняется и пользователь получает предложение выбрать Observer и Territory в
Settings.
Offline package не обязателен: при наличии сети карта работает online, а GPS,
ObservationPoint и исследовательские операции не блокируются его отсутствием.

Минимальный сценарий первого запуска:

```text
Запуск Bee Search
        ↓
Открыть карту или Settings по выбору пользователя
        ↓
Создать или выбрать Observer и Territory перед созданием точки
        ↓
Перейти к рабочей карте с полным контекстом
        ↓ при необходимости
Выбрать область → Подготовить для офлайн
```

---

# 4. Обычный запуск приложения

## 4.1. Settings без обязательного onboarding

Settings можно открыть с карты и закрыть без созданных Observer или Territory;
экран не является ловушкой и не блокирует просмотр карты. В списках доступны
выбор current записи, редактирование и удаление. Удаление требует подтверждения
и разрешено только для записи, не связанной с ObservationPoint; используемые
исследовательские данные не удаляются cascade. При удалении текущей свободной
записи соответствующий current ID очищается.

Если пользователь ранее уже работал с приложением и оба current selection
определены, приложение должно запомнить их между сессиями.

При следующем запуске приложение не должно снова требовать выбора территории.

Пользователь должен максимально быстро попадать в рабочую часть приложения.

Пример:

```text
Запуск Bee Search
        ↓
Текущая территория:
KLYAZMA-01
        ↓
Открывается карта этой территории
```

На рабочем экране должно быть понятно, какая территория сейчас активна.

Пользователь должен иметь возможность явно перейти к управлению территориями и выбрать другую.

---

# 5. Текущая территория

Приложение должно хранить понятие **текущей территории**.

После создания новой территории или явного выбора существующей она становится текущей.

Текущая территория сохраняется между запусками приложения.

Все новые точки наблюдения по умолчанию создаются внутри текущей территории.

Пример:

```text
Текущая территория

KLYAZMA-01
Клязьминская пойма
```

Пользователь не должен подтверждать этот выбор при каждом запуске.

Для смены территории используется отдельное действие:

```text
Территория → Сменить
```

После выбора другой территории она становится новой текущей территорией и используется также при последующих запусках.

---

# 6. Управление территориями

Управление территориями является отдельным режимом приложения и не должно мешать быстрому запуску полевой работы.

В нём пользователь может:

* увидеть список доступных территорий;
* увидеть текущую территорию;
* создать новую территорию;
* выбрать другую существующую территорию;
* проверить гарантированное offline coverage;
* при необходимости подготовить новую область;
* продолжить или повторить incomplete download;
* безопасно расширить подготовленное покрытие.

Пример:

```text
Территории

● KLYAZMA-01
  Клязьминская пойма
  Offline: готово
  Текущая

○ MESCHERA-01
  Мещёра
  Offline: готово

○ VLAD-02
  Владимирский участок
  Offline: загружено не полностью

[ + НОВАЯ ТЕРРИТОРИЯ ]
```

---

# 7. Создание новой территории

Создание Territory и подготовка offline coverage являются разными действиями.
После сохранения идентификационных данных Territory может стать текущей и
использоваться с обычной online-картой. Подготовку нужной области пользователь
может выполнить сразу или позднее.

## 7.1. Данные территории

Пользователь задаёт как минимум:

```text
Код территории
Название территории
```

Пример:

```text
Код: KLYAZMA-01
Название: Клязьминская пойма
```

Код должен быть удобен для дальнейшего объединения данных.

Название предназначено для человека и может быть более описательным.

---

## 7.2. Выбор области для offline preparation

На обычной карте пользователь формирует будущую offline coverage из нужных
прямоугольных фрагментов — участков, которые требуется гарантированно сохранить на
устройстве. Сохранённый набор участков одной Territory образует её Ареал: у Territory
не более одного Ареала, а участок — один прямоугольник внутри него.

Предполагаемый сценарий:

1. приложение открывает обычную карту;
2. пользователь pan/zoom выставляет первый нужный участок;
3. текущий viewport становится rectangle fragment, который пользователь
   добавляет в будущую offline coverage действием `Добавить участок`;
4. выбранный фрагмент остаётся видимым поверх карты;
5. пользователь перемещает или масштабирует карту и добавляет следующие
   фрагменты;
6. до получения Map Package пользователь визуально проверяет составное покрытие целиком,
   видит overlap соседних фрагментов и возможные незакрытые промежутки;
7. видит используемый в первом milestone единый field vector profile и zoom,
   площадь, доступное место и приблизительный объём загрузки, если его можно
   оценить без ложной точности;
8. пользователь сохраняет участки действием `Готово`.

Фрагменты могут иметь разный размер вследствие разного zoom и положения карты;
их частичное перекрытие является нормальным и полезным. Составное coverage —
это объединение выбранных rectangles, а не один общий bounding rectangle.
Приложение не добавляет автоматический fixed buffer: необходимую ширину
покрытия пользователь определяет сам по местности. Геометрия coverage не
обязана совпадать с Territory boundary, ObservationPoint или текущим viewport.
Она является device-local map infrastructure, а не данными research model. В
текущем прототипе список fragments сохраняется отдельно для каждой Territory по
стабильному UUID; редактирование работает через working copy.

`Готово` — единственное явное завершение редактирования: оно сохраняет выбранные
участки и выходит из режима. Обычного действия `Выйти`, которое молча отбрасывает
несохранённые изменения, в редакторе нет. Открытие редактора само по себе не
является изменением: dirty-state возникает только тогда, когда working copy
отличается от последнего сохранённого набора. Если пользователь покидает редактор
системным `Back` при несохранённых изменениях, приложение требует явного решения —
`Сохранить`, `Выйти без сохранения` или `Остаться`; без несохранённых изменений
`Back` закрывает редактор без диалога. `Отменить последний` убирает только
последний добавленный участок, `Очистить всё` требует подтверждения, и до `Готово`
оба действия затрагивают только working copy, поэтому выход без сохранения
возвращает прежний сохранённый набор.

Первое `Готово` одновременно создаёт Ареал, поэтому приложение спрашивает его
название диалогом `Название ареала` с предзаполненным названием Territory. Пустое
название не создаёт Ареал, а `Отмена` возвращает пользователя в редактор с
сохранённым draft и ничего не записывает. Последующие `Готово` меняют только участки
существующего Ареала и больше имя не спрашивают: имя задаётся один раз и считается
стабильным названием Ареала, отдельного переименования в интерфейсе нет.

После каждого сохранения Bee Search сам создаёт или обновляет файл всего Ареала в
папке обмена, в подпапке `Areas`. Пользователю не нужно копировать координаты и
передавать их вручную: готовый файл содержит все участки Ареала и используется для
подготовки офлайн-карты. Файл — только зеркало: если его удалить, Ареал остаётся, а
файл создаётся заново при следующем открытии экрана Ареала или при отправке.

`Очистить всё` с последующим `Готово` не удаляет Ареал: сохранение отклоняется с
сообщением, что ареал должен содержать хотя бы один участок, сохранённые участки
остаются прежними, а редактор остаётся открытым. Ареал удаляется только отдельным
действием `Удалить ареал` на экране `Objects → Ареал` после подтверждения; вместе с
ним исчезают только его сохранённые участки и managed-файл Ареала, а Territory, точки
наблюдения и установленная офлайн-карта остаются.

## 7.2.1. Просмотр Ареала и отправка файла

Экран `Objects → Ареал` показывает название Ареала, число участков и общую площадь, а
действия на нём — `Посмотреть на карте`, `Отправить ареал` и `Удалить ареал`.

`Посмотреть на карте` открывает отдельный режим просмотра: обычная карта, на которой
видны все сохранённые участки Ареала, а камера сразу показывает Ареал целиком. Панели
редактирования в этом режиме нет, поэтому случайное касание не меняет участки. Чтобы
изменить участки, пользователь нажимает `Изменить участки` на том же экране; после
завершения редактирования он возвращается туда, откуда пришёл. Системная кнопка
возврата ведёт обратно к экрану Ареала.

`Отправить ареал` открывает стандартное меню Android: пользователь выбирает Telegram,
почту, облачное хранилище или другое приложение. Приложение само готовит актуальный
файл Ареала и передаёт его выбранному приложению, поэтому искать файл в «Загрузках»
вручную не нужно. Отправка ничего не меняет в Ареале, а её ошибка показывается
сообщением и не влияет на сохранённые данные.

При удалении неиспользуемой Territory её сохранённое coverage удаляется вместе с
этим device-local map context. Используемую ObservationPoint Territory удалить
нельзя, поэтому её coverage остаётся без изменений.
Сохранённая геометрия не означает, что tiles или другие ресурсы уже скачаны.

## 7.3. Получение и активация офлайн-карты

Первый production acquisition flow — ручной импорт через системный Android Files
picker. Для текущей Territory пользователь выбирает сначала D065 sidecar
manifest, затем соответствующий PMTiles artifact. Приложение stage-ит обе части
в app-controlled storage, проверяет совместимость и целостность и только затем
атомарно делает package active.

```text
Выбрать coverage
        ↓
Импортировать карту
        ↓
Выбрать manifest → выбрать PMTiles
        ↓
stage → validate → atomically activate
        ↓
Офлайн-карта готова
```

Если package ещё не Ready, обычная карта явно сообщает об этом и предлагает
сначала выбрать coverage либо импортировать карту. Неудачный import или
replacement не изменяет уже активный package. Future server download должен
использовать тот же package lifecycle; pause/resume, progress и background
semantics не входят в этот milestone.

После успешной загрузки приложение на данном устройстве показывает для области
состояние:

```text
Готово офлайн
```

Это состояние относится к локальной установке приложения на данном устройстве, а не к синхронизируемым исследовательским данным Territory.

Ready показывается только для полностью staged, проверенного и атомарно
активированного совместимого PMTiles Map Package. Package identity/version
metadata должна позволять отличить установленный artifact от совместимой
замены. Внешний URI, partially staged file, ambient cache и тот факт, что карта
сейчас видна online, этого не доказывают.

Выбранное coverage и состояние Ready/не-Ready доступны прямо на обычной карте.
Для первого milestone достаточно простого app-generated GeoJSON outline без
сложного объединения полигонов.

---

## 7.4. Переход к рабочей карте

После успешного создания Territory она может автоматически стать текущей и
открыть рабочую карту независимо от наличия offline package.

Сценарий:

```text
Создать территорию
        ↓
Задать код и название
        ↓
Сделать территорию текущей
        ↓
Перейти к рабочей карте
        ↓ optional
Подготовить область для офлайн
```

Последующие запуски приложения используют эту территорию без повторного запроса.

---

## 7.5. Прерывание или ошибка загрузки

Если загрузка карты была прервана, территория не должна теряться.

Приложение должно сохранить её данные и позволить продолжить загрузку позднее.

Состояние установки и активации Map Package является локальным для данного
устройства. Неуспешное acquisition или validation не изменяет Territory и
исследовательские данные.

Состояние может отображаться, например, так:

```text
KLYAZMA-01
Offline coverage загружено не полностью

[ Продолжить загрузку ]
```

Приложение не должно ошибочно показывать такую территорию как полностью подготовленную для офлайн-работы.

Если пользователь меняет coverage или получает replacement, уже активный
package сохраняется. В перспективе coverage можно расширять добавлением
фрагментов без повторного определения всей геометрии; конкретная
generation/download/update/storage механика определяется отдельно. Старый
package можно удалить только после того, как replacement прошёл validation,
использует совместимый profile, покрывает требуемую область и атомарно
активирован.

---

# 8. Выбор другой территории

Смена территории является явным действием пользователя.

Она не должна происходить автоматически при обычном запуске приложения.

Пользователь открывает список территорий и выбирает другую:

```text
KLYAZMA-01   ← текущая
MESCHERA-01
VLAD-02
```

После выбора, например, `MESCHERA-01`:

* она становится текущей;
* открывается её карта;
* новые точки создаются внутри неё;
* при следующем запуске приложения по умолчанию используется `MESCHERA-01`.

Если offline coverage выбранной территории отсутствует или загружено не
полностью, приложение должно ясно показать отсутствие гарантированной карты,
но не блокировать рабочую карту, GPS, создание ObservationPoint или локальные
исследовательские операции.

---

# 9. Незавершённое наблюдение при запуске

Если при предыдущем закрытии приложения существовало незавершённое наблюдение, приложение должно предложить продолжить его.

Территория при этом определяется самим незавершённым наблюдением.

Она не должна автоматически заменяться другой текущей территорией.

Возможный сценарий:

```text
Найдено незавершённое наблюдение

Территория: KLYAZMA-01
Точка: P-017

[ ПРОДОЛЖИТЬ ]
[ ПЕРЕЙТИ К КАРТЕ ]
```

Конкретная форма интерфейса определяется позднее.

---

# 10. Переход к рабочей карте

При обычном запуске после определения текущей территории приложение должно максимально быстро предоставить пользователю рабочую карту.

На ней отображаются:

* одна карта текущей территории, использующая online и подготовленные offline
  ресурсы;
* текущее GPS-положение;
* ранее созданные точки этой территории;
* код или название текущей территории.

Пример:

```text
KLYAZMA-01                         ⋮

             КАРТА

                  ● P-012

        ◎ текущее положение


[ + НОВАЯ ТОЧКА ]
```

Этот экран следует считать основным стартовым экраном обычной полевой работы.

---

# 11. Создание записи на основной карте

Красный прицел в центре основной карты показывает координаты будущей записи.
Пользователь сначала получает GPS-позицию, при необходимости перемещает карту
под прицелом и только затем нажимает общий крестик `Создать запись здесь`.

Перед началом создания приложение проверяет current Observer и current
Territory. Если хотя бы один выбор отсутствует или его UUID больше не
соответствует сохранённой сущности, создание не начинается; показывается
сообщение с предложением открыть Settings.

Крестик фиксирует текущие координаты прицела и открывает компактный chooser:

```text
Красный прицел
        ↓
Создать запись здесь
        ↓
Что создать?
        ↓
Точка наблюдения
        ↓
создать transient draft с observer_id + territory_id,
original GPS и зафиксированными координатами прицела
```

Отдельного экрана или действия `Подтвердить координаты` после выбора типа нет.
Открытие chooser само по себе ничего не создаёт. Дупло, Колода, Ловушка и Пасека
пока могут быть только явно недоступными пунктами: форм и Room-записей для них нет.

После появления сохранённой точки переключение current Observer или current
Territory не меняет её immutable `observer_id` и `territory_id`.

При первом доступном GPS fix карта центрируется на этой позиции. При нажатии
крестика исходный GPS fix, включая доступную accuracy, фиксируется как исходное
измерение создаваемой точки. Одновременно фиксируется текущий центр карты;
последующие GPS updates не меняют выбранные latitude/longitude.

На карте одновременно должны быть различимы:

* текущее GPS-положение;
* предполагаемое положение создаваемой точки.

Если доступна оценка точности GPS, она показывается пользователю.

# 12. Корректировка GPS-положения

Пользователь визуально сравнивает показанное положение с окружающей местностью и картой.

Если GPS определил положение достаточно точно, пользователь нажимает крестик без изменения карты.

Если положение ошибочно, пользователь перемещает и масштабирует карту под неподвижным прицелом, расположенным в геометрическом центре карты. Отдельный маркер не перетаскивается. Координаты под прицелом всегда соответствуют текущему центру карты и являются предлагаемым итоговым положением ObservationPoint.

Например, пользователь знает, что находится:

* на конкретной лесной дороге;
* возле пересечения просек;
* на берегу;
* рядом с хорошо различимым объектом,

а GPS показывает положение в стороне.

До нажатия крестика пользователь может отдельным действием вернуть карту и
прицел к текущей GPS-позиции. После корректировки крестик фиксирует координаты,
а выбор `Точка наблюдения` сразу открывает transient-стадию «Подготовка точки».
На карте больше нет отдельного `Подтвердить координаты / Отмена`.

Закрытие chooser возвращает на ту же карту без записи. В подготовке пользователь
может выбрать `Отмена` или Android system Back: draft отбрасывается, приложение
возвращается к карте текущей Territory, а в Room не появляются ObservationPoint,
Bee или FlightCycle.

Итоговое положение точки, локальный календарный `observation_year` и следующий
`point_number` назначаются только в транзакции первого содержательного
результата. UUID остаётся идентичностью сохранённой записи.

При наличии соответствующих данных желательно также сохранить:

* первоначальную GPS-позицию;
* заявленную точность GPS;
* подтверждённые пользователем координаты точки.

## Практические ориентиры масштаба карты

Ручная полевая проверка online-basemap показала, что разные задачи требуют
разных масштабов карты:

* примерно `z15–16` удобен для общей ориентации по территории, просмотра
  дорог и выбора следующего места наблюдения;
* примерно `z19–20` нужен для точной корректировки координаты
  ObservationPoint относительно GPS, когда смещение может составлять всего
  `5–20 м`.

Поэтому recenter возвращает центр карты к текущему GPS, сохраняя выбранный
пользователем zoom. Эти диапазоны — практические ориентиры по результатам
ручной проверки, а не жёсткие системные ограничения. Автоматическое
переключение масштаба по режимам сейчас не вводится.

# 13. Координаты точки и пчёл

Координаты принадлежат точке наблюдения.

Отдельным пчёлам координаты не присваиваются.

Все наблюдения за пчёлами внутри одной точки используют координаты этой точки.

Это позволяет избежать искусственного пространственного разброса из-за повторных GPS-измерений.

---

# 14. Подготовка точки

После выбора `Точка наблюдения` открывается transient-подготовка точки. Она хранит
будущие данные `ObservationPoint`, но ещё не является research record и может
быть прервана без создания точки.

Экран подготовки не содержит выбора меток: метка выбирается при первом вылете,
а не заранее.

Пользователь выполняет действие `Добавить`. Приложение одной Room-транзакцией
создаёт `ObservationPoint` с неустановленным результатом присутствия и
открывает экран «Наблюдение». Реальные пчёлы при этом не создаются.

Если после проверки точки пчёлы не найдены, на экране подготовки доступен явный сценарий:

```text
Пчёлы отсутствуют
        ↓
явное подтверждение пользователя
        ↓
ObservationPoint + NO_BEES_FOUND + completed_at сохраняются одной транзакцией
        ↓
возврат к карте текущей Territory
```

Перед сохранением приложение объясняет, что точка останется историческим наблюдением и будет завершена. Отмена подтверждения ничего не изменяет. Действие доступно только пока результат присутствия не установлен и Bee ещё не созданы.

Этот сценарий доступен и из подготовки точки до `Добавить`, и на открытом наблюдении, пока на точке нет ни одной Bee.

После успешного сохранения активной ObservationPoint больше нет: перезапуск не возвращает пользователя к ней, и можно создать следующую точку. После `NO_BEES_FOUND` Bee в завершённую ObservationPoint не создаются.

# 15. Варианты метки на экране наблюдения

Экран наблюдения выводит доступные варианты метки как производное значение:
5 цветов каталога × `NONE` / `RIGHT_WING` / `LEFT_WING` — 15 вариантов, минус
метки уже существующих реальных пчёл.

Например:

```text
☐ Белая (Грудь)
☐ Белая КП
☐ Белая КЛ

☐ Синяя (Грудь)
☐ Синяя КП
☑ Синяя КЛ — уже улетела

☐ Жёлтая (Грудь)
☐ Жёлтая КП
☐ Жёлтая КЛ
```

Вариант не является пчелой: он не хранится, не отображается как карточка Bee и
не расходует лимит пчёл. Внутреннее значение `NONE` показывается пользователю
как `Грудь`.

Карточка варианта имеет серый фон, состояние `Выбор` и действие `УЛЕТЕЛА`.

Варианты всегда располагаются ниже карточек реальных пчёл, поэтому уже
зарегистрированные пчёлы остаются на виду.

Граница `В полёте` / `На точке` служит зоной внимания: в полёте карточки
сортируются по времени полёта по возрастанию, а на точке — по времени нахождения
по убыванию. Номер `FlightCycle` на порядок карточек не влияет.

---

# 16. Регистрация первого вылета

Пользователь наблюдает за точкой и при фактическом вылете конкретной пчелы
нажимает `УЛЕТЕЛА` в карточке её метки.

Приложение одной Room-транзакцией:

1. фиксирует текущее время как индивидуальное время вылета этой Bee;
2. создаёт реальную Bee с выбранной меткой;
3. создаёт её `FlightCycle 1`;
4. устанавливает `BEES_FOUND`, если он ещё не установлен.

После этого карточка реальной Bee занимает место выше вариантов и показывается
как существующая пчела со своим состоянием и таймером:

```text
БЕЛАЯ
В полёте
00:03
[ ПРИЛЕТЕЛА ]

[ СИНЯЯ — Выбор — УЛЕТЕЛА ]
```

Метка, использованная реальной Bee, больше не предлагается как вариант.

Каждая пчела вылетает в свой момент, поэтому индивидуальное время вылета
фиксируется отдельно для каждой из них. Одна `ObservationPoint` содержит не
более 10 реальных пчёл; при достигнутом лимите оставшиеся варианты показаны, но
недоступны.

---

# 17. Локальная отмена ошибочно зарегистрированного первого вылета

Если первый вылет был зарегистрирован ошибочно, пользователь выбирает
локальную `↶` именно в карточке этой Bee, пока её первый цикл ещё открыт и для
него ни разу не был записан прилёт.

Приложение одной транзакцией удаляет и ошибочно созданный `FlightCycle 1`, и
саму Bee. Метка снова становится доступным вариантом, а результат присутствия
возвращается в неустановленное состояние, если на точке не осталось ни одной
Bee. Остальные пчёлы и их циклы не меняются.

---

## 17.1. Bee уже прилетала

После реального `Прилетела` эта correction больше не доступна, и Bee этим
действием не удаляется. Последующая отмена прилёта такую возможность не
возобновляет.

Когда такая Bee действительно улетает снова, обычное действие следующего вылета
создаёт её следующий FlightCycle.

---

# 18. Азимут первого вылета

Во время первого вылета пчёлы обычно выполняют ориентировочный облёт.

Надёжно определить направление их дальнейшего движения часто невозможно.

Поэтому азимут первого вылета:

* не является обязательным;
* не должен автоматически назначаться;
* его отсутствие является нормальным состоянием данных.

---

# 19. Состояние сразу после первого вылета

Экран наблюдения остаётся открытым; отдельный переход не требуется.

Например:

```text
БЕЛАЯ
В полёте
00:00
[ ПРИЛЕТЕЛА ]
```

Для каждой пчелы может отображаться увеличивающаяся продолжительность текущего отсутствия.

---

# 20. Основной рабочий экран

Это наиболее важный экран приложения во время наблюдения.

Пользователь большую часть времени должен иметь возможность оставаться на нём.

На экране одновременно представлены все активные пчёлы.

Для каждой пчелы показываются как минимум:

* метка;
* текущее состояние;
* живой таймер текущего состояния: от вылета для Bee в полёте либо от возвращения для Bee на точке;
* следующее допустимое действие.

Интерфейс должен позволять быстро найти нужную пчелу по визуальной метке.

Большая часть списка активных пчёл должна быть доступна без сложной навигации. Интерфейс не должен вводить отдельный числовой предел помимо доступных уникальных сочетаний меток.

---

# 21. Возвращение пчелы

Допустим, одновременно находятся в полёте:

```text
Белая
Синяя
Жёлтая КП
```

Хотя белая была первой в списке, раньше возвращается синяя.

Пользователь не должен завершать наблюдение белой или переключать приложение в строгой последовательности.

Он сразу нажимает:

```text
Синяя → ПРИЛЕТЕЛА
```

Приложение:

1. фиксирует текущее время;
2. записывает его как время возвращения синей пчелы;
3. вычисляет продолжительность её цикла;
4. переводит синюю пчелу в состояние `вернулась`;
5. оставляет остальные пчёлы без изменений.

---

# 22. Независимость состояний пчёл

Каждая пчела имеет собственное состояние.

Например:

```text
Белая       В ПОЛЁТЕ       08:41
Белая КП    НА ТОЧКЕ       06:13
Белая КЛ    В ПОЛЁТЕ       07:58
Синяя       НА ТОЧКЕ       05:22
Синяя КП    В ПОЛЁТЕ       08:02
```

Действие с одной пчелой не должно изменять состояние других.

Это является фундаментальным требованием рабочего процесса.

---

# 23. Повторный выпуск

После возвращения пчела может снова получить сироп и быть выпущена.

Пользователь выбирает соответствующую пчелу и выполняет действие:

**Улетела**

Приложение:

1. создаёт новый цикл;
2. фиксирует текущее время вылета;
3. переводит пчелу в состояние `в полёте`;
4. сохраняет предыдущий цикл без изменений.

Например:

```text
Синяя

Цикл 1
09:34:12 → 09:39:27
5:15

Цикл 2
09:41:08 → ...
```

# 24. Регистрация азимута

Во время активного наблюдения карточка Bee показывает live-направление верхней короткой стороны
телефона только для текущего открытого FlightCycle, если его `azimuth_deg` ещё отсутствует.
Дополнительно persisted `azimuth_capture_consumed` этого цикла должен быть `false`.

В таком случае он:

1. направляет верх телефона в наблюдаемую сторону ухода Bee;
2. видит текущее true/geographic heading, например `247°`;
3. один раз нажимает на значение;
4. приложение сохраняет его в явный последний FlightCycle этой Bee;
5. атомарно помечает полевую возможность этого FlightCycle использованной;
6. сохранённое число перестаёт изменяться вслед за поворотом телефона, а control становится
   read-only.

После `Прилетела` FlightCycle закрыт, поэтому azimuth control остаётся на месте, но становится
read-only: он показывает сохранённый азимут закрытого цикла либо `—°`. После `Улетела` persisted
состояние содержит новый открытый FlightCycle, и control снова показывает live heading и принимает
one-tap фиксацию.

Например:

```text
247°
```

Sensor heading сначала является магнитным. `HeadingProvider` корректирует его через
`GeomagneticField`, используя подтверждённые координаты ObservationPoint, системное время каждого
вычисления и высоту `0 м`, поскольку отдельная высота в текущей модели отсутствует. В Room попадает
только скорректированный истинный / географический азимут.

После успешной фиксации вверху экрана примерно на три секунды появляется `ОТМЕНИТЬ`. Оно очищает
азимут только этого FlightCycle, но не возвращает возможность повторной фиксации: control показывает
`—°` и остаётся disabled даже после restart. Более новая фиксация другого FlightCycle заменяет
предыдущий Undo-контекст. Постоянное редактирование и ручной числовой ввод на активном полевом экране
отсутствуют; repository-возможность изменить или удалить ненадёжное значение сохраняется для
будущего history/edit workflow.

---

# 25. Вылет без азимута

Пользователь может не успеть определить направление.

В таком случае он просто регистрирует:

**Улетела**

без азимута.

Цикл остаётся полностью допустимым.

Приложение не должно:

* требовать измерить направление;
* задерживать регистрацию времени;
* автоматически подставлять предыдущее значение;
* использовать `0°` вместо отсутствующего значения.

---

# 26. Ошибочный азимут

После фиксации пользователь может решить, что измерение было ненадёжным.

Например:

* пчела изменила направление;
* пользователь неправильно направил телефон;
* компас был нестабилен;
* рядом находился источник магнитных помех.

На active observation screen icon-only `↶` показывается в карточке конкретной Bee,
если её последнее действие ещё можно однозначно и безопасно скорректировать.
Для азимута оно удаляет значение, но сохраняет использованной однократную
возможность этого FlightCycle.

Постоянное удаление позднее может быть доступно через отдельный history/edit workflow, где
пользователь открывает соответствующий цикл и выбирает:

**Удалить азимут**

После этого значение отсутствует.

Время вылета и остальные данные цикла сохраняются.

Такой history/edit UI в текущий active observation milestone не входит.

---

# 27. Окно полевой фиксации азимута

Регистрация времени вылета имеет более высокий приоритет, чем работа с компасом.

Поэтому интерфейс не должен заставлять пользователя задерживать регистрацию события ради азимута.

На рабочем экране азимут можно добавить одним быстрым нажатием только к текущему открытому
FlightCycle Bee в состоянии `В полёте`. Возможность однократна для конкретного вылета. После
успешной фиксации повторный capture запрещён; Undo удаляет ошибочное значение, но не даёт второй
попытки. Локальная отмена `Прилетела` снимает только последний `return_time` и
возвращает Bee к исходному текущему вылету. Локальная отмена `Улетела` удаляет
только новый открытый повторный FlightCycle, возвращая Bee к исходному времени
возвращения предыдущего цикла. Более ранние закрытые FlightCycle этим UI не
редактируются.

Отдельное исключение существует только для ошибочно приписанного открытого
первого группового FlightCycle Bee, которая фактически не улетела: локальная
`↶` удаляет этот цикл до первого `Прилетела`, не создавая фиктивного результата.

Следующее `Улетела` создаёт новый FlightCycle и новую однократную возможность. Действия `Прилетела`
и `Улетела` не создают и не требуют азимут автоматически.

---

# 28. Несколько событий подряд

Интерфейс должен учитывать ситуацию, когда события происходят почти одновременно.

Например:

```text
09:41:10 — вернулась Белая
09:41:14 — вернулась Синяя КП
09:41:20 — улетела повторно Белая
09:41:27 — вернулась Жёлтая
```

Каждое действие должно выполняться независимо и требовать минимального количества операций.

После регистрации события приложение должно возвращать пользователя к общему рабочему экрану, а не оставлять его глубоко внутри карточки одной пчелы.

---

# 29. Ошибочное нажатие

Полевой интерфейс должен учитывать случайные нажатия.

Пользователь должен иметь возможность исправить ошибочно зарегистрированное событие.

При этом исправление не должно быть настолько лёгким, чтобы событие можно было случайно удалить одним касанием.

Предпочтительная схема:

```text
обычное нажатие → регистрация события
локальное `↶ Отменить` в той же карточке Bee → correction последнего действия
```

После более позднего действия отмена шага становится недоступной, пока не будут
отменены более новые обратимые действия той же Bee. Действия других Bee не
изменяются.

---

# 30. Пчела не вернулась

Если пчела не возвращается, пользователь продолжает работать с остальными пчёлами.

Такая пчела остаётся в состоянии `в полёте`.

Она не должна блокировать:

* регистрацию других возвращений;
* повторные выпуски;
* завершение работы на точке.

При завершении наблюдения приложение должно позволить оставить её цикл без времени возвращения.

---

# 31. Завершение наблюдения

Когда пользователь решает закончить работу на данной точке, он выбирает:

**Завершить наблюдение**

Обычное завершение доступно только после явного установления результата присутствия пчёл. Оно не должно молча завершать точку, если результат ещё не установлен. Отдельный сценарий `Пчёлы отсутствуют` одновременно сохраняет `NO_BEES_FOUND` и завершает точку.

Если существуют пчёлы, которые всё ещё числятся в полёте, приложение предупреждает об этом.

Например:

```text
Наблюдение ещё не завершено для:

Белая КЛ
Синяя

Завершить наблюдение всё равно?
```

Пользователь может:

* вернуться к наблюдению;
* подтвердить завершение.

Подтверждение не создаёт фиктивного времени возвращения.

---

# 32. Автоматическое сохранение

Все значимые действия должны сохраняться сразу после выполнения.

Например, после нажатия `Прилетела` запись должна быть сохранена до выполнения следующего пользовательского действия.

Не следует рассчитывать только на общую кнопку сохранения в конце наблюдения.

Это снижает риск потери данных при:

* случайном закрытии приложения;
* разрядке телефона;
* сбое приложения;
* перезагрузке устройства.

---

# 33. Восстановление после закрытия приложения

Если приложение было закрыто во время активного наблюдения, при следующем запуске пользователь должен иметь возможность продолжить работу.

Должны быть восстановлены:

* территория;
* точка;
* набор активных пчёл;
* состояния пчёл;
* времена текущих вылетов;
* предыдущие циклы;
* зарегистрированные азимуты.

Продолжительность текущего полёта вычисляется из сохранённого времени вылета и текущего времени, а не зависит от непрерывно работающего таймера.

---

# 34. Просмотр сохранённых точек

Из нижней панели основной карты пользователь открывает
`Объекты → Точки наблюдения`. `Объекты` — каталог режимов просмотра, а не
domain entity и не точка входа в создание. Settings не содержит Points Browser.
Рядом с точками `Объекты` содержит режим `Ареал`: он показывает единственный Ареал
текущей Territory — название, число участков и общую площадь — и предлагает
`Посмотреть на карте`, `Отправить ареал` и `Удалить ареал`. Создание Ареала
начинается не здесь, а в редакторе покрытия на карте, где первое `Готово` спрашивает
название.
Раздел использует текущую Territory и показывает карту или компактную таблицу
одной и той же выборки ObservationPoint. По умолчанию выбран последний доступный
год; пользователь может выбрать другой имеющийся год или `Все годы`. Переключение
`Карта` / `Таблица` не меняет фильтр или набор точек.

На карте маркеры различают `BEES_FOUND`, `NO_BEES_FOUND` и активную точку без
окончательного результата. Нажатие маркера показывает номер или код, дату и время,
результат и число Bee; действие `Открыть` ведёт к просмотру точки. Таблица показывает
те же точки от новых к старым: номер, дату, время, результат, число Bee и число
завершённых FlightCycle. Нажатие строки открывает тот же просмотр.

Просмотр ObservationPoint доступен только для чтения. Он показывает Territory,
номер и код, время создания, координаты, сохранённую точность GPS, Observer и
persisted результат. Далее для каждой Bee показываются метка и FlightCycle по
`sequence_number`: departure time, return time завершённого цикла, вычисленная
длительность и сохранённый азимут. Цикл без `return_time` явно обозначается открытым.
Точка `NO_BEES_FOUND` открывается как полноценное наблюдение с нулём Bee; nullable
результат не подменяется значением `NO_BEES_FOUND`.

Приложение показывает сводку наблюдения.

Например:

```text
Точка 12
26.08.2026

Белая
  цикл 1   05:15
  цикл 2   04:48   127°
  цикл 3   05:02   132°

Белая КП
  цикл 1   06:41
  цикл 2   не вернулась

Синяя
  цикл 1   04:57
```

Точный внешний вид определяется позднее.

Сохранённые абсолютные моменты событий отображаются в текущем часовом поясе устройства. Отдельный часовой пояс ObservationPoint в MVP не хранится.

История отделяет точки по сохранённому `observation_year` и различает
`BEES_FOUND`, явно подтверждённый `NO_BEES_FOUND` и отсутствие окончательного
результата.

Пользователю не требуется читать JSON или содержимое внутренней базы данных.

---

# 35. Работа с несколькими точками

После завершения наблюдения пользователь возвращается к карте текущей территории.

Он может:

* просмотреть существующую точку;
* перейти в другое место;
* создать новую точку;
* начать новое наблюдение.

Новая точка получает собственные координаты и собственный набор наблюдений.

Пчёлы одной точки не должны автоматически переноситься в другую точку.

---

# 36. Работа без интернета

Offline readiness означает, что выбранная область была явно подготовлена и
полностью сохранена на устройстве. Это не отдельный режим карты.

Типичный сценарий:

```text
Дома / при наличии интернета

Открыть обычную карту Territory
→ сформировать coverage из прямоугольных фрагментов
→ Подготовить для офлайн
→ дождаться Ready

              ↓

В поле / связи нет

Запустить приложение
→ автоматически открыть текущую территорию
→ использовать ранее загруженную карту
→ создать точку
→ подготовить пчёл
→ провести наблюдение
→ сохранить результаты
```

Недоступность сервера или мобильной сети не должна прерывать этот процесс.

Если необходимые картографические данные не были подготовлены, приложение
должно явно предупредить, что гарантированной карты нет. Исследовательский
workflow остаётся доступен; за пределами Ready coverage карта без сети может
быть неполной.

---

# 37. Будущая синхронизация

Когда соединение доступно, приложение в дальнейшем должно иметь возможность синхронизировать локальные данные с сервером.

С точки зрения пользователя предполагаемый сценарий:

```text
Полевое наблюдение
        ↓
Локальное сохранение
        ↓
Появление сети
        ↓
Синхронизация
        ↓
Данные доступны на ПК
```

Пользователь не должен вручную экспортировать JSON для обычной синхронизации.

Точная модель синхронизации определяется отдельно.

---

# 38. Приоритет действий в полевом интерфейсе

При проектировании интерфейса следует исходить из следующего порядка важности:

1. не пропустить событие;
2. правильно определить пчелу;
3. точно зафиксировать время;
4. при возможности определить азимут;
5. показать дополнительную информацию;
6. выполнить административные действия.

Если дополнительная функция мешает быстро зарегистрировать возвращение или вылет, она должна быть вынесена из основного пути.

---

# 39. Основной UX-принцип

Во время активного наблюдения пользователь должен работать преимущественно с **одним общим экраном**, а не постоянно открывать и закрывать карточки отдельных пчёл.

Основная единица взаимодействия — компактная строка или карточка активной пчелы.

Она должна позволять быстро ответить на три вопроса:

```text
Кто это?
Что с ней сейчас?
Что я могу нажать?
```

---

# 40. Что требует полевого прототипирования

Следующие решения нельзя считать окончательными без испытания интерфейса в реальной работе:

* размер карточки пчелы;
* расположение кнопок `Улетела` и `Прилетела`;
* способ визуального отображения цвета метки;
* способ обозначения `КП` и `КЛ`;
* необходимость постоянного отображения секундомера;
* звуковая или вибрационная обратная связь после фиксации события;
* необходимость подтверждения обычных событий;
* способ отмены ошибочного события;
* порядок регистрации азимута;
* возможность работы одной рукой;
* удобство интерфейса при ярком солнечном освещении;
* максимально удобное количество одновременно видимых пчёл;
* допустимый объём офлайн-карты одной территории;
* поведение при неполной загрузке карты;
* практическая разница source z15 и z16 на целевом Samsung.

Эти вопросы должны решаться не только теоретически, но и посредством раннего рабочего прототипа на реальном телефоне.

---

# 41. Первый прототип пользовательского потока

Первая версия интерфейса должна позволить проверить следующий минимальный сценарий:

```text
Если территория ещё не создана:
создать территорию
        ↓
Открыть текущую территорию
        ↓ optional до поля
сформировать coverage из rectangles и подготовить его для офлайн
        ↓
Создать или выбрать current Observer и current Territory
        ↓
Создать точку на карте
        ↓
При необходимости скорректировать GPS
        ↓
Подтвердить точку и открыть наблюдение
        ↓
Нажать «УЛЕТЕЛА» в карточке метки улетевшей пчелы
        ↓
Увидеть карточку этой пчелы в состоянии «В полёте»
        ↓
Нажать «Прилетела» у произвольной пчелы
        ↓
Повторно нажать «Улетела»
        ↓
При желании сохранить азимут
        ↓
Продолжать работу с остальными пчёлами
        ↓
Завершить наблюдение
        ↓
Открыть сохранённый результат
```

До реализации сложной аналитики, серверной синхронизации и дополнительных функций этот поток должен быть проверен в реальной полевой работе.

# 42. Помощь и управление данными

Встроенная помощь открывается из настроек, доступна без сети и содержит краткий
старт и раскрываемые подробные разделы по текущему полевому процессу.

Полевой процесс офлайн-карты описан в помощи отдельными разделами: `Создание
участка офлайн-карты` объясняет выбор участка и действия редактора вплоть до
`Готово` и поведения `Back` при несохранённых изменениях, а `Загрузка
офлайн-карты` объясняет пару файлов, двухшаговый импорт, переключение источника
карты и типичные отказы, включая отказ по неполному покрытию. Названия действий в
помощи совпадают с фактическим интерфейсом.

Экспорт выполняется так:

```text
Настройки → Данные → Экспортировать данные
        ↓
системный выбор места и имени файла
        ↓
создание logical backup-архива
        ↓
сообщение об успехе или ошибке
```

Экспорт не удаляет данные и не отправляет файл автоматически.

Выборочное удаление выполняется так:

```text
Настройки → Данные → Удалить отдельную точку
        ↓
выбрать завершённую ObservationPoint по территории, дате и номеру
        ↓
подтвердить удаление этой точки, её Bee и FlightCycle
```

Активная незавершённая точка в список не входит. Отмена подтверждения ничего не
изменяет; после удаления остальные ObservationPoint, Territory, Observer,
текущий выбор и карты сохраняются.

Очистка наблюдений выполняется только после диалога, который показывает число
точек, пчёл и циклов, сообщает о необратимости и о том, что автоматического
экспорта нет. Отмена диалога ничего не изменяет. После подтверждения точки,
пчёлы и циклы удаляются одной транзакцией; Territory, Observer, текущий выбор и
карты сохраняются, а удалённая активная точка больше не восстанавливается при
запуске.

# 43. Каталог обмена файлами

Bee Search использует один предсказуемый каталог обмена в общем хранилище
устройства, чтобы файлы не приходилось искать среди случайных файлов в загрузках.
Каждая сборка приложения работает только со своей веткой каталога, поэтому Stable,
Beta и Dev не смешивают файлы:

```text
Download/BeeSearch/Stable/Exchange/
Download/BeeSearch/Beta/Exchange/
Download/BeeSearch/Dev/Exchange/
```

Внутри каталога обмена:

```text
Areas
OfflineMaps
Data
```

`OfflineMaps` содержит готовые офлайн-карты — пару `*.pmtiles` и
`*.pmtiles.manifest.json`. `Data` содержит экспортированные данные Bee Search.
`Areas` подготовлен для файлов участков; формат файла участка появится отдельной
задачей, а до тех пор участки хранятся внутри приложения.

Пользователь может положить свою пару файлов в `OfflineMaps` заранее и затем
импортировать её обычным способом: при импорте приложение открывает системный
проводник в этом каталоге и показывает ожидаемое имя файла карты. Выбор файла
всегда подтверждает пользователь, поэтому приложение не запрашивает широкие
разрешения на файловую систему. Если система не открывает проводник сразу в
каталоге обмена, приложение показывает точный путь текстом на экране.

Экспорт данных предлагает сохранить архив в `Data` этого же варианта. Имя и место
по-прежнему подтверждает пользователь, а формат архива не меняется.

Каталог обмена — не внутреннее хранилище приложения. Room DB, настройки, кэш и
установленная копия офлайн-карты остаются внутри приложения. Импортированная карта
продолжает работать без сети после удаления или перемещения её исходной пары из
каталога обмена, а удаление файла из каталога не удаляет данные наблюдений.

# Unified Territory Data Map — панель «Данные на карте» и фильтры по типам, второй макет

Статус: PROPOSAL · не утверждено · ожидает решения владельца

## Контракт

Один дизайн-контракт образуют четыре файла:

| Файл | Содержимое |
|---|---|
| `unified-territory-layers-v2.png` | кадры A–D: карта по умолчанию, панель «Данные на карте», экран типа (уровень «Год»), результат с активным фильтром |
| `unified-territory-layers-v2-calendar.png` | кадры E, F, C2: уровни «Месяц» и «День», и второй тип со своими значениями |
| этот MD | семантика, подписи, состояния и поведение |
| `unified-territory-layers-v1.png` + `.md` | **сохраняются без изменений** как неутверждённая первая попытка; V2 не переписывает V1 и не отменяет его |

PNG задаёт композицию, плотность и расположение; MD — семантику, состояния и поведение. При
существенной неоднозначности решение не додумывается, а запрашивается у владельца. Pixel-perfect не
требуется, если он ломает Android accessibility, системные inset или адаптивность.

Макет — вариант дизайна, а не production-требование и не разрешение менять принятые решения.

Имя файлов — идентификатор итерации фичи (`unified-territory-layers`, версия 2), а не название
функции в UI: функция в панели называется «Данные на карте».

## Что изменилось относительно V1

Два замечания владельца определили V2.

| Тема | V1 (не утверждено) | V2 |
|---|---|---|
| Точка входа управления отображением | отдельная подписанная пилюля `Слои` в нижнем левом стеке, над селектором источника карты | третье действие в существующей нижней панели, рядом с `Объекты` и `Настройки`; ничего нового над картой не появляется |
| Модель периода | один общий календарный диапазон на все типы | у каждого типа свой период и своя точность; типы независимы |
| Форма периода | строка значения + shortcuts `Всё время` / `Текущий год` / `Текущий сезон` | экран типа с явной точностью `Год` → `Месяц` → `День`; shortcuts-пресеты убраны, вместо них уровень «Год» |
| Дополнительные фильтры | общий период | раздел периода у каждого типа; место под другие фильтры типа зарезервировано пунктирным блоком |
| Индикация активного фильтра | активный вид пилюли + точка-индикатор + чип `Период: …` в статусной колонке | только точка-индикатор на действии в нижней панели; глобальный чип периода на карте убран |
| Источник карты | остаётся отдельным контролом | без изменений |

Отдельно учтено, что замечание владельца про «один общий набор фильтров» относится не только к
периоду: макет сразу разводит периоды по типам (кадр C против кадра C2) и оставляет каждому типу
место для собственных будущих фильтров.

## Внешнее исследование

Смотрелись приложения полевого сбора данных и картографические приложения общего назначения. Цель —
не копировать, а понять, какие решения для «какие данные показаны» и «за какой период» уже
существуют, и где проходит граница между общими и типовыми фильтрами.

| Приложение | Что смотрели | Что берём / что отклоняем | Где смотрели |
|---|---|---|---|
| ArcGIS Field Maps (Esri) | список слоёв карты, включение/выключение видимости, фильтрация по дате | берём: видимость слоя — быстрое действие в списке слоёв карты, отдельно от настроек карты. Отклоняем: фильтр задаётся в веб-карте и живёт как свойство слоя, а не как полевое действие; в вопросах сообщества именно фильтр слоя по дате приходится настраивать вне мобильного клиента | `community.esri.com` — ArcGIS Field Maps questions, «Layer Filter by Date in Field Maps» (m-p/1598313, m-p/1672870); Esri France, «Gérer l'affichage des couches»; Field Maps Early Access update (блог Esri) |
| QField (QGIS) | фильтрация и стилизация слоя, «tip filter» | берём: фильтр относится к конкретному слою, а не ко всей карте. Отклоняем: выражение/атрибутный фильтр как основной полевой UI — слишком тяжёл для перчаток и солнца | `docs.qfield.org` — «Map styling and configuration»; QField GitHub Discussions #6126 «Tip Filter in QFIELD» |
| SW Maps | группы слоёв, видимость, работа с растровыми подложками | берём: видимость и подложка — разные вопросы и разные контролы. Отклоняем: перегруженный список слоёв с техническими названиями | SW Maps Manual V3.0 (`aviyaantech.com/SwMaps/assets/SW%20Maps%20Manual%20V3.0.pdf`) |
| OsmAnd | дерево «Configure map» с десятками переключателей | берём: подписанный заголовок раздела данных. Отклоняем: длинный плоский список опций — не для частого полевого действия | OsmAnd map configuration (обзор DeepWiki по `osmandapp`) |
| Google Maps / Google Earth | стили карты, слои, фильтры мест | берём: управление отображением не занимает карту постоянно и открывается по требованию. Отклоняем: «слои» как набор чужих предустановленных оверлеев — не наш случай | `maps.google.com`, Google Earth help, Material Symbols (`fonts.google.com/icons`) |
| QGroundControl-подобные полевые приложения | компактные нижние панели действий как основная навигация по разделам | берём: главные разделы живут в нижней панели, а не плавающими кнопками над картой | обзоры плана полевого ПО (QGroundControl user guide, `docs.qgroundcontrol.com`) |

Итог исследования: во всех рассмотренных приложениях (1) видимость данных и выбор подложки — разные
контролы; (2) фильтр относится к конкретному слою/типу, а не ко всей карте; (3) управление
отображением не держится на карте постоянно. V2 следует всем трём выводам.

## Точка входа в управление отображением

Замечание владельца: отдельная крупная кнопка над селектором источника карты выглядит плохо и
занимает карту. Решение V2 — **третье действие в существующей нижней панели**.

Рассматривались три кандидата:

| Кандидат | Плюс | Минус |
|---|---|---|
| `visibility` (глаз) + заголовок «Данные на карте» — **выбран** | прямо говорит «что показано на карте»; не путается с фильтром-воронкой; понятен без обучения | глиф глаза иногда читают как «скрыть всё» |
| `tune` (ползунки) | читается как «настройка отображения» | визуально близок к шестерне `Настройки` рядом — два похожих контрола подряд |
| `filter_list` (воронка-список) | читается как «фильтры» | обещает фильтры, а действие открывает ещё и видимость; уже занято смыслом «фильтр точек» в других экранах |

Нижняя панель остаётся тем же `Surface(tonalElevation = 3.dp)`, высота 56 dp, три 48 dp `IconButton`
с `Arrangement.End`. Слева направо: `Объекты`, действие отображения, `Настройки`. Порядок внутри
существующего идиома не меняет смысла `Объекты` и `Настройки`.

Селектор источника карты (`Онлайн карта` / `Векторная карта`, в DEV также `Спутник Sentinel` /
`Гибрид`) остаётся **отдельным** контролом с существующей позицией и существующим
`contentDescription` «Источник карты»: это разные вопросы («какая подложка» и «какие данные
показаны»), и технические источники не должны становиться пунктами пользовательского списка данных.
Объединение возможно только при конкретной UX-причине и отдельном решении.

## Кадры

### A — Карта по умолчанию

Ничего в существующем экране не меняется: статусная колонка вверху слева (`DEV`, точность, `z`),
GPS-точка, красная точка центра, направляющая линия GPS → центр, контролы внизу справа, селектор
источника карты внизу слева. В нижней панели три действия; **точка-индикатор на действии не горит**.

На карте показаны все четыре доступных типа данных и записи всех периодов: точки наблюдения
(круги трёх тонов, включая точки прошлого сезона), дупла (ромбы), колоды (скруглённые квадраты),
пасеки (шестиугольники).

### B — Панель «Данные на карте»

Контейнер — modal bottom sheet от середины экрана: drag handle, заголовок `Данные на карте`, `✕`
справа. Карта остаётся видимой сверху и затемняется — состояние карты видно при изменении настроек.

Разделы и строки:

- `ИССЛЕДОВАТЕЛЬСКИЕ ДАННЫЕ`
  - `Точки наблюдения` — switch включён, период `2026` (primary-цвет), шеврон `›`;
  - `Дупла` — switch выключен, период `авг–сен 2026` (muted), шеврон `›`;
  - `Колоды` — switch включён, `всё время` (muted), шеврон `›`;
  - `Пасеки` — switch включён, период `2024–2026` (primary-цвет), шеврон `›`;
  - `Осмотры` — недоступная строка с muted-пояснением `позже`.
- нижние действия: `Сбросить фильтры` (текстовая, не destructive) и `Готово` (filled).

Анатомия строки типа: `switch видимости` · `название типа` · `сводка периода` · `шеврон`.
Сводка и шеврон — разные вещи: switch отвечает на вопрос «рисовать ли этот тип», шеврон открывает
экран фильтров этого типа. Тап по названию не делает ничего скрытого: видимость меняется только
switch-ем.

### C — Экран типа «Точки наблюдения», уровень «Год»

Тот же контейнер, заголовок — имя типа, слева стрелка назад `‹`. Один sheet с внутренними уровнями
(панель → тип → точность), а не отдельный экран навигации: пользователь не теряет контекст карты и
возвращается одним жестом «назад».

- раздел `ПЕРИОД`: строка значения `Период | 2026 ›`;
- переключатель точности `Год | Месяц | День`, выбран `Год`;
- список лет: `Всё время`, `2026` (выбран), `2025`, `2024`;
- пояснение: `Точки фильтруются по дате наблюдения.`;
- пунктирный блок `Здесь появятся другие фильтры этого типа`;
- нижние действия: `Сбросить период` и `Готово`.

### D — Результат с активным фильтром

Панель закрыта. На карте — только включённые типы и только записи внутри их периодов: точки внутри
`2026`, колоды, пасеки; дупла отсутствуют, как и точки прошлого сезона. Точка-индикатор на действии
отображения горит.

Кадр D — тот же экран, что кадр A, с включёнными фильтрами: разница между A и D и есть результат
работы фильтров.

### E — Уровень «Месяц» («Точки наблюдения»)

Строка значения `авг–сен 2026`, точность `Месяц`, заголовок года со стрелками `‹ 2026 ›`, сетка
12 месяцев, выбраны `авг` и `сен`. Пояснение: `Несколько месяцев подряд дают период от начала первого
до конца последнего.` Нижние действия как на кадре C.

### F — Уровень «День» («Точки наблюдения»)

Строка значения `10.08.2026 — 01.09.2026`, точность `День`, заголовок месяца `‹ август 2026 ›`,
шапка недели `Пн … Вс`, сетка месяца. Выбран день `10` (заполненный primary-круг), дни `11–31`
показаны как попадающие в диапазон. Пояснение: `Конец диапазона — 1 сентября; диапазон продолжается
в следующем месяце.` Нижние действия как на кадре C.

### C2 — Второй тип со своими значениями («Дупла»)

Заголовок `Дупла`, свой период `авг–сен 2026`, точность `Месяц`, те же выбранные месяцы, своё
пояснение `Дупла фильтруются по дате фиксации.` и свой зарезервированный блок.

Кадр C2 существует ровно для того, чтобы было видно: значения фильтров у типов независимы. Период
`авг–сен 2026` у дупел не означает и не требует такого же периода у точек, у которых стоит `2026`.

## Модель фильтрации по типам

| Строка панели | Сущность | Маркер на карте | Canonical research date (D094) | По умолчанию |
|---|---|---|---|---|
| `Точки наблюдения` | `ObservationPoint` | существующий круг с тоном `POSITIVE` / `NEGATIVE` / `UNRESOLVED` | дата наблюдения | включён, период `всё время` |
| `Дупла` | `Hollow` | ромб, коричневый | дата фиксации | включён, период `всё время` |
| `Колоды` | `LogHive` | скруглённый квадрат, коричневый | дата фиксации | включён, период `всё время` |
| `Пасеки` | `Apiary` | шестиугольник, синий | дата фиксации | включён, период `всё время` |
| `Осмотры` | будущий `Inspection` | — | дата осмотра | недоступна |

Правила модели:

1. **Видимость и период независимы для каждого типа.** Включение типа не сбрасывает и не задаёт его
   период; изменение периода не меняет видимость.
2. **У типа один период.** Период типа — один непрерывный интервал, а не набор интервалов.
3. **Период применяется к canonical research date этого типа**, а не к `created_at` и не к
   «существованию объекта в мире» (D094).
4. **Скрытый тип сохраняет свои фильтры.** Выключенный тип не теряет период: сводка остаётся на
   строке, но muted. Это видно на кадре B: `Дупла` выключены, а их `авг–сен 2026` сохранён.
5. **Обычный фильтр не является запросом о существовании.** В UI не вводится ни одного элемента
   вида «существовал / активен / подтверждён / существование неизвестно»: это отдельная будущая
   аналитическая задача, а не семантика обычного фильтра карты (D094 §3).
6. **Тип без записей не является ошибкой.** Пустой результат фильтра — не ошибка и не пустой экран
   с объяснением: это состояние карты, где маркеров типа нет.

`Осмотры` показывается недоступной строкой с пояснением `позже`: сущности ещё нет (D088, I009),
поэтому строка не выдаётся за работающую функцию и ничего не рисует на карте.

Форма маркера различает тип, тон различает состояние точки; цвет не является единственным носителем
смысла. Цвета объектов (коричневый для дупел и колод, синий для пасек) — предложение макета, а не
решение; тона точек остаются существующими (`#1B5E20`, `#C62828`, `#F9A825`).

## Календарь: Год → Месяц → День

Три уровня точности, выбор явный — приложение не угадывает точность по тому, что нажал пользователь.

| Точность | Что выбирается | Значение периода | Пример сводки |
|---|---|---|---|
| `Год` | один год из списка (`Всё время` снимает период) | 01.01 — 31.12 выбранного года | `2026` |
| `Месяц` | один месяц или несколько подряд в показанном году | от первого дня первого месяца до последнего дня последнего | `авг–сен 2026` |
| `День` | первый тап — начало, второй тап — конец | точные даты; диапазон может пересекать границу месяца | `10.08.2026 — 01.09.2026` |

Правила:

- **Список лет** строится из годов, в которых есть записи этого типа (на макете `2024`, `2025`,
  `2026`). Если у типа записей нет, список пуст и доступен только `Всё время` — недоступных лет,
  ведущих в пустоту, не показывается. Это в предположениях макета.
- **Непрерывность месяцев.** Выбор месяцев — непрерывный ряд: тап по месяцу, соседнему с выбранным,
  продолжает ряд; тап по месяцу не рядом с рядом — начинает новый ряд вместо старого. Тип
  многоинтервальных периодов (например май и сентябрь одновременно) этим макетом **не вводится**:
  он требует другой модели фильтра (набор интервалов) и отдельного решения.
- **Снятие выбора.** Тап по единственному выбранному месяцу или по выбранному году снимает период и
  возвращает `Всё время`.
- **Точность «День»** не выводится автоматически из «Месяц» и обратно; переключение точности
  сохраняет текущее значение периода, а не сбрасывает его.
- **Время суток** в фильтр не входит: исследовательская дата — дата, а не момент времени.
- **Применение — live.** Изменение применяется сразу, отдельной кнопки `Применить` нет; `Готово`
  только закрывает панель и возвращает полевой экран. Немедленная обратная связь — сводка периода на
  строке типа, которая обновляется сразу; сама карта при открытом экране типа видна лишь полосой
  сверху.
- **Конкретный компонент не фиксируется.** Может быть Material3 `DatePicker`/`DateRangePicker` с
  обвязкой уровней или собственный календарь; макет задаёт модель точности и поведение, а не
  библиотеку. `DateRangePicker` сам по себе не даёт уровень «Год» и «несколько месяцев подряд», а
  `ExperimentalMaterial3Api` в проекте уже включён там, где это нужно.

## Одновременные периоды у разных типов

Пример состояния, которое обязано работать (это не набор отдельных экранов, а одна карта):

| Тип | Видимость | Период | Что видно на карте |
|---|---|---|---|
| Точки наблюдения | включён | `2026` | только точки 2026 года |
| Дупла | выключен | `авг–сен 2026` (сохранён) | ничего |
| Колоды | включён | `всё время` | все колоды |
| Пасеки | включён | `2024–2026` | пасеки за три года |
| Осмотры | недоступен | — | ничего |

## Индикация активного фильтра (пересмотр решения V1)

| | V1 | V2 |
|---|---|---|
| Отдельная пилюля/кнопка над картой | была | нет |
| Активный вид действия | тонированный фон + обводка + точка | точка-индикатор на действии |
| Чип периода в статусной колонке | был (`Период: 10.08 — 01.09.2026 ✕`) | **убран** |
| Где читаются конкретные значения | в чипе на карте | в панели, на строках типов |

Причины пересмотра: при периодах, независимых для каждого типа, единого значения периода на карте
больше не существует, а пять сводок в статусной колонке заняли бы ту самую карту, которую владелец
просил не занимать. Поэтому на карте остаётся минимальный признак «фильтры активны», а значения
читаются там, где живут типы.

Правила индикации:

- точка-индикатор горит, если скрыт хотя бы один доступный тип **или** хотя бы у одного типа период
  отличается от `всё время`;
- при состоянии по умолчанию (все доступные типы включены, у всех `всё время`) индикатора нет;
- состояние **не передаётся только цветом или точкой**: `contentDescription` действия называет его
  словами, например `Данные на карте. Скрыты: Дупла. Периоды: Точки наблюдения — 2026, Дупла —
  август–сентябрь 2026, Пасеки — 2024–2026`, а при отсутствии фильтров — `Данные на карте. Фильтров
  нет`;
- принятая цена решения: чтобы узнать точные диапазоны, нужно один тап и открыть панель. Это
  осознанный компромисс в пользу карты; если владелец сочтёт иначе, минимальная добавка — короткая
  сводка на строке действия, а не чип на карте.

## Сброс и видимость

Два разных сброса, и ни один из них не удаляет данные:

| Действие | Где | Что делает | Чего не делает |
|---|---|---|---|
| `Сбросить период` | экран типа, внизу | снимает период **только этого типа** → `всё время` | не меняет видимость типа и не трогает другие типы |
| `Сбросить фильтры` | панель, внизу | снимает периоды у всех типов → `всё время` | не меняет видимость: выключенные типы остаются выключенными |

Дополнительно: включение типа **не** сбрасывает его период; выключение типа **не** сбрасывает его
период. Сброс видимости как отдельное действие не вводится: включить скрытый тип — это один тап по
его switch, и такое действие понятнее, чем ещё одна кнопка «показать всё».

Исследовательские записи при любом сбросе не меняются, подтверждение не запрашивается, действие
визуально нейтральное (не destructive, без красного).

## Зарезервировано для будущих групп

I014 (пользовательские геопривязанные растры), I011 (GPX и пользовательская полевая геометрия),
I001 (аналитические слои) в этом макете **не показаны в UI**. Эти три группы остаются
зарезервированными: каждая станет отдельным разделом той же панели в том же порядке, что и в I016 —
подложка → пользовательские растры → пользовательские полевые данные → исследовательские данные →
аналитические overlays.

Пунктирный блок `Здесь появятся другие фильтры этого типа` на экране типа — **иллюстрация
расширяемости, а не production UI**. Он показывает, куда придёт будущий типовой фильтр (например
характеристики дупла или пасеки), и не должен реализовываться как пустой блок. По той же логике в
production-панели не показываются разделы, которых нет.

## Согласование с D094 — impact analysis

**Расхождение действительно есть, и оно не решается молча.**

D094 §3 говорит буквально:

> «Пользователь выбирает один календарный диапазон; каждый тип использует свою canonical research
> date из раздела 2.»

V2 требует обратного: диапазон задаётся **на тип**, и общей календарной рамки у карты нет.

Практическое следствие, если расхождение не устранить: D094 — ACCEPTED, поэтому исполнитель,
читающий §3 как ограничение, обязан сделать ровно один диапазон на все типы, и панель V2 окажется
несовместимой с принятым решением. При этом §1, §2, §4, семантика «обычный фильтр — не запрос о
существовании», mapping canonical research date по типам и правило про позднее внесение остаются
верными и в V2: меняется только фраза про один диапазон.

**Минимальная правка (предложение, НЕ применено):** переписать одно предложение §3, например:

> Каждый тип использует свою canonical research date из раздела 2, и календарный период задаётся
> для типа независимо от других типов; общий период для всех типов — частный случай, а не
> единственная модель.

Всё остальное в §3 (смысл запроса, запрет понятий существования/активности/подтверждённости,
следствие про `Hollow` / `LogHive` / `Apiary`) сохраняется дословно. Заголовок D094 уже говорит, что
решение «не меняет текущий UI и продуктовые требования к фильтру», поэтому правка §3 не выходит за
рамки самого решения и не требует отдельного нового решения; если владелец предпочтёт отдельное
решение, следующий свободный durable-номер — **D095** (`docs/decisions.md`, строка ~3093).

Документы, которые потребуют изменения **только после одобрения** (сейчас не изменены):

| Документ | Что именно | Комментарий |
|---|---|---|
| `docs/decisions.md` D094 §3 | предложение про один диапазон | минимальная правка выше; статус D094 остаётся ACCEPTED |
| `docs/ideas.md` I016 | `Temporal filtering`: «нужен один календарный диапазон … с быстрыми вариантами `всё время` / `текущий год` / `текущий сезон` / `свой период`» | формулировка и набор shortcuts не совпадают с V2 (уровни `Год`/`Месяц`/`День`); статус I016 остаётся `idea` |

## Согласование с I016

- Цель I016 (одна карта исследовательских данных с независимыми слоями) — реализуется без изменений
  смысла: панель даёт независимую видимость по типам.
- Общий механизм маркеров уже существует: `SavedObjectMarkers.kt` документирует, что добавление
  `Hollow`, `LogHive`, `Apiary` — это новая запись в `MapObjectType`, mapper и больше ничего, потому
  что overlay, обвязка карты и отрисовка уже работают по списку маркеров. Макет этому соответствует.
- Технические источники карты ≠ пользовательские слои (I016): селектор подложки остаётся отдельным,
  технические источники не попадают в список данных.
- `MapObjectTone` обязателен в `MapObjectMarker`; какой тон получают физические объекты — открытый
  технический вопрос реализации, макет его не решает.
- Идея I016 остаётся `idea`; этим макетом её статус не меняется.

## Сценарии

Обязательные сценарии, которые контракт должен выдерживать. «Показать» означает «на карте нет
маркеров этого типа», а не «маркеры скрыты визуально».

1. **ObservationPoint = 2026.** Панель → `Точки наблюдения` → `Год` → `2026`. Точки вне 2026 не
   показываются; видимость и периоды других типов не меняются.
2. **ObservationPoint = август 2026.** То же, точность `Месяц`, выбран `авг`. Значение —
   `авг 2026`, то есть 01.08.2026 — 31.08.2026.
3. **ObservationPoint = авг–сен 2026.** Точность `Месяц`, выбраны `авг` и `сен` подряд. Значение —
   `авг–сен 2026`, то есть 01.08.2026 — 30.09.2026, один интервал, а не два.
4. **ObservationPoint = 10.08.2026 — 01.09.2026.** Точность `День`, тап по `10` в августе, переход к
   сентябрю, тап по `1`. Диапазон пересекает границу месяца и остаётся одним интервалом.
5. **Смешанные периоды типов.** `Точки наблюдения` = `2026`, `Дупла` = `авг–сен 2026`, `Колоды` =
   `всё время`, `Пасеки` = `2024–2026` одновременно. Каждый тип фильтруется по своей canonical
   research date; значения не влияют друг на друга; состояние переживает закрытие и повторное
   открытие панели.
6. **Скрытый тип с сохранёнными фильтрами.** `Дупла` выключены, период `авг–сен 2026` сохранён и
   показан muted на строке. Повторное включение дупел возвращает ровно прежний период, а не
   `всё время`.

## Стоимость в жестах

Считаются жесты от карты до карты; закрытие панели — `Готово`, свайп вниз, системный «назад» или тап
по затемнению, то есть один жест.

| Задача | Жесты | Разбор |
|---|---|---|
| Скрыть `Дупла` | 3 | действие в нижней панели · switch `Дупла` · закрыть |
| `Точки наблюдения` = `2026` | 4 | действие · шеврон строки · `2026` · закрыть |
| `Точки наблюдения` = `авг 2026` | 5 | действие · шеврон · `Месяц` · `авг` · закрыть |
| `Точки наблюдения` = `авг–сен 2026` | 6 | действие · шеврон · `Месяц` · `авг` · `сен` · закрыть |
| `Точки наблюдения` = `10.08.2026 — 01.09.2026` | 7 | действие · шеврон · `День` · `10` · `›` (сентябрь) · `1` · закрыть |
| Вернуться к «без периодов» | 3 | действие · `Сбросить фильтры` · закрыть |

Точность по умолчанию — `Год`, поэтому самому частому полевому вопросу «этот сезон» соответствует
минимум жестов, а точные диапазоны стоят дороже осознанно.

## Доступность и полевые требования

- touch targets ≥ 48 dp: действие в нижней панели, строки типов, switch, шевроны, месяцы и дни
  календаря, обе нижние кнопки;
- состояние не передаётся только цветом: точка-индикатор дублируется словами в
  `contentDescription`, выключенный тип — не только цветом текста, но и значением switch;
- увеличенный системный `fontScale`: панель скроллится, длинные подписи переносятся, строки не
  ломаются по буквам; сетка месяцев при увеличенном шрифте перестраивается в меньшее число колонок;
- солнце и перчатки: один главный экран, крупные цели, никаких hover- и long-press-действий;
- постоянных контролов на карте не добавляется **ни одного**: точка входа живёт в существующей
  нижней панели, а V1-пилюля над картой удалена;
- карта остаётся читаемой: на экране карты от фильтров остаётся только точка-индикатор;
- research markers остаются Compose-маркерами с semantics и не переносятся в MapLibre (§73.3);
- offline: панель и календарь не требуют сети и не зависят от источника карты.

## Mockup assumptions (обратимые предположения)

1. Точка входа — третье действие в существующей нижней панели, глиф `visibility` (`Material
   Symbols`), заголовок панели `Данные на карте`.
2. Селектор источника карты остаётся отдельным контролом; в панель данных не переносится.
3. Контейнер — modal bottom sheet; панель от середины экрана, экран типа выше; изменения применяются
   live, `Готово` только закрывает.
4. По умолчанию все доступные типы включены, у всех период `всё время`.
5. Строка типа = `switch` · название · сводка периода · шеврон; видимость меняет только `switch`.
6. Период типа — один непрерывный интервал; многоинтервальные периоды не вводятся.
7. Список лет строится из годов, в которых есть записи этого типа.
8. Пояснения про canonical date: `Точки фильтруются по дате наблюдения.` /
   `Дупла фильтруются по дате фиксации.`
9. Активный фильтр показан только точкой-индикатором на действии; чип периода на карте убран.
10. `Пасеки` — обычный переключатель; `Осмотры` — недоступная строка `позже`.
11. Формы маркеров: круг (точки, тон не меняется), ромб, скруглённый квадрат, шестиугольник; цвета
    объектов — предложение макета.
12. Зарезервированные группы I014 / I011 / I001 в production-панели не показываются; пунктирный
    блок на экране типа — иллюстрация расширяемости, а не production UI.
13. Исследовательские маркеры рисуются на основном полевом экране (см. вопросы владельцу №2).
14. Пояснительные полосы под кадрами на PNG — комментарии к макету, а не часть UI.

## Открытые вопросы владельцу

1. **Точка входа.** Глиф `visibility` (глаз) с заголовком «Данные на карте» — или `tune`
   (ползунки), или `filter_list` (воронка)? И оставить ли действие третьим в нижней панели, как на
   макете?
2. **Маркеры на основном полевом экране.** Кадры A и D показывают, что исследовательские маркеры
   рисуются на основном полевом экране. Сейчас по I016 (раздел «Наблюдаемое состояние») маркеры
   показываются только в просмотре `Точки`. Подтверждаете, что основной полевой экран становится
   единой картой данных?
3. **Индикация.** Достаточно ли точки-индикатора на действии (как на макете), или нужна короткая
   сводка активных периодов рядом с действием?
4. **Период для объектов.** Выпускать период только для точек до появления fixation-date полей у
   `Hollow` / `LogHive` / `Apiary`, или панель и data-model изменение идут одним шагом?
5. **`Пасеки`.** Рабочий переключатель уже сейчас (как на макете) или тоже недоступная строка, пока у
   `Apiary` нет пользовательского жизненного цикла?

## Что макет не определяет

Окончательные названия и количество map modes; судьбу `ONLINE` / `VECTOR` / `SENTINEL`; финальный
набор и порядок кнопок нижней панели; конкретный компонент календаря; финальную графику и цвета
маркеров; правила порядка слоёв и z-order; performance limits; точный тон физических объектов в
`MapObjectMarker`; статус §73.3; schema, migration и реализацию; формулировки D094 и статус I016;
состав Help.

Фон карты на PNG — условная иллюстрация, а не выбор подложки: макет не назначает map mode по
умолчанию и не показывает конкретный источник как обязательный. Маркеры на кадрах — условная
иллюстрация состава данных, а не утверждение о количестве записей.

# Создание интерфейсов Bee Search

## Назначение
Процесс для новых и существенно перерабатываемых интерфейсов Bee Search: сначала согласовать интерфейс, затем тратить ресурсы на Compose-код, интеграцию и тесты.

## Основное правило: mockup-first
1. Сформулировать пользовательскую задачу и основные состояния.
2. Создать один или несколько статических визуальных макетов.
3. Исправлять и обсуждать макеты без функциональной реализации.
4. Получить явное одобрение владельца проекта.
5. Создать для утверждённого макета текстовую UI-спецификацию.
6. Только после этого переходить к функциональной реализации.
7. После реализации выполнить необходимые тесты и сравнить фактический экран с утверждённым макетом.

Мелкие локальные изменения — текст, подпись, небольшое перемещение существующего элемента и подобные правки — полного цикла не требуют.

## Пакет утверждённого интерфейса
Минимально:
- `docs/ui/mockups/<name>-vN.png` — визуальный эталон;
- `docs/ui/mockups/<name>-vN.md` — семантический и поведенческий контракт.

Для существенно разных состояний допускаются отдельные PNG.

### PNG определяет
- расположение элементов;
- визуальную иерархию;
- относительные размеры и интервалы;
- общий внешний вид;
- видимые состояния.

PNG не должен быть единственным источником смысла элемента.

### MD-спецификация определяет
- назначение экрана;
- значимые элементы;
- точные подписи и термины;
- интерактивные элементы и действия;
- обязательные/необязательные поля;
- состояния;
- согласованные ошибки и предупреждения;
- детали изображения, которые модель может неверно интерпретировать;
- существенные требования и иллюстративные детали.

## Приоритет при расхождениях
- MD имеет приоритет в семантике, данных и поведении.
- PNG имеет приоритет в визуальном расположении и композиции.
- При существенной неоднозначности агент не додумывает решение, а запрашивает уточнение.

## Передача агенту реализации
Задание должно явно называть оба файла и требовать прочитать их до изменения кода.

Рекомендуемая формулировка:

> Реализуй интерфейс по утверждённому визуальному макету `<PNG>`. Перед реализацией прочитай сопровождающую спецификацию `<MD>`. PNG является визуальным reference для композиции и расположения, MD — семантическим и поведенческим контрактом. Не додумывай существенные неоднозначные детали; при конфликте или недостатке информации остановись и запроси уточнение.

Макет не является разрешением самостоятельно менять принятые требования, модель данных или архитектуру.

## Состояния
Если экран существенно меняется, до реализации следует согласовать отдельные макеты либо явно описать состояния в MD: например пустой экран, заполненная форма, ошибка обязательного поля, фиксация азимута, добавленные медиа, просмотр сохранённой записи.

Отдельный макет для каждого незначительного состояния не требуется.

## После реализации
Для значимых экранов желательно сохранить скриншот фактической реализации и визуально сравнить его с утверждённым макетом.

Если отдельно не оговорено обратное, макет не является pixel-perfect контрактом: сохраняются адаптивность Android, доступность, системные отступы и корректная работа с реальным масштабом шрифта.

## Где mockup-first не обязателен
Room migrations, backup/restore, алгоритмы анализа, внутренние repository/service изменения, картографический/файловый pipeline и исправления без существенного изменения UI.

## Критерий перехода
Функциональная реализация нового или существенно переработанного UI начинается только после явного решения владельца проекта, что выбранный макет согласован. До этого макет — вариант дизайна, а не production-требование.
